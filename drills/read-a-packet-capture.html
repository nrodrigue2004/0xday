drill read-a-packet-capture

~/drills/read-a-packet-capture

Read a text packet capture line by line, spot a scan and an upload, and find which host received the stolen data.

1simple2mid3complex4hands-on

01 simple // the idea in plain words

A packet is one small envelope of data on the network. A capture tool such as tcpdump or Wireshark records packets, and a text capture is one line per packet. You do not need a GUI to read one.

Every line answers five questions: when, who sent it, who gets it, what kind of packet, and how much data.

09:14:02.104512 IP 10.0.5.23.51515 > 203.0.113.50.443: Flags [S], seq 1000, win 64240, length 0
  • 09:14:02.104512 is the time, down to the microsecond.
  • 10.0.5.23.51515 is the sender. The last number is the port: IP 10.0.5.23, port 51515. High random ports are normally the client.
  • > points to the receiver, 203.0.113.50.443: IP 203.0.113.50, port 443 (HTTPS).
  • Flags [S] is a TCP SYN, the first packet of a new connection.
  • length 0 means no data inside, just the envelope.

Three habits make this fast. Find the client (random high port) and the server (well-known port like 53, 80, 443). Follow one conversation by its two address-and-port pairs. Then ask what the conversation was for.

Never trust an address because it looks familiar. The capture only shows what was sent, not who really sent it.

Ports worth knowing by heart

22 SSH, 25 SMTP, 53 DNS, 80 HTTP, 123 NTP, 443 HTTPS, 445 SMB, 3389 RDP. Anything else needs a reason.

02 mid // how it's actually used

TCP flags, the part you read most

TCP uses flags to run a conversation. In a capture they sit between brackets.

  • S SYN: "I want to open a connection."
  • S. SYN-ACK: "OK, I am here." (the dot means ACK)
  • . ACK: "I got it." Nearly every packet after the start carries an ACK.
  • P. PSH-ACK: "Here is data, hand it up now."
  • F. FIN-ACK: "I am done, closing politely."
  • R or R. RST: "No. Or: abort now." A reset in reply to a SYN means the port is closed.

A normal connection starts with the three-way handshake: client S, server S., client ..

09:14:02.1045 IP 10.0.5.23.51515 > 203.0.113.50.443: Flags [S], seq 1000, length 0
09:14:02.1190 IP 203.0.113.50.443 > 10.0.5.23.51515: Flags [S.], seq 5000, ack 1001, length 0
09:14:02.1191 IP 10.0.5.23.51515 > 203.0.113.50.443: Flags [.], ack 5001, length 0

Notice the numbers: the server acknowledges 1001, which is the client's seq 1000 plus one. The ACK number always means "the next byte I expect from you".

What common traffic looks like

  • DNS is usually UDP port 53. A query line has the question (A? shop.example.com.) and the answer line has the result. DNS comes *before* most connections: a name is looked up, then a connection follows to the answer.
  • A scan is one source sending SYNs to many ports on one host (or one port across many hosts) in a few milliseconds. Closed ports answer with R., open ports with S..
  • An upload is a long run of packets from your machine with a large length (often 1448 on Ethernet) to one outside address. A download is the same, reversed.
  • A beacon is the same small connection at an even interval (every 60 seconds, say) to the same host.

Direction matters. A lot of bytes *from* a server to your workstation is a download. The same number of bytes *from* your workstation is data leaving.

Questions to ask a capture

  1. Who is talking the most? (count by address)
  2. Who is receiving the most data *from my hosts*? (sum lengths by destination)
  3. Which conversations never completed a handshake? (SYNs without SYN-ACKs)
  4. Is there a name lookup just before the odd connection?

03 complex // what the pros do

Sequence numbers and what they give you

Each side numbers the bytes it sends. seq 2001:3449 means "bytes 2001 up to, not including, 3449" and the length is the difference, 1448. The other side acknowledges with ack 3449. From this you can tell:

  • Retransmissions: the same seq range twice means the first copy was lost or ignored. Many of them mean a bad link, or a firewall silently dropping.
  • Missing data: a hole between ranges that never gets filled.
  • Total bytes in a flow: last seq minus first seq. Handy when the capture is huge and you cannot sum by hand.

Why 1448?

Ethernet's standard maximum packet is 1500 bytes. Subtract 20 for IP and 20 for TCP, leaving 1460. TCP timestamps use 12 more, so streams commonly carry 1448 bytes. When you see many equal lengths of 1448 in one direction, you are looking at a bulk transfer, because only a bulk sender fills packets to the maximum.

Reading without seeing inside

Most traffic today is TLS. You cannot read the content, but the shape still talks:

  • The SNI name in the TLS ClientHello (Wireshark: tls.handshake.extensions_server_name) says which site was asked for.
  • Size and timing reveal behavior: tiny regular packets look like beacons, a huge one-way stream looks like exfiltration, a burst of small packets both ways looks like an interactive shell.
  • A server on a strange high port (8443 is common, 4444 is a famous default) deserves a look. Port numbers prove nothing alone, but they start the question.

Capturing and filtering

Capture filters (BPF) drop packets before they are saved. Display filters (Wireshark) only hide them afterwards. They use different syntax.

tcpdump -nn -i eth0 host 10.0.5.23 and port 443     # BPF capture filter
tcpdump -nn -r web.pcap 'tcp[tcpflags] & tcp-syn != 0'   # read a file, SYNs only
tshark -r web.pcap -Y 'ip.src==10.0.5.23' -T fields -e ip.dst -e frame.len
tshark -r web.pcap -q -z conv,tcp      # per-conversation byte totals

-nn turns off name and port lookups. Always use it when investigating: a reverse DNS lookup of an attacker's address can alert them, and port names hide the real number.

Putting it together on a text capture

When you only have text, a shell pipeline is a fine analyzer: filter by direction with grep, pull out the field with awk, then sort | uniq -c. The lab does exactly that.

04 hands-on // sandbox shell

The SOC flagged workstation 10.0.5.23 for odd traffic. A text capture of its minute of activity is at ~/captures/ws23.txt.

It contains a normal HTTPS visit, a port scan from someone else, and a bulk upload of data to an outside host. Work out which outside IP received the most data *from* 10.0.5.23, and submit that IP address (no port).

Hint on the format: the receiver is the field after >, written as IP.port:.

Solve it in the sandbox. Type hint when stuck and submit <answer> when you have it.
