drill security-onion-intrusion-hunt

~/drills/security-onion-intrusion-hunt

Work a night of fictional Security Onion alerts, Zeek conn logs and DNS. Find the one host that is compromised and the server it phones home to.

1simple2mid3complex4hands-on

01 simple // the idea in plain words

A SIEM shows you hundreds of alerts. Almost all of them are noise: scans you started yourself, updates, software doing what software does. A hunt is how you find the few that matter.

The approach is the same every time:

  1. Rank by severity, but do not stop there. High-severity alerts are a starting point, not the answer.
  2. Pick a suspect (a host or an address) and pull everything about it.
  3. Build a timeline around the suspect: what happened just before, and just after?
  4. Ask what is regular. Software that talks to the same address every 60 seconds is either a clock or malware. Humans are not that regular.

In this lab the files are fictional, in the style of what Security Onion shows: an alert export, a Zeek conn.log (one line per connection) and a Zeek dns.log.

02 mid // how it's actually used

What each log tells you

  • alerts (Suricata): a rule matched. It says *what looked wrong*, not that anything is proven.
  • conn.log (Zeek): who talked to whom, when, on which port, and how many bytes. No content, but great for patterns.
  • dns.log (Zeek): which names a host looked up, and the answers. Malware usually has to look up its server.

Known noise, in this lab

10.20.0.66 is the Kali box. Scan alerts from it are *you*. Downloads from 198.51.100.77 are the update mirror every host uses. Neither is the story. Write that down in your notes so the next analyst does not chase it.

Pulling everything about one host

$ grep 10.20.0.50 ~/hunt/alerts.csv
$ grep 10.20.0.50 ~/hunt/conn.log | head
$ grep 10.20.0.50 ~/hunt/dns.log

Counting destinations

When you are not sure where a host is talking, count:

$ grep 10.20.0.50 ~/hunt/conn.log | awk '{print $3}' | sort | uniq -c | sort -rn

A destination with a very high count and very similar byte sizes is worth a look.

03 complex // what the pros do

Beaconing

Malware that checks in with its operator tends to do it on a timer: every 60 seconds, with a little jitter so it is not perfectly regular. The signature in conn.log is the same destination, the same port, tiny and nearly identical byte counts, running for hours. Look at the timestamps for one pair of addresses:

$ grep 198.51.100.44 ~/hunt/conn.log | head

Real tools do this at scale with Zeek scripts or RITA, but you can see it by eye in a short log.

The kill chain order

Even in a small data set you can often put the events in order: *delivery* (an executable downloaded), *execution* (the host starts talking to something new), *command and control* (the regular beacon). If you can find all three on one host, you have a confident finding, not a hunch.

Write the hypothesis first

A good hunt starts with a sentence: "If a workstation downloaded and ran something, I should see a new, regular outbound connection soon after." Then you test it against the logs. If the logs do not agree, the hypothesis was wrong, and that is a result too.

What to do next (outside this lab)

Isolate the host, capture memory and disk before wiping, block the destination at the firewall and the DNS server, then look for the same destination from other hosts. Write it up: the incident report generator turns your lab notes into a report.

Common mistakes

  • Treating a high-severity alert as the finding and stopping.
  • Chasing your own scanner. Always rule out your own tools first.
  • Calling it compromised from one alert. Get a second, independent kind of evidence (here: DNS plus conn).

04 hands-on // ticket queue

The overnight export is in ~/hunt. One internal host downloaded something and started beaconing to an outside server. Most of the alerts are noise, including scans from the Kali box (10.20.0.66) and traffic to the update mirror (198.51.100.77).

Find the host that is compromised, then find the outside IP address it beacons to. Resolve the ticket with that IP address.
