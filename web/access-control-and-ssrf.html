~/web/access-control-and-ssrf

Access control bugs let one user reach another user's data or an admin's features. Learn IDOR, privilege escalation, CSRF and SSRF, how they show up in logs, and the checks that stop them.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Logging in proves who you are. Access control decides what you may do. The bug is almost never that the check is hard. It is that the check is missing on one route that the developer forgot, or only done in the browser.

IDOR: insecure direct object reference

The app uses an ID from the request to fetch a record, and never asks whether *this user* owns it.

GET /invoices/1001   <- your invoice
GET /invoices/1002   <- someone else's, and the server happily returns it

*Fix:* on the server, look up the record and confirm it belongs to the signed-in user (or return 404). Random IDs (UUIDs) make guessing harder but do not replace the check.

Two directions of escalation

  • Horizontal: reach another user at the same level (user A reads user B's messages)
  • Vertical: reach a higher level (a normal user opens /admin or sends role=admin)

Forced browsing

Hiding the "Admin" link is not security. If /admin/users returns data to any logged-in user, the page is open. Every route needs its own server-side check.

The default rule

Deny by default. A new endpoint should be forbidden until someone writes the rule that allows it. Forgetting then fails closed, not open.

02 mid // how it's actually used

Where the checks go wrong

  • Checking only in the UI or the JavaScript, not on the API the UI calls
  • Protecting GET /orders/5 but not PUT /orders/5 or DELETE
  • Trusting a field the client sends (userId, isAdmin, role)
  • Different code paths for the web app and the mobile API, with checks in only one
  • Method override headers and alternate URLs (/Admin, /admin/, /admin;x) slipping past a path-based rule
  • Multi-step processes where step 3 trusts that step 2 happened

CSRF: cross-site request forgery

Your browser automatically attaches cookies to requests for a site. If a malicious page makes your browser send POST /transfer to your bank, the cookie goes along, and the bank thinks it was you.

Defenses that work:

  • Anti-CSRF tokens: a random value in each form that the attacker's page cannot know
  • SameSite cookies (Lax is the browser default now), which stop most cross-site sends
  • Require a custom header for API calls, and check Origin
  • Re-authenticate for sensitive actions

CSRF needs the victim to be logged in and the action to be predictable. It does not let the attacker read responses.

SSRF: server-side request forgery

A feature fetches a URL on the user's behalf (link preview, image import, webhook). The attacker supplies a URL that points inward:

  • http://localhost:8080/admin or http://10.0.0.5/ (internal services)
  • http://169.254.169.254/latest/meta-data/ (the cloud metadata service, which can hand out credentials)

Because the request comes from the trusted server, firewalls and "internal only" pages do not stop it. This is the Capital One breach pattern.

*Fixes:* allow-list the destinations you really need, resolve the hostname and check the IP after DNS, block link-local and private ranges, do not follow redirects blindly, never return the raw response, and on AWS use IMDSv2 (it needs a token header, which many SSRF bugs cannot send).

03 complex // what the pros do

Finding IDOR at scale

Build two test accounts. Do an action as A, then replay A's requests with B's cookie (Autorize does this). Look beyond URLs: IDs hide in JSON bodies, headers, GraphQL arguments and cookies. Test every verb. Also check indirect references: an export file name that is a sequential number.

Authorization models, quickly

  • RBAC: roles (admin, editor, viewer) carry permissions
  • ABAC: rules over attributes (department, time, record owner)
  • ACL: a list per object saying who may do what
  • Ownership checks: the rule behind most IDOR fixes (record.owner_id == session.user_id)

Centralize the check in one policy layer (middleware, decorator, policy engine) so a new route cannot skip it.

Blind SSRF and bypasses

When the response is not shown, you prove SSRF with a callback you control, or by timing. Attackers get around naive blacklists with decimal or hex IPs (2130706433), IPv6, a domain that resolves to 127.0.0.1, DNS rebinding (a name that resolves to a public IP at check time, then an internal one at use time), and open redirects on an allowed host. This is why the check belongs *after* resolution, on the real connect address.

Other related bugs

  • Open redirect: ?next=https://evil.example after login. Allow-list the destination
  • Path traversal: ../ in a file parameter; resolve and confirm the final path stays inside the allowed folder
  • CORS misconfiguration: reflecting any Origin with credentials allowed lets a hostile site read responses
  • Clickjacking: framing the page; use X-Frame-Options or CSP frame-ancestors

Detection

  • One session requesting many sequential or random IDs it does not own (low 200 rate for foreign IDs, many 403/404)
  • A 200 for a resource whose owner differs from the session user: log owner and caller together
  • Outbound requests from the app tier to metadata IPs or internal ranges
  • Cross-site POSTs with a missing or foreign Origin header
