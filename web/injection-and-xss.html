Injection happens when user input is treated as part of a command, query or page. Learn how SQL injection, command injection and XSS work, how to confirm them safely in a lab, and the fix that stops each one.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Injection means the app builds an instruction (a SQL query, a shell command, an HTML page) by gluing user input into a string, and the interpreter cannot tell where the programmer's text stops and the attacker's starts.

SQL injection (SQLi)

The app wants this query:

SELECT name FROM users WHERE id = '7'

but builds it with string concatenation: "... WHERE id = '" + id + "'". If the input is 7' OR '1'='1, the query becomes ... WHERE id = '7' OR '1'='1', which is true for every row. The user input changed the *structure* of the query.

The fix is a parameterized query (also called a prepared statement). The query shape is sent first with a placeholder, the value is sent separately, and the database never treats the value as code.

Command injection

An app that runs ping <host> using the shell can be fed 127.0.0.1; id. The ; ends the first command and starts another. *Fix:* do not call a shell. Use a library function, or pass arguments as a list so no shell parses them.

Cross-site scripting (XSS)

The app puts user input into a web page without encoding it, so the browser runs it as script. Three types:

  • Reflected: the payload is in the request (a link) and echoed straight back
  • Stored: the payload is saved (a comment, a profile name) and runs for every visitor
  • DOM-based: client-side JavaScript writes untrusted data into the page itself

What XSS lets an attacker do: act as the victim in the app, read what the page shows, steal tokens that are not protected, show fake login boxes. *Fix:* encode output for the place it lands (HTML body, attribute, JavaScript, URL) and let your template engine auto-escape.

Practice only on lab apps (DVWA, Juice Shop, WebGoat, PortSwigger labs). Probing a real site with these inputs can be a crime even when "nothing happened".

02 mid // how it's actually used

Confirming SQL injection safely (in a lab)

  1. Add a single quote ' to a parameter. A database error or a changed page suggests the input reaches a query
  2. Test logic: ' OR '1'='1 versus ' AND '1'='2 give different pages
  3. Find the column count with ORDER BY n or UNION SELECT NULL,... until errors stop
  4. Only in your own lab: read data with UNION SELECT
  5. Blind SQLi: no output, so you ask true/false questions (AND SUBSTRING(...)='a') or use time delays (SLEEP(5))

Tools like sqlmap automate this. In a real test they run only with permission and a throttle, since they send a lot of traffic.

Defenses that actually work

  • Parameterized queries / ORM bound parameters for every value. This is the answer, not filtering quotes
  • Allow-list for things that cannot be parameterized (column names, sort direction)
  • Least privilege database account: the web app should not be able to DROP TABLE or read other schemas
  • Hide errors from users, log them server-side

XSS in more detail

Where the input lands decides the payload and the fix:

Other defenses: Content-Security-Policy (limits which scripts can run), HttpOnly cookies (JavaScript cannot read the session), textContent instead of innerHTML, and a sanitizer library (DOMPurify) when HTML must be allowed.

Other injections to know by name

  • Template injection (SSTI): user input is evaluated by the template engine ({{7*7}} renders 49)
  • NoSQL injection: operators like {"$ne": null} in a JSON login body
  • LDAP / XPath injection: same idea, different language
  • Header injection: line breaks in a value split an HTTP response

03 complex // what the pros do

Second-order and blind cases

Second-order SQLi stores the payload safely, then a *different* feature reads it back and concatenates it into a query. A scanner that tests each page alone misses it, so trace where stored values are reused.

For blind command injection, prove it with a harmless time delay (sleep 5) or a DNS callback you control. Never run destructive commands to "prove impact"; id or a delay is enough evidence.

Bypassing weak filters (why filtering is not a fix)

Blacklists fail: case changes (SeLeCt), comments inside keywords, alternate encodings (URL, double URL, HTML entities, Unicode), or a different tag or event handler for XSS. Each bypass is trivial because the real bug, mixing code and data, is still there. If you find yourself adding to a blacklist, switch to parameterization or output encoding.

Reading code for injection

In a code review, search for: string formatting or + near SELECT/INSERT; exec, system, popen, Runtime.exec, os.system, shell=True; innerHTML, document.write, dangerouslySetInnerHTML, |safe; eval, pickle.loads, yaml.load. Follow each one back to see whether user input reaches it. Frameworks make this safe by default, then people opt out.

Detection

  • WAF or web log: ', --, UNION, SELECT, <script, onerror= in query strings or bodies; a spike of 500 errors from one source
  • Database logs: syntax errors, a query that returns a huge row count
  • Alert on the *response* too: an unusually large response from a normal endpoint

Fixing it in a report

Give the vulnerable line, the corrected line (the parameterized version) and the test that proves it: send the same payload and show it is treated as plain text.
