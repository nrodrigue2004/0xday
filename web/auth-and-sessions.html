Logging in and staying logged in are where most real breaches start. Learn how passwords should be stored, how cookies and tokens carry a session, what a JWT is, and the mistakes that let attackers in.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Authentication answers "who are you?". Authorization answers "what may you do?". Session management is how the app remembers the answer between requests, because HTTP itself remembers nothing.

The flow

  1. You send a username and password
  2. The server checks them and creates a session: a random ID stored in its memory or database
  3. It sends the ID back in a cookie
  4. Your browser sends that cookie with every later request, and the server looks it up

So the session ID is as good as the password for as long as it lives. Anyone who steals it *is* you.

Cookie flags that matter

FlagWhat it does
Secureonly sent over HTTPS
HttpOnlyJavaScript cannot read it, which limits what XSS can steal
SameSite=Lax or Strictnot sent on most cross-site requests, which blunts CSRF
Max-Age / Expireshow long it lives

Passwords done right

  • Never store the password. Store a slow salted hash: bcrypt, scrypt or Argon2
  • Never use plain MD5, SHA-1 or unsalted SHA-256 for passwords: they are built to be fast, so attackers try billions per second
  • Require length (12+ is a good floor) over weird symbol rules, and check against lists of breached passwords
  • Offer MFA. An authenticator app or security key stops almost all credential stuffing

02 mid // how it's actually used

Common authentication failures

  • Credential stuffing: attackers replay leaked username/password pairs from other sites. Defenses: MFA, rate limits per account and per IP, breached-password checks
  • Brute force and password spraying: spraying tries one weak password across many accounts to avoid lockouts. Defense: alert on many accounts failing from one source
  • User enumeration: "no such user" versus "wrong password", or a response that takes longer for real users. Use one message and similar timing
  • Weak reset flow: guessable tokens, tokens that never expire, a reset link built from the Host header. Reset tokens must be random, single-use and short-lived
  • Default and hard-coded credentials: admin/admin, keys in source control

Session weaknesses

  • Session fixation: the attacker gives you a session ID before login and the app keeps it after. *Fix:* issue a new ID on login
  • Predictable IDs: sequential or timestamp-based. Use a cryptographically random value of 128 bits or more
  • No expiry or logout that does nothing: the server must invalidate the session, not just delete the cookie
  • Session in the URL: leaks through logs and the Referer header

JSON Web Tokens (JWT)

A JWT has three base64url parts separated by dots: header.payload.signature. The header and payload are readable by anyone (decode them, no key needed). The signature only proves they were not changed.

header   {"alg":"HS256","typ":"JWT"}
payload  {"sub":"1042","role":"user","exp":1767225600}

Typical mistakes:

  • Putting secrets in the payload (it is not encrypted)
  • Accepting "alg":"none" so an unsigned token is trusted
  • Using a weak HMAC secret that can be guessed offline
  • Trusting the role claim without checking the signature, or never checking exp
  • Confusing algorithms (an RSA public key used as an HMAC secret)
  • No way to revoke a stolen token before it expires, so keep lifetimes short and rotate refresh tokens

03 complex // what the pros do

OAuth 2.0 and OpenID Connect in one paragraph

OAuth 2.0 lets an app act with limited permission on your behalf without learning your password (authorization). OpenID Connect adds a standard way to prove who you are (authentication). The safe flow for web and mobile apps is authorization code with PKCE. Common bugs: an unvalidated redirect_uri, a missing state parameter (CSRF on the login), tokens in the URL fragment, and treating "the user came from the identity provider" as proof of identity.

MFA and its limits

Codes sent by SMS can be intercepted (SIM swap). Push approvals suffer MFA fatigue attacks. FIDO2/WebAuthn keys and passkeys are bound to the real site, so a phishing page cannot use them. That is why they are the strongest common option.

Testing checklist

  1. Log in; inspect the cookie flags in dev tools
  2. Log in again from another browser; are session IDs random and new?
  3. Log out, then replay the old cookie in Repeater: does it still work?
  4. Change a user ID or role in a JWT payload: is the signature actually verified?
  5. Request password reset twice: are tokens different, single-use, expiring?
  6. Send 20 wrong passwords: is there a throttle or lockout, and does it leak user existence?
  7. Try the same flow without the cookie at all

Detection

Alert on impossible travel, many failed logins across accounts, a successful login right after many failures, new device plus password reset, and the same session ID from two countries.
