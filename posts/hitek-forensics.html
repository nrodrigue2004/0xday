Reconstructing a Data Exfiltration: The HiTek Forensics Challenge

2026-09-07Nathan#forensics #wireshark #autopsy #incident-response

The HiTek Forensics Challenge was the capstone exercise in my Digital Forensics course at LSU. My team of five got two disk images, a Windows workstation and an Ubuntu server, plus one packet capture, and a single question: what left the building, how, and who did it?

Forensics is a reconstruction problem. You work backwards from artifacts to events, the artifacts are incomplete (sometimes on purpose), and every conclusion has to point at a specific piece of evidence. This is how we rebuilt the case.

The scene

host          ip            os           role
WIN-WS-01     192.168.0.6   Windows      suspect's workstation
web-srv-02    192.168.0.8   Ubuntu       FTP + web server (staging)
(unnamed)     192.168.0.4   Mac OS X     retrieval machine

Toolkit: FTK Imager and Autopsy for the disks, Wireshark for network.pcapng, John the Ripper, impacket-secretsdump and CrackStation for credentials, and plain Linux tools for the logs.

Step 1: get everyone's passwords

Recovering credentials early meant we could tie each action in the logs and the capture to a specific account instead of guessing.

  • Ubuntu: pulled the SHA-512 hashes from /etc/shadow and ran John with rockyou.
  • Windows: exported the SAM and SYSTEM hives with Autopsy, dumped NT hashes with secretsdump, and fed them to CrackStation.
$ john --wordlist=rockyou.txt shadow.txt
$ impacket-secretsdump -sam SAM -system SYSTEM LOCAL

account      box        password
webmaster    ubuntu     password
cknight      ubuntu     popcorn
carson       windows    123456     (admin)
jonathan     windows    letmein
tester       windows    monkey     (hint: "the zoo")

Every password was in the top of any wordlist. That's a finding on its own, separate from the case. The tester password was double-confirmed by its hint and a monkey picture sitting in the browser cache, which is the kind of detail that makes forensics fun.

Step 2: the night before (Nov 27)

auth.log and the webmaster's bash history showed a login at 23:13. Over the next 24 minutes:

sudo apt-get install apache2 apache2-doc apache2-utils
sudo apt-get install vsftpd
sudo nano /etc/vsftpd.conf
sudo apt-get install mysql-server
echo "create database website;" | mysql -u root -p
sudo chmod 777 /var/www      # <- the important one
ifconfig

chmod 777 on the web root means anything dropped in over FTP is instantly downloadable over HTTP by anyone, no login needed. The server was being set up as an open staging point the night before anything was stolen.

Step 3: the exfil (Nov 28)

File metadata on the Windows image showed two password-protected archives, secrets.zip and BusinessStrategy.zip, created around 15:45. The capture picks it up from there. FTP is plaintext, so Wireshark showed the login, the credentials and the file names outright.

ftp || ftp-data
ip.addr == 192.168.0.6 && ip.addr == 192.168.0.8
ip.src == 192.168.0.4 && http
Nov 27 23:13  webmaster logs in to web-srv-02, installs apache2/vsftpd/mysql
Nov 27 23:37  chmod 777 /var/www
Nov 28 ~15:45 secrets.zip + BusinessStrategy.zip created on WIN-WS-01
Nov 28 15:46:30  STOR BusinessStrategy.zip  .6 -> .8 (as webmaster)
Nov 28 15:52:06  STOR secrets.zip           .6 -> .8 (as webmaster)
Nov 28 >15:52    HTTP GET both zips         .4 -> .8 (no auth)
Nov 28 after     zips deleted from WIN-WS-01 and /var/www
Nov 28 17:52:02  web-srv-02 shuts down

Three hops: compress on Windows, stage on the Ubuntu box over FTP, pull from the web server with a Mac.

Step 4: the cover-up that didn't work

  • Deletion: both ZIPs were deleted from the workstation and the server. On NTFS, deleting a file only marks its clusters free. Nothing had overwritten them yet, so Autopsy carved both archives back out of unallocated space.
  • Encryption: the archives were password-protected, so we could prove what moved by name and metadata but not what was inside.
  • Ambiguity: chmod 777 looks like a lazy admin mistake. Without the rest of the timeline it would have been easy to wave off.

Step 5: who

Several independent threads point at carson:

  • The FTP uploads came from 192.168.0.6, carson's workstation.
  • They used the same webmaster credentials that configured the server the night before, and carson, as a Windows admin, had the access to get them.
  • Evaluations.odt in carson's Documents held a supervisor note about carson installing the wrong VMware version on every office machine: a history of misusing admin access and a plausible grudge. Projects.odt confirmed the IT role.
  • The other accounts came up clean. tester was just browsing (YouTube, Google, Amazon, starwars.com) and jonathan had nothing in the window. Ruling people out mattered as much as ruling carson in.

What the evidence doesn't prove

I think being honest about the gaps is part of the job. We proved the activity came from carson's machine with webmaster credentials, not that carson was physically at the keyboard. A real case would need physical access logs, interviews, and a check for remote access. And without the ZIP passwords, we never confirmed what data was actually inside the archives.

Takeaways

  • No malware, no exploit. Everything here was apt, FTP, a web server and a delete key. An insider with admin rights can do this on most networks.
  • Signatures would have missed it. No bad hashes, no bad IPs. What was detectable was behavior: an admin creating archives and immediately moving them out, then deleting them. That's a UEBA / DLP problem, not an antivirus one.
  • Deletion isn't destruction. Without overwriting the sectors, deleted files are just waiting to be carved.
  • The story is the deliverable. Each artifact alone is ambiguous. Lined up in order and tied to accounts and timestamps, they tell one story.

We delivered a full investigative report with a relationship map of every user, host and transfer, plus a presentation. Rebuilding it here was a good excuse to re-read the bash history one more time.
