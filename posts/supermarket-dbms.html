Designing a Supermarket Database (and Its Checkout Transaction)

2025-12-03Nathan#sql #databases #python

For my database systems course, my team designed and built a multi-branch supermarket database and a command-line checkout app on top of it. The point was to practice the whole pipeline: requirements, an E-R diagram, a relational schema, test data, SQL queries and an application that actually uses them.

The problem

A supermarket chain with several branches needs one place to keep prices, stock and sales. Without it, every branch tracks everything by hand, and nobody can see revenue or stock across the company.

Relational schema

StoreBranch(branch_id PK, name, address, phone)
Product(product_id PK, name, barcode UNIQUE, unit_price, is_active, category)
Inventory(branch_id PK/FK, product_id PK/FK, quantity)
Sale(sale_id PK, branch_id FK, sale_datetime, total_amount)
SaleItem(sale_id PK/FK, product_id PK/FK, quantity, unit_price, discount)
  • Inventory is a junction table with a composite key, so the same product can be stocked at many branches with a different quantity at each.
  • SaleItem copies unit_price at the time of sale. That way, changing a price later never rewrites history.
  • Foreign keys are switched on (PRAGMA foreign_keys = ON), because SQLite doesn't enforce them by default.

The checkout transaction

The part I find most interesting is checkout. It has to either completely happen or not happen at all, so it runs inside one transaction: check stock for every item in the cart again, insert the sale, insert each sale line, and subtract inventory. If anything fails, the whole thing rolls back.

BEGIN;
  -- re-check stock for every cart item
  INSERT INTO Sale (branch_id, sale_datetime, total_amount) VALUES (?, datetime('now'), ?);
  INSERT INTO SaleItem (...) VALUES (...);          -- per cart line
  UPDATE Inventory SET quantity = quantity - ? WHERE branch_id = ? AND product_id = ?;
COMMIT;   -- any error: ROLLBACK

Re-checking stock inside the transaction matters: the stock you saw when you added to the cart may not be what's left when you pay.

Reports

Queries live in a plain queries.sql file, each tagged with -- name: .... The app loads them by name and runs them from a Statistics menu, so adding a report means adding SQL and not changing Python.

-- revenue by category
SELECT p.category,
       ROUND(SUM((si.unit_price - si.discount) * si.quantity), 2) AS revenue
FROM SaleItem si
JOIN Product p ON si.product_id = p.product_id
GROUP BY p.category;

There are 16 in total, including sales history, revenue per day, top sellers, low stock, inventory value per product, and products that never sold (a LEFT JOIN with WHERE ... IS NULL).

The app

=== LSU Market CLI ===
1. List available products
2. Add product to cart
3. View cart
4. Checkout
5. Statistics
6. Exit

Python with SQLite, a plain menu, and a seeded sample dataset of products, stock and sales. The repo includes the schema, data, queries and a rebuild guide so anyone can recreate the database from scratch in four commands.

What I'd improve

  • Use parameterized queries everywhere (checkout already does) and move the statistics menu to a loop instead of one block per report.
  • Add indexes on the sale date and on SaleItem.product_id once the data grows.
  • Track stock changes in their own table (receiving, returns, shrinkage) so inventory is auditable and not just a number that goes down.

It was a team project, and my part was the data generation, the relational schema and the written report. Source: CSC4402-Supermarket.
