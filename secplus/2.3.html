2.3 Explain various types of vulnerabilities

key ideas

  • Application: memory injection, buffer overflow, race conditions (TOCTOU), malicious updates.
  • Web: SQL injection, cross-site scripting (XSS). OS-based, hardware (firmware, end-of-life, legacy).
  • Virtualization: VM escape, resource reuse. Cloud-specific, supply chain (service/hardware/software providers).
  • Cryptographic weaknesses, misconfiguration, mobile (sideloading, jailbreaking), zero-day.

study notes

A vulnerability is a weakness an attacker can exploit. Objective 2.3 lists the families you must recognize in a scenario. For each one, learn what it is, how it shows up, and the mitigation.

Application vulnerabilities

Memory injection: malicious code is placed into a running process's memory (often by a malicious DLL or code injection into a trusted process), so it runs with that process's privileges and hides inside a legitimate name. Mitigation: endpoint protection, memory protections, application control, patching.

Buffer overflow: the program writes more data into a fixed-size buffer than it can hold, spilling into adjacent memory. The attacker can crash the program or overwrite a return address to run their own code. Mitigations: input validation and bounds checking, safe languages, ASLR (random memory layout), DEP/NX (data pages can't execute), stack canaries, patching. Seen as a crash or unexpected behavior after oversized input.

Race condition: the outcome depends on timing between operations. The classic is time-of-check to time-of-use (TOCTOU): the program checks a condition, then acts on it, and an attacker changes the state in between. Related: time-of-use errors and file/temp-file races. Mitigation: atomic operations, locks, minimize the gap, secure coding.

Malicious update: an attacker poisons a software update channel or fake update prompt to deliver malware (this is also a supply chain risk). Mitigation: update only from the vendor, verify digital signatures and hashes, use trusted repositories, test updates, application control.

SQL injection (SQLi): user input is placed into a SQL statement, letting the attacker change the query (for example ' OR 1=1 --). Impact: read, change or delete data, bypass login. Mitigations: parameterized queries / prepared statements, input validation, stored procedures, least-privilege database accounts, web application firewall. Don't rely on blocklists of bad characters.

Cross-site scripting (XSS): the attacker gets script to run in another user's browser in the context of a trusted site.

TypeHow it works
Reflected (non-persistent)Script is in a crafted link; the server echoes it back immediately in the response. Needs the victim to click

Impact: steal session cookies, redirect users, act as the user. Mitigations: output encoding, input validation, Content Security Policy, HttpOnly cookies, frameworks that escape by default. Contrast with CSRF, which makes a logged-in browser send an unintended request (see 2.4).

Operating system vulnerabilities

Unpatched flaws, privilege escalation bugs, insecure default settings, unneeded services, outdated or end-of-life OS versions. Mitigation: patch management, hardening baselines, remove unused components, endpoint protection, vulnerability scanning.

Hardware vulnerabilities

  • Firmware flaws (BIOS/UEFI, network device firmware, printers): hard to patch and invisible to most tools.
  • End-of-life hardware that no longer receives updates.
  • Legacy devices that can't support modern security.
  • Speculative execution CPU flaws (Meltdown, Spectre) that let one process read another's data.
  • Mitigations: firmware updates, retire unsupported hardware, secure boot, supply chain verification, isolation.

Virtualization vulnerabilities

  • VM escape: code running in a guest breaks out to the hypervisor or other VMs. Rare but severe, because the hypervisor controls everything.
  • VM sprawl: unmanaged, forgotten virtual machines that never get patched or monitored.
  • Resource reuse: memory or storage from one VM leaking into another.
  • Mitigations: patch the hypervisor, limit who can manage it, inventory and decommission VMs, segment management networks, separate sensitive VMs.

Cloud-specific vulnerabilities

Misconfigured storage buckets, overly broad IAM roles, exposed management consoles and APIs, weak keys, lack of logging, and misunderstanding the shared responsibility model (the provider secures the cloud itself; the customer secures their data, access and configuration). Mitigations: CSPM tools, least privilege IAM, encryption, MFA, logging, regular configuration review.

Supply chain vulnerabilities

Compromise through a service provider, hardware provider or software provider: a tainted firmware, a backdoored library, a compromised MSP. Mitigations: vendor due diligence, software bills of materials, signed code, limit vendor access, monitor third-party connections, validate hardware sources.

Misconfiguration vulnerabilities

  • Open permissions (world-readable files and shares), unsecured admin accounts, default accounts and passwords, open ports and unneeded services, insecure protocols (Telnet, FTP, HTTP), weak encryption settings, verbose error messages that leak details.
  • Mitigations: secure baselines and hardening guides, configuration management, change control, automated audits, vulnerability scans.

Mobile device vulnerabilities

  • Jailbreaking / rooting removes OS protections and lets unsigned code run.
  • Sideloading installs apps outside the official store, skipping its review.
  • Outdated OS, malicious apps, unencrypted data, insecure Wi-Fi, lost devices.
  • Mitigations: MDM, app allow lists, enforce updates and encryption, block jailbroken devices.

Zero-day vulnerabilities

A flaw unknown to the vendor (and so unpatched) that attackers are already exploiting or could. The vendor has had "zero days" to fix it. Mitigations: defense in depth, segmentation, EDR/behavior detection, rapid response, virtual patching (WAF/IPS rules), threat intelligence. Once a patch exists it is no longer a zero-day, only a known unpatched vulnerability.
