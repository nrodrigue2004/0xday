SY0-701domain 4.0 · Security Operations4.9

4.9 Given a scenario, use data sources to support an investigation

key ideas

  • Log data: firewall, application, endpoint, OS-specific security logs, IPS/IDS, network logs, metadata.
  • Data sources: vulnerability scans, automated reports, dashboards, packet captures.

study notes

When something goes wrong, data sources tell the story. Objective 4.9 asks which log or data source answers a given question, and how to use it.

Log data

Logs are time-ordered records of events. A good investigation correlates several sources by timestamp, so time synchronization (NTP) matters.

SourceWhat it recordsTypical use
Firewall logsAllowed/denied connections: IPs, ports, protocols, bytesFind scans, blocked attacks, exfiltration, command-and-control traffic
Application logsApplication events and errorsTrace what a user or attacker did inside an app; find failed logins, crashes
Endpoint logsOS and security events on hosts (Windows Security log, auditd, EDR)Logons, process creation, file and registry changes, privilege use
OS-specific security logsAuthentication, account changes, policy changesAccount lockouts, privilege escalation, new accounts
IPS/IDS logsSignature matches and alertsWhat attack patterns were seen and from where
Network logsSwitch, router, DNS, DHCP, proxy, VPN, wireless controllerWho had which IP, which domains were looked up, who connected remotely
MetadataData about data: email headers, file properties (author, timestamps), EXIF, mobile call/location records, web request headersWho created/sent something, when, from where

Related sources:

  • Vulnerability scan output shows weaknesses present at scan time.
  • Automated reports from SIEM and dashboards summarize activity and trends.
  • Packet captures (full content) vs NetFlow (conversation summaries).
  • Web server and DNS logs: attack patterns (scans, SQLi attempts), suspicious domains.
  • Authentication logs (RADIUS, Active Directory, SSO, VPN): who logged in, from where, success or failure.
  • Cloud audit logs (API calls, console activity).
  • Mobile logs and location data.
  • Database logs for queries and access.
  • Syslog consolidates logs from network devices and Linux/Unix.

Using the data

  • Aggregate logs in a SIEM so you can search across sources and see an end-to-end timeline.
  • Correlate: link events from different systems (a DHCP lease, a firewall log and an endpoint log tell one story).
  • Normalize formats and time zones.
  • Protect integrity: send logs to a central write-once store so attackers can't delete them. Missing logs are an indicator of compromise.
  • Retention must meet investigation and regulatory needs.
  • Packet captures and dashboards help visualize patterns and trends.

Choosing the right source (exam style)

QuestionBest source

More detail from the lessons

  • Firewall log fields: timestamp, source IP (and on some NGFWs the receiving MAC), destination IP, port, application, and the disposition (allowed or blocked). An NGFW adds application and URL-category visibility plus anomaly hints. DNS sinkhole hits in the logs can point to an infected internal host.
  • Application logs: Windows Event Viewer's Application section; on Linux and macOS look under /var/log. Everything usually rolls up into the SIEM, where it can be filtered several ways.
  • Endpoint logs: logon and logoff, system events, running processes, device management events (password changes, lockouts) and directory service activity.
  • OS security logs catch brute force attempts, changes to critical system files and authentication events. One odd entry, such as a service disabled that an admin would not normally disable, can raise an alert and stop an attack early.
  • Send only what matters to the SIEM: collecting everything is costly, so forward the data useful for security decisions.
  • IPS/IDS functions now usually live inside the NGFW. A Snort-style entry shows timestamp, alert class (for example a possible DoS via SYN flood), priority, and source and destination IP and port.
  • Network device logs (switches, routers, access points, VPN concentrators) show routing table changes, failed authentication to the device and attacks. Example: a switch logs a TCP SYN attack on a port and auto-blocks the SYN traffic for 60 seconds.
  • Metadata: email headers (sending servers, SPF and signature details), photo EXIF (device and GPS coordinates), browser data (OS, browser type, IP), and document properties (author, title, contact details).
  • Vulnerability scan logs reveal hosts with no firewall, antivirus or anti-spyware, open shares needing no credentials, guest accounts left on, unsupported operating systems and world-readable NFS shares. Update the scanner's signatures first so it knows current vulnerabilities.
  • Automated reports are only useful if someone reads them; on terabytes of data, narrow reports run faster. A dashboard is a live at-a-glance view (active firewall rules, warnings, users and devices) for the SOC screen and generally avoids long-term data because that takes too long to compile.
  • Packet captures: Wireshark on wired or wireless networks, and some switches, routers and firewalls can capture themselves. The top pane lists each packet (for example an HTTP GET); the detail pane breaks one frame into Ethernet, IPv4, TCP and HTTP layers.

Exam traps

  • Metadata is data about data; it can prove who and when without revealing content.
  • A packet capture shows content; NetFlow shows only who talked to whom.
  • Firewall logs won't show what happened inside an encrypted session or inside the host; use endpoint logs.
  • Accurate time across devices is what makes correlation possible.
