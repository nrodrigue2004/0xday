SY0-701domain 3.0 · Security Architecture3.1

3.1 Compare and contrast security implications of different architecture models

key ideas

  • Cloud: responsibility matrix (shared responsibility), hybrid, third-party vendors. IaC, serverless, microservices.
  • Network infrastructure: physical isolation (air-gapped), logical segmentation, SDN.
  • On-premises, centralized vs decentralized, containerization, virtualization, IoT, ICS/SCADA, RTOS, embedded systems, high availability.
  • Considerations: availability, resilience, cost, responsiveness, scalability, ease of deployment, risk transference, ease of recovery, patch availability, inability to patch, power, compute.

study notes

Objective 3.1 compares architecture models and the security trade-offs of each. The pattern is the same everywhere: what does this model give you, what does it cost you, and who is responsible for securing which part.

Cloud infrastructure

Service models (what you rent):

ModelYou getCustomer securesProvider secures
IaaS (infrastructure)Virtual machines, storage, networksOS, apps, data, configuration, accessHardware, hypervisor, facility
PaaS (platform)A runtime to deploy codeApp code, data, accessOS, runtime, infrastructure
SaaS (software)A finished applicationData, user access, configurationEverything else

The shared responsibility model: the provider is responsible for security *of* the cloud, the customer for security *in* the cloud. The more managed the service, the more the provider handles, but the customer always keeps responsibility for their data and who can access it.

Deployment models: public (shared provider infrastructure), private (dedicated to one organization), community (shared by organizations with common needs), hybrid (mix of cloud and on-prem or multiple clouds). Multi-cloud uses more than one provider (resilience, avoids lock-in, more to manage).

Other cloud concepts:

  • Third-party vendors add supply chain risk and need contracts, assessments and monitoring.
  • Infrastructure as code (IaC): define servers and networks in versioned code so builds are repeatable and reviewable. Misconfigurations can be copied everywhere, so scan templates.
  • Serverless / function as a service: you run code without managing servers. The provider handles scaling and patching; you still secure code, permissions and data.
  • Microservices: an application split into small independent services that communicate by API. Easier to scale and update, but more network connections and APIs to secure.
  • Software-defined networking (SDN): separates the control plane from data forwarding so networks are configured centrally by software. SD-WAN does the same for wide area links.
  • On-premises: you run everything. Maximum control, maximum responsibility and capital cost.
  • Centralized vs decentralized: central control is easier to manage and secure; decentralized spreads risk but is harder to manage consistently.

Network infrastructure concepts

  • Physical isolation / air gap: no network connection to anything else. Used for the most sensitive systems (classified networks, ICS). Data moves only by controlled removable media, which is itself a risk.
  • Logical segmentation: VLANs, subnets, firewalls and access control lists separate traffic on shared hardware.
  • Network layers matter when choosing devices: switches (layer 2), routers (layer 3), firewalls (3 to 7).
  • Software-defined networking (above) and zero trust (1.2) both reduce implicit trust.

Other infrastructure concepts

  • Virtualization: multiple VMs on one host. Isolation is strong but not perfect (VM escape, sprawl, see 2.3).
  • Containerization (Docker, Kubernetes): packages an app with its dependencies, sharing the host OS kernel. Lighter than VMs, weaker isolation, so secure the images, the registry and the orchestrator.
  • Internet of Things (IoT): smart devices, cameras, sensors. Often weak default credentials, little patching, long life. Segment on their own VLAN.
  • Industrial control systems (ICS) / SCADA: supervisory control of industrial processes. Availability and safety come first; systems are old and patching is difficult. Isolate from IT networks. PLCs (programmable logic controllers) run physical equipment.
  • Real-time operating systems (RTOS): strict timing, minimal features, used in embedded devices. Security patches are rare.
  • Embedded systems: dedicated hardware/software inside a device (appliances, vehicles, medical devices). Hard to update and monitor.
  • High availability (HA): redundancy so a failure does not interrupt service (clusters, load balancers, redundant power and links).

Infrastructure considerations

When picking an architecture, weigh:

ConsiderationQuestion
AvailabilityHow much downtime is acceptable?
ResilienceCan it keep working, or recover quickly, after failure?
CostCapital vs operating expense; security tools; staff
ResponsivenessLatency and performance for users
ScalabilityCan it grow (or shrink) with demand? Cloud scales elastically
Ease of deploymentHow fast and consistent is setup? IaC helps
Risk transferenceCan risk be moved to a provider or insurer? (Not responsibility)
Ease of recoveryHow quickly can it be restored?
Patch availabilityWill the vendor release fixes?
Inability to patchCommon for ICS, IoT, embedded: needs isolation and compensating controls
Power and computeResource needs, especially for low-power or edge devices

More detail from the lessons

Cloud responsibility and hybrid

  • Providers publish a responsibility matrix for SaaS, PaaS, IaaS and on-premises; each provider's differs and a contract can modify it. Example from the lesson: the OS is the provider's job for SaaS and PaaS and the customer's for IaaS and on-prem, but accounts and identities are always the customer's responsibility.
  • Hybrid here means using multiple clouds across different providers (the lesson's framing). Costs: providers do not talk to each other, so authentication, server and firewall settings must be configured separately and kept matching; logs use different formats and terminology; and data moving between clouds crosses the public internet, so protect it in transit.
  • Third parties on top of the cloud (for example a third-party firewall in front of your app) need a vendor risk management policy, a shared incident response process with all parties, and continuous monitoring of security and availability.
  • Infrastructure as code: describe hosts, web servers and database servers as code, tweak the code, and rebuild a perfect instance on any provider at any time.
  • Serverless: the app is broken into individual functions; each runs only when needed, in whatever OS fits, is built in real time and removed when not needed (saves money), and most security work sits in the cloud.
  • Monolithic vs microservices: a monolith is one executable (UI, login, business logic) installed locally and needing change control to update. With microservices, the client talks to an API gateway, which routes to the right service. Benefits: scalability (add copies of the busy service), resilience (losing one service does not kill the app), and tailored security per service (authentication service vs database-writing service).

Network infrastructure

  • Air gap: physical isolation, such as web servers in one rack and databases in another, or an MSP putting each customer on its own switch. It does not scale (100 customers = 100 switches), so VLANs give the same separation on shared switches. VLANs cannot talk to each other directly.
  • SDN planes: the data plane (forwarding, NAT, encryption, trunking), the control plane (routing tables, dynamic routing, session and address tables), and the management plane (SSH, SNMP, API configuration). Splitting these into software lets cloud builders add devices on demand. Example: load balancer to web servers A and B plus a database server, then click to insert a firewall between the internet and load balancer and another between web servers and database.

Other infrastructure

  • On-prem vs cloud: cloud security is centralized with no hardware or data center to staff, and the provider handles it. On-prem gives full control and local security but you pay for staff, equipment, purchase time and configuration. Attackers do not care where it is.
  • Centralized management: one console for consolidated alerts, log analysis and global patching, but it is a single point of failure, and needs more storage and CPU as the organization grows.
  • Virtualization: infrastructure, then hypervisor, then separate VMs each with a guest OS and apps. Inefficient when every guest is the same OS. Containers share one host OS and put only the app and dependencies in a container, managed by container software such as Docker. Containers are isolated from each other, easy to swap, and designed for one host OS (Windows containers vs Linux containers).
  • IoT: home (garage openers, video doorbells, smartwatches) and workplace (air quality, temperature, lighting). Makers are good at thermostats, not security, and one exploited device can expose the network.
  • SCADA / ICS: networks large machinery (manufacturing, power generation, refineries) from a central control room, and must be completely segmented from outside.
  • RTOS: Windows and Linux are non-deterministic; deterministic real-time systems (cars with anti-lock brakes, military, manufacturing) let one task take priority. They are self-contained and hard to access.
  • Embedded system: purpose-built hardware and software for one task (traffic lights, watches, medical monitors).
  • HA vs redundant: redundant means a spare exists (maybe in a closet needing to be racked and configured). High availability keeps running through a failure, for example a firewall pair in active/passive (failover) or active/active (both working, no visible failure). More HA means more cost (second firewall, network, power), so it is a business decision.

Infrastructure considerations

  • Availability is measured as uptime percent (for example 99.999%), and in security means available to the *right people*. Resilience measure: MTTR (mean time to repair). First find the root cause; hardware needs replacing, software needs a patch, redundant parts need replacing.
  • Cost includes install cost (varies by platform), maintenance (vendor or internal), replacement, plus accounting aspects: depreciation (capital expense), operational costs and tax implications.
  • Responsiveness: users notice delay; measure across a transaction's steps. Elasticity: expand and contract capacity with demand (quarter end, time of day). Building the largest version costs money, so start at the current load and scale, sometimes automatically. Extend security monitoring as it scales.
  • An application instance has many parts (web server, database, caching server, firewall). Orchestration automates building the whole stack on demand. Deployment still needs project planning: where, who, resources, budget, change control.
  • Risk transference: cybersecurity insurance (for example for ransomware) can cover outages, financial loss and legal costs. It does not prevent the attack.
  • Ease of recovery: reload an OS from media (about an hour) vs restore from an image backup (about 10 minutes) after malware. Plan the fastest recovery.
  • Patch availability: patch before production, test monthly patches, deploy fast. Inability to patch is common for embedded systems such as HVAC controls and time clocks with no connectivity; add a firewall in front as another layer.
  • Power: have a licensed electrician review usage; data centers differ from offices; use a UPS or generator for backup. Compute: the cloud "compute engine" does the processing and can scale across many processors.

Exam traps

  • You can transfer risk (insurance, outsourcing), but you can never transfer accountability for your data.
  • Air-gapped means no network connection at all; a segmented VLAN is not an air gap.
  • Containers share a kernel; VMs have their own. VMs are more isolated.
  • When a device cannot be patched, think segmentation and access control, not "patch harder".
  • SaaS leaves the customer the *least* security work, but never zero.
