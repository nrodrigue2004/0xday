~/cases/stuxnet

The first widely known cyberweapon built to cause physical damage. It crossed an air gap on a USB stick, used four zero-days and stolen certificates, and lied to the operators while it wrecked centrifuges.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

The story

In June 2010 a small Belarusian security firm, VirusBlokAda, was asked to look at an Iranian customer's computers that kept crashing and rebooting. They found a worm unlike anything before: it used several unpublished Windows flaws, its drivers were signed with valid stolen certificates, and it carried a payload aimed at one specific industrial system.

Analysis by Symantec and the German engineer Ralph Langner over the next months showed what it was for. It looked for Siemens S7 PLCs (industrial controllers) running a particular configuration, in a facility with a very specific arrangement of frequency converters, the kind that spin uranium-enrichment centrifuges. When it found them, it quietly changed their rotor speeds, wearing the machines out, while showing operators normal readings.

The target was almost certainly Iran's Natanz enrichment plant. Reporting by the New York Times and others attributed Stuxnet to a joint US and Israeli effort (codename Olympic Games). Neither government has officially confirmed it, so treat attribution as widely reported, not proven. Independent estimates suggest on the order of a thousand centrifuges were taken out of service.

Why it matters

It showed that malware can break physical things, that air gaps are not safe (a USB stick crossed it), and that a well-funded actor will chain several unknown flaws and stolen identities. It started industrial control system (ICS/OT) security as a mainstream field.

Timeline (approximate)

  • 2007 to 2009: earlier versions appear to have run, and a more aggressive one in 2009 to 2010.
  • Jun 2010: VirusBlokAda reports the worm; Microsoft begins working on the shortcut-file bug.
  • Jul 2010: the vulnerable-shortcut flaw is made public; Siemens and Microsoft respond.
  • Sep 2010: Langner publishes his analysis of the PLC payload, and Iranian officials acknowledge infections.
  • Feb 2011: Symantec's dossier is published.

02 mid // how it's actually used

How it worked (concept level)

Stuxnet was a long chain. No single trick is the story; the chaining is.

  1. Delivery by USB. A flaw in how Windows rendered the icon of a shortcut (.LNK) file ran code the moment you opened a folder on a USB drive (CVE-2010-2568). No click on the file was needed. This crossed the air gap.
  2. Spread inside the network. Used an older network-service flaw (MS08-067, the same one Conficker used), a print spooler flaw (CVE-2010-2729), and shared folders. It also used the default password that Siemens software used to talk to its database (CVE-2010-2772).
  3. Gain SYSTEM. Two local privilege-escalation zero-days (in the keyboard layout code and in Task Scheduler) gave full control.
  4. Hide. A rootkit driver, signed with certificates stolen from the Taiwanese chipmakers Realtek and JMicron, so Windows loaded it without complaint.
  5. Find the target. On machines with Siemens Step 7 engineering software, it replaced a library (s7otbxdx.dll) that sits between Step 7 and the PLC. Now it could see, and change, everything the engineer sent to the PLC.
  6. Sabotage with patience. It checked that the PLC matched the intended target. It then waited, recorded normal sensor data, changed the speeds at intervals (reports describe both speeding up and slowing down), and replayed the recorded good data to the operators' screens during the attack.

The logic as pseudo-code (a description, not working code)

on_usb_insert:
    if windows_shortcut_flaw_present: run_loader()         # CVE-2010-2568
run_loader:
    install_signed_rootkit()
    spread(network_flaws, shared_folders, usb)
    if step7_installed:
        hook(s7otbxdx.dll)
        if plc_matches(target_fingerprint):
            record(normal_sensor_values)
            wait(weeks)
            modify(rotor_speed_commands, sometimes)
            while attacking: show_operators(recorded_values)   # replay
        else:
            do_nothing()                                  # stay quiet elsewhere

This is a paraphrase of the structure documented by Symantec, not their code and not malware. The point is the shape: a gate that only fires on the right target, and a lie to the monitoring.

Defensive lessons

  • Air gap is a speed bump, not a wall. Treat removable media as hostile; scan and restrict USB.
  • Sensors can lie when the controller is compromised. Cross-check with independent measurements, like vibration sensors on the shaft.
  • Code signing proves origin, not intent. Protect signing keys in hardware, and watch for unusual driver loads.
  • Patch the boring stuff, and change default passwords on industrial software.

03 complex // what the pros do

Why it was so unusual

  • Four zero-days in one piece of malware (a typical campaign uses zero or one). Zero-days are expensive. Spending four on one target says a lot about the actor's budget.
  • A specificity gate. It spread widely (some infected machines were outside Iran) but did damage only when it found one narrow configuration. This reduced the chance of detection and collateral damage, but it did not prevent either.
  • The payload was in the PLC code, written in an industrial language (STL), a place almost no antivirus looked.

Detection and why it took a year

Stuxnet was found because a bug in the malware crashed machines, not because defenders saw it. Typical antivirus relied on known samples. Detection ideas that would have worked: unusual DLL replacement in the Step 7 directory, unsigned or oddly signed drivers loaded from a USB path, new .LNK files on removable media, network traffic from the engineering workstation to the PLC outside change windows, and process data that disagrees with an independent measurement.

Descendants

Duqu (2011) shared code and stole data; Flame (2012) was a large espionage tool; Industroyer (2016) and Triton (2017) attacked Ukrainian power and a Saudi petrochemical safety system, respectively. They moved from "destroy equipment quietly" to "cut the power" to "disable safety systems".

OT security basics (what to do now)

  1. Segment IT from OT with a controlled boundary (the Purdue model).
  2. Inventory every controller and engineering workstation.
  3. Allow-list applications on engineering stations.
  4. Monitor protocols such as Modbus and S7comm for unexpected writes.
  5. Safety systems independent of control systems, as a physical backstop.
