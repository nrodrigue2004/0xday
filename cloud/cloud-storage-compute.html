Object storage holds most of the world's cloud data and most of its leaks. Learn buckets and blobs, the compute options from VM to function, and the settings that decide whether strangers can read your files.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Storage

  • Object storage: files (objects) in containers called buckets (AWS S3) or containers inside storage accounts (Azure Blob). Cheap, huge, reached over HTTPS. Websites, backups, logs and data lakes live here.
  • Block storage: a virtual disk for a VM (EBS, Azure Managed Disks).
  • File storage: a shared network drive (EFS / FSx, Azure Files).

Compute

  • Virtual machine: a whole server you manage (EC2, Azure VM).
  • Containers: packaged apps (ECS/EKS/Fargate, AKS/Container Apps).
  • Serverless functions: run code on events, pay per run (Lambda, Azure Functions). No server to patch.

The classic leak: a storage bucket set to public that holds something private. Cloud storage is private by default; people open it for convenience and forget. Block public access by default, and make exceptions deliberately.

02 mid // how it's actually used

Who can read a bucket

Access comes from several places that combine: IAM policies on identities, a bucket policy on the resource, an ACL (older, avoid), and the account/bucket-level Block Public Access switch, which overrides the rest. A policy with "Principal": "*" and s3:GetObject makes objects world-readable. In Azure, check the storage account's "allow blob public access", the container access level, and any SAS token (a signed URL that grants time-limited access; treat as a password).

Protecting data

  • Encryption at rest (on by default almost everywhere; know who holds the key: provider-managed, or customer-managed in KMS / Key Vault) and in transit (TLS).
  • Versioning and object lock protect against deletion and ransomware.
  • Lifecycle rules move old data to cheaper tiers or delete it, which also limits breach blast radius.
  • Access logs record who read what.
  • Classify data first: public website assets can be public, invoices and backups cannot.

Compute choices, in one line each

VM: full control, you patch. Container: portable, share a kernel, scan images. Function: smallest attack surface, watch the role it runs as and its event inputs. Best practices: no credentials baked into images, use instance roles/managed identities, patch or rebuild from a fresh image, and turn off what is not needed.

Costs to remember

Stopped VMs still bill for their disks. Unattached volumes, snapshots, load balancers and public IPs bill until deleted. Data egress bills per GB.

03 complex // what the pros do

Storage attack paths

  • Anonymous listing and reading of public buckets, found by guessing names (company-backups, company-dev). Enumeration tools exist for authorized testing.
  • Over-broad SAS tokens or pre-signed URLs with long expiry, shared in tickets or chat.
  • A compromised role with s3:* copying data out; look for unusual GetObject volume in logs.
  • Bucket takeover / dangling DNS: a CNAME pointing at a deleted bucket or site that someone else can re-create.
  • Ransomware that deletes or re-encrypts objects with its own key; defended by versioning, MFA delete and offline copies.

Compute attack paths

  • Exposed management ports and weak passwords on VMs.
  • SSRF reaching the instance metadata service for role credentials; enforce IMDSv2 (AWS) and restrict identity endpoints.
  • Vulnerable container images or exposed Kubernetes dashboards and API servers.
  • Over-privileged function roles: the function is small, but its role is the prize.
  • Cryptomining on stolen credentials: the signature is a huge bill and instances in regions you never use.

Controls that scale

Account-wide Block Public Access, policy-as-code checks in CI (reject public buckets before deploy), CSPM scanning (Security Hub, Defender for Cloud), GuardDuty / Defender findings, tagging so every resource has an owner, and data discovery (Macie, Purview) to find personal data in the wrong place.

Shared responsibility check

For S3/Blob the provider guarantees the service is durable and patched. Whether the bucket is public, encrypted with the right key, logged, and versioned is entirely you.
