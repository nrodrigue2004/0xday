A cloud network is software-defined: virtual networks, subnets, route tables and stateful firewalls you create with API calls. Reachability needs several things to line up, and most mistakes are one of them lining up by accident.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Your servers live in a virtual network: a VPC (virtual private cloud) in AWS, a VNet (virtual network) in Azure. You choose a private address range (for example 10.0.0.0/16) and carve it into subnets.

  • Public subnet: has a route to an internet gateway, so resources with a public IP can be reached from the internet.
  • Private subnet: no direct route in from the internet. Outbound traffic goes through a NAT gateway.
  • Firewall rules: security groups (AWS) and network security groups, NSGs (Azure) allow or deny traffic by port, protocol and source.

A server is reachable from the internet only if all are true: it has a public IP, its subnet routes to the internet gateway, and a firewall rule allows the port from the source. Knock out any one and it is not exposed. Open 0.0.0.0/0 on SSH or RDP and you invite the whole internet to guess passwords.

Safe default: nothing public except what has to be (a load balancer or web front end). Databases and admin ports stay private.

Rules of thumb

  • Stateful means return traffic is allowed automatically. A stateless NACL needs rules both ways.
  • Security group rules can name another security group as the source ("allow from the web tier"), which is better than IP ranges inside an app.
  • Management access: no public SSH/RDP. Use a bastion, a VPN, AWS Systems Manager Session Manager or Azure Bastion.
  • A WAF in front of web apps filters HTTP attacks. DDoS protection is a separate service (AWS Shield, Azure DDoS Protection).
  • Check the CIDR: 203.0.113.0/24 is 256 addresses (an office), 0.0.0.0/0 is everyone.

03 complex // what the pros do

Segmentation patterns

Three-tier layout: public web tier, private app tier, private data tier, each with its own subnet and security group that only accepts the previous tier. Add a separate management subnet and separate accounts/subscriptions for prod and dev; the account boundary is the strongest isolation in the cloud.

Egress is a security control too

Attackers need outbound paths for command and control and exfiltration. Restrict egress with route design, proxy/firewall appliances (AWS Network Firewall, Azure Firewall), and DNS filtering, and log it. A NAT gateway that allows everything outbound is a quiet hole.

Private access to platform services

By default, calls to S3 or Storage go over the public endpoint. VPC endpoints and Private Endpoints keep that traffic on the provider's network and let you block public access to the service entirely. Pair this with bucket policies that only accept requests from your endpoint.

Visibility

  • AWS: VPC Flow Logs, Traffic Mirroring, GuardDuty. Azure: NSG flow logs, Network Watcher, Defender for Cloud.
  • Flow logs show allowed and rejected connections (source, destination, port, bytes) but not payloads. They are the first stop for "did anything talk to that host".

Reachability checklist for incident work

  1. Public IP or load balancer in front? 2. Subnet route table to an internet gateway? 3. Network ACL / NSG at the subnet? 4. Security group / NSG at the instance? 5. Host firewall and the service actually listening? 6. Any WAF or identity in front? A finding is "exposed" only when you can walk the whole path.
