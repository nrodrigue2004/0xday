MAL300 Reverse engineering and malware (extra labs)

Static analysis reads the sample; dynamic analysis runs it in a disposable VM and records what it touches. Learn the setup, the tools (Procmon, Wireshark, FakeNet, strace) and how to read a behavior log to find the dropped file, the persistence and the callback.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Static analysis looks at a file without running it (strings, imports, disassembly). It is safe and it misses what is hidden or encrypted. Dynamic analysis runs the sample in a controlled machine and records what it does: files it creates, registry keys it changes, processes it starts, network traffic it generates. Malware cannot hide behavior it has to perform.

The question you are trying to answer is always the same four things:

  1. What does it drop? Files written (often a copy of itself or a second stage)
  2. How does it persist? Run keys, scheduled tasks, services, startup folder
  3. Who does it talk to? DNS names, IP addresses, ports, URLs
  4. What does it change or steal? Documents, browser data, security settings

Never run a sample on your real computer. Use a throwaway VM with a snapshot, no shared folders, no clipboard sharing, and a network that goes nowhere or to a fake internet. Revert to the snapshot after every run.

Before running, snapshot. After running, diff: what is different from the clean snapshot is the malware's footprint.

02 mid // how it's actually used

The lab

  • A Windows analysis VM (snapshot taken) with Sysinternals Procmon, Process Explorer, Autoruns, Regshot and Wireshark
  • A second VM or the host running fake internet services: INetSim (Linux) or FakeNet-NG answers DNS, HTTP, SMTP and others with canned data, so the sample "connects" and you see what it asks for
  • The network set host-only or internal. No route to the real internet or your home network. Read the homelab segmentation notes for the same idea
  • Know the anti-VM tricks: a sample may check for VM artifacts and exit. Patching those checks is a post on the site

Reading Procmon

Procmon logs every file, registry, process and network event. Raw it is millions of lines; filter it:

  • Include Process Name is sample.exe, then add its child processes (follow the tree in Process Tree)
  • Exclude noise: Result is SUCCESS is too broad, but excluding Path contains \Windows\Prefetch and well-known reads helps
  • Interesting operations: WriteFile, CreateFile (with Create disposition), RegSetValue, Process Create, TCP Connect

Network side

Run Wireshark on the analysis network. Look for DNS names, the User-Agent, URL paths, the beacon interval (steady spacing is a tell) and any binary body. The names and IPs go into your indicators of compromise (IOC) list: hashes, file paths, registry keys, domains, mutex names.

03 complex // what the pros do

Behavior vs. evasion

Samples try to avoid analysis: sleep for hours (patch Sleep or fast-forward the VM clock), check for a debugger (IsDebuggerPresent), look for low RAM, few CPU cores, VM MAC prefixes or analysis tool processes, or wait for user activity. When the sample does nothing, that is a result too: find the check in disassembly and see which condition it needs.

Debugging dynamically

Besides logging, you can step the sample under a debugger (x64dbg on Windows, gdb on Linux), set breakpoints on interesting API calls (CreateFileW, RegSetValueExW, connect, VirtualAlloc, WriteProcessMemory) and read the arguments as they are passed. Breaking on VirtualAlloc followed by VirtualProtect is a classic way to catch a payload being unpacked into memory (see unpacking). Linux equivalents: strace -f -e trace=file,network,process ./sample, ltrace, and gdb with catch syscall.

Memory is truth

Even if a payload is encrypted on disk, it must be decrypted to run. Take a memory dump while it runs and carve the decrypted config or injected code out of it with Volatility (malfind, procdump, netscan). Process injection (CreateRemoteThread, process hollowing) is visible as executable memory regions with no backing file.

Writing it down

A good report names: sample hashes (MD5, SHA-256), file type and compile time, what it drops and where, persistence method, network IOCs with ports and protocol, the capabilities (keylogging, credential theft, ransomware, RAT commands), and the detection ideas (YARA rule, Sigma rule, network signature). The detection output is the reason the analysis exists. See detections and malware analysis.

Safety checklist

Snapshot before; host-only network; no shared folders or drag and drop; analysis tools not signed in to personal accounts; never upload a sample you were sent confidentially to a public sandbox; revert after. If a sample escapes a VM it is almost always because someone left a shared folder or a bridged network on.

04 hands-on // sandbox shell
