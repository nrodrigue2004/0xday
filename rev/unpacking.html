MAL300 Reverse engineering and malware (extra labs)

A packer wraps a program in a compressed or encrypted shell with a small stub that unpacks it at run time. Learn the signs of a packed file (entropy, odd sections, few imports) and how to find the original entry point with a tail jump.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

A packer compresses or encrypts an executable and adds a small program, the stub, in front. When you run the packed file, the stub unpacks the real program into memory and then jumps to it. Software makers use packers to shrink files. Malware authors use them to hide the real code from antivirus and from strings, so every sample of the same malware can look different on disk.

How you can tell a file is packed:

  • High entropy: compressed or encrypted data is close to random. Entropy is scored 0 to 8 per byte; normal code is about 5 to 6, and packed data is above 7
  • Strange section names such as UPX0, UPX1, .aspack, or random letters
  • A section that is big in memory but empty on disk: the place the stub will unpack into
  • Very few imports: often just LoadLibrary and GetProcAddress, because the real import table is rebuilt at run time
  • Almost no readable strings

The goal of unpacking is to get the original program back: either let it run until it has unpacked itself and dump it from memory, or work out how the stub does it.

02 mid // how it's actually used

The unpacking idea

  1. The OS loads the packed file and runs the stub at the entry point
  2. The stub allocates memory, decompresses or decrypts the real code into it, and fixes up imports
  3. The stub performs a tail jump to the original entry point (OEP), the first instruction of the real program
  4. From the OEP on, the real program runs

To unpack manually, you find the tail jump, break on it, and then dump the process memory to a file (and repair the import table). Everything before the OEP is stub.

Finding the tail jump

In a debugger the stub ends with something recognizable: a pushad/popad pair around the unpacker, followed by a jmp to an address far from the stub, in a different section than the code you are executing. A UPX-style stub finishes with something like popad; ... ; jmp 0x401a30. The address that leaves the stub's section is the OEP. Heuristics: a long run of 00 bytes after the jump (the unused end of the stub), or a jump whose target section has just been written to.

Tools

  • PE-bear / DIE (Detect It Easy) show sections, entropy and a packer guess
  • UPX itself unpacks files it packed: upx -d packed.exe (try it first; it fails on modified packers)
  • x64dbg with a break on VirtualProtect / the tail jump, then Scylla to dump and rebuild imports
  • Memory dump + Volatility when the sample is already running: dump the process after it has unpacked
  • Automatic sandboxes unpack common packers for you and give you the unpacked memory

Is packed malicious?

No. Many legitimate installers and commercial software are packed. Packing is a signal, not a verdict: combine it with imports, strings (what is left), signature, origin and behavior in dynamic analysis.

03 complex // what the pros do

Entropy, precisely

Shannon entropy of a block is -sum(p * log2 p) over byte frequencies. Text is about 4.5, x86 code 5.5 to 6.5, compressed or encrypted data 7.8 to 8. Compute it per section and per sliding window; the high-entropy region is the payload. A fully encrypted blob with a small low-entropy stub in front is the normal picture. Malware also appends junk or mixes in padding to lower the average entropy and slip past naive checks.

Packer families

  • Compressors (UPX, MPRESS): reversible with a tool, mostly harmless
  • Protectors (Themida, VMProtect, Enigma): obfuscate, virtualize and detect debuggers; hard
  • Crypters: custom encryption stub, usually per-customer, designed to defeat signatures
  • Custom malware packers: often a decryption loop (XOR, RC4, AES) plus manual import resolution; reading the loop shows the key
  • Multi-stage: the unpacked code is itself a loader that fetches a payload

API resolution and import rebuilding

A stub often avoids a normal import table. It walks the loaded modules in memory (via the process environment block, PEB) and finds functions by comparing hashes of names. That is why the imports list is nearly empty and why hash-resolving routines are a signature of malware; once unpacked, you rebuild the import table so a disassembler can label the calls.

Manual unpack, in outline

Run in a debugger, find the allocation and decrypt loop, break on the tail jump or on the first execution of the newly written region (a hardware breakpoint on execute), dump the region, fix the entry point to the OEP and the imports with Scylla, and open the result in Ghidra. Reading the unpacker teaches you the key and algorithm to unpack the next sample in the family without running it.

Defender view

Yara rules that match the unpacked strings only fire on memory, so scan memory as well as disk. Rules on the packer's stub catch every sample from that crypter, regardless of payload. Good detection combines both. Related: the wg2 RAT and the PE format.

list sections, entropy, imports
diec file.exe

upx -d file.exe
unpack a UPX-packed file
strings -n 8 file
readable strings (few = packed)
xxd file | head
look at the raw bytes
ent file
entropy of a file (0 to 8)

packer terms

stub
the small program that unpacks the real one
OEP
original entry point: where the real program starts
tail jump
the jump from the stub to the OEP
entropy
randomness per byte, 0 to 8; above 7 is packed or encrypted
UPX0 / UPX1
UPX section names
import rebuild
repairing the import table after dumping
PEB walk
stub finds API functions by looking at loaded modules
