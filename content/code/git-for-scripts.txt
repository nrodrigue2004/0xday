:: simple
A script you wrote once and never touched is fine. A script that runs from cron every night, that three people edit, is a liability unless you can answer: **what changed, who changed it, and how do I go back?** That is what git is for.

- A **commit** is a labelled snapshot of the whole folder
- `git log` is the list of snapshots, newest first
- `git diff` shows exactly which lines changed
- `git blame file` shows who last touched each line

```
$ git log --oneline
$ git blame rotate-logs.sh
```

> If a script deletes or sends things, change it on a **branch** and test it before it reaches the machine that runs it. The nightly job is not the test environment.

### What goes in the repo
- The scripts, a short `README` with how to run them, and sample input
- **Not** API keys, passwords, tokens, real logs or exports with customer data. Put those names in `.gitignore` before the first commit.
:: mid
### The loop for script work
```
git switch -c fix-rotation          # branch for the change
# edit, test with --dry-run
git add rotate-logs.sh
git commit -m "Keep 30 days of logs, not 0"
git switch main && git merge fix-rotation
```

Commit messages say **why**. "Speed up rotation" tells you nothing at 3 a.m.; "Delete logs older than 30 days only" tells you what the code was meant to do, which is the thing you need when it does not.

### Finding the commit that broke it
- `git log -p -- rotate-logs.sh` shows every change to one file, with the diff
- `git log -S"mtime +0" --oneline` finds the commits that added or removed that exact text
- `git blame -L 12,14 rotate-logs.sh` shows who changed lines 12 to 14, and in which commit
- `git show <sha>` prints one commit in full

```
$ git log -S"mtime +0" --oneline
$ git show 77f3a0e
```

### Secrets
Git remembers everything, including the key you deleted in the next commit. Use `.gitignore` for files that hold secrets, read them from environment variables in the script, and if one leaks, **rotate the key**. Rewriting history does not un-leak a key that was ever pushed.
:: complex
### Bisect: let git do the search
When you do not know which commit broke the behavior, `git bisect` binary-searches the history. Mark one good and one bad commit; git checks out the middle, you test, you say good or bad, and it halves the range. Fifty commits take about six steps. That is O(log n) applied to your own history, same as binary search on the [Big-O page](../bigo.html).

```
git bisect start
git bisect bad HEAD
git bisect good 1a05f9b
# test, then: git bisect good | git bisect bad
git bisect run ./test.sh        # fully automatic if the test exits 0/1
git bisect reset
```

### Guardrails
- **Pre-commit hook** (`.git/hooks/pre-commit`) runs a secret scanner such as gitleaks before the commit is created, so the key never enters history
- **Protected branch + review** on the shared repo: a second pair of eyes on anything that deletes or sends
- **Tags** (`git tag v1.4`) mark what is deployed, so `git diff v1.4 HEAD` is exactly what a release changes
- **Signed commits** prove who made a change on repositories where that matters
- **`git revert <sha>`** undoes a commit by adding a new one; safe on shared branches. `reset --hard` rewrites history and loses work, so keep it off anything pushed
- **Deploy from a tag, not from someone's laptop**: cron should run a checked-out tagged version

The same moves as the [git guide](../learn/git-github.html), pointed at your own automation.

### scripts in git
git switch -c name | branch for a risky change
git log -p -- file | every change to one file
git log -S"text" --oneline | commits that added or removed text
git blame -L 12,14 file | who changed lines 12-14
git show sha | one commit in full
git diff v1.4 HEAD | what a release changes
git bisect start | begin a binary search for a bad commit
git bisect run ./test.sh | automatic bisect with a test script
git revert sha | undo a commit safely on a shared branch
git tag v1.4 | mark a deployed version
git check-ignore -v file | why is this file ignored?
