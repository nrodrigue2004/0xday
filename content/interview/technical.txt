tagline: The data structures, algorithms and software engineering questions that come up in a coding screen, with the reasoning interviewers want to hear.
:: pitch
**How to open.** "I'll restate the problem, ask about input size and edge cases, give a simple solution first, then improve it, and I'll say the time and space cost as I go."
**What the interviewer is testing:** not whether you memorized a trick, but whether you can reason out loud, pick a fitting data structure, state the cost, and test your own code. Narrating is worth more than silence followed by a perfect answer.
:: prep
- Work through the [CS201 chapters](cs.html) and the [visualizer](cs/viz.html) until you can sketch sorting, BFS/DFS, Dijkstra, a hash table and a DP table from memory.
- Know the cost of every structure in the [~/bigo tables](bigo.html), and be able to say why.
- Practice small problems in the [dojo](dojo.html) with a timer and talk while you code.
- For software engineering questions, use the [CS240 chapters](cs.html): testing, patterns, CI/CD, agile and architecture. Prepare one real story for each (a bug you found with a test, a disagreement in code review, a deploy that went wrong).
- Always finish by testing your solution with a small example and one edge case (empty input, one item, duplicates).
:: q
- [e] What is the time complexity of looking up a key in a hash table, and why? => O(1) on average: the hash function turns the key into an index, so you jump straight to the bucket. Worst case is O(n) if everything collides, which is why good hash functions, resizing at a load factor and randomized hashing matter.
- [e] When would you choose a hash map over a sorted array? => When you need fast lookup, insert and delete by key and do not need order. A sorted array gives binary search in O(log n) and range queries, but inserts cost O(n). Mention that a balanced tree gives ordered keys with O(log n) for everything.
- [e] What is the difference between a stack and a queue, and where does each show up? => Stack: last in, first out (call stack, undo, DFS, matching brackets). Queue: first in, first out (job scheduling, BFS, buffers). Both are O(1) push/pop at their ends.
- [e] Explain unit tests versus integration tests. => A unit test checks one function or class in isolation and runs in milliseconds; an integration test checks several parts working together, such as code plus a real database. Have many unit tests, fewer integration tests, and a handful of end-to-end tests (the test pyramid).
- [n] Walk me through binary search and its common bug. => Keep lo and hi, check the middle, discard half each step: O(log n), array must be sorted. The bugs are off-by-one errors: keep the loop condition (`lo <= hi`) consistent with how you update the bounds (`mid + 1`, `mid - 1`), and avoid overflow in `(lo + hi) / 2` in fixed-width languages (`lo + (hi - lo) / 2`).
- [n] Compare quicksort and merge sort. => Both average O(n log n). Merge sort is always O(n log n) and stable but needs O(n) extra space. Quicksort is in place and cache friendly, usually faster in practice, but O(n²) worst case with bad pivots (fix with random or median-of-three pivots). Mention Timsort (Python, Java objects) and that built-in sorts are what you use in practice.
- [n] BFS or DFS: how do you choose? => BFS uses a queue and finds the shortest path in an unweighted graph, level by level. DFS uses a stack or recursion and suits exploring everything, detecting cycles, topological order and connected components. Both are O(V + E). For weighted shortest paths use Dijkstra.
- [n] Find two numbers in an array that add up to a target. => Brute force checks all pairs in O(n²). Better: one pass with a hash map from value to index; for each x look up `target - x`. O(n) time, O(n) space. If the array is sorted, two pointers works in O(1) extra space.
- [n] Detect a cycle in a linked list. => Floyd's tortoise and hare: one pointer moves one step, the other two; if they ever meet there is a cycle. O(n) time, O(1) space. A hash set of visited nodes also works in O(n) space.
- [n] What is dynamic programming and how do you recognize a DP problem? => Solve overlapping subproblems once and reuse the answers (memoization top-down or a table bottom-up). Signs: "number of ways", "min/max cost", choices at each step with optimal substructure. Define the state, the transition, the base case and the order; give the time as states times work per state.
- [n] How do you test a function that calls an external API or reads the clock? => Inject the dependency (pass the client or the clock in) and use a stub, fake or mock in tests. Test the boundary behavior, plus a small number of integration tests against a sandbox. Avoid mocking your own internals.
- [n] What is CI/CD and what happens between push and production? => Push triggers a pipeline: build, unit tests, security scans, package an artifact, deploy to staging, integration tests, then promote to production (manual approval for delivery, automatic for deployment). Failures stop the pipeline. Mention rollbacks, feature flags and canary releases.
- [n] Name SOLID principles and give one example. => Single responsibility, open/closed, Liskov substitution, interface segregation, dependency inversion. Pick one with a story: dependency inversion lets you pass a fake database into a service for tests; open/closed is adding a new pricing rule as a new strategy class instead of editing an if/else chain.
- [h] Design a rate limiter. => Clarify: per user or IP, limit, window. Token bucket or sliding window counter keyed by user in Redis with expiry, atomic increment. Return 429 with Retry-After. Discuss distributed consistency, clock skew, burst allowance and abuse of the identifying key. Complexity: O(1) per request.
- [h] Given a list of courses with prerequisites, can a student finish all of them? => Model it as a directed graph; the answer is yes exactly when there is no cycle. Use Kahn's algorithm (queue of zero in-degree nodes) or DFS with three colors. O(V + E). Return an order if asked (topological sort).
- [h] Explain the difference between a monolith and microservices and when you would choose each. => Monolith: one deployable, simple to build and test, good for small teams. Microservices: independent deploys and scaling, but you pay in network failures, versioned APIs, tracing and operations. Start with a modular monolith and extract a service when there is a clear reason (team boundaries, scaling needs).
- [h] A test passes on your machine but fails in CI sometimes. How do you debug it? => Treat it as a flaky test: look for order dependence, shared state, time, randomness, concurrency and environment differences. Reproduce by running it repeatedly with the CI seed, add logging, isolate it, and fix the cause rather than adding retries. Quarantining is a temporary measure with a ticket.
- [h] How would you secure a CI pipeline? => Least-privilege tokens, short-lived OIDC credentials, secrets never in the repo or logs, pin third-party actions to commit SHAs, treat fork PRs as untrusted, protect branches and require reviews, scan dependencies, secrets and images, sign artifacts and keep an SBOM.
