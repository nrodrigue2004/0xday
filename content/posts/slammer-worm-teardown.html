This is the companion to my wg2 RAT teardown. It's a 2003-era worm, an SQL Slammer / Sapphire style sample. For my reverse engineering course I made a fully commented disassembly and a stack-layout diagram. This post is the short version.

It's a good contrast with wg2. wg2 is a big C++ program with a command loop. Slammer is 376 bytes with no C2, no persistence and no commands. It does one thing, forever.

What it does, in one breath

A single UDP packet to SQL Server's resolution service (UDP 1434) overflows a stack buffer, redirects the return address to a JMP ESP gadget in sqlsort.dll, and lands in the worm body. The worm then resolves the few APIs it needs, opens a UDP socket, and sprays copies of itself at pseudo-random IPv4 addresses until the machine is turned off.

overflow 1434/udp -> RET to JMP ESP -> shellcode on stack
  -> build API names on the stack -> LoadLibraryA / GetProcAddress
  -> GetTickCount (seed) -> socket(UDP) -> sendto() in an endless loop

I'm describing behavior and structure for defenders and students. I left out the full packet bytes on purpose.

Getting control

The first byte of the packet selects the vulnerable code path in the SQL Server parser. A long run of 0x01 filler overruns the buffer, and the saved return address is replaced with 0x42B0C9DC, a JMP ESP inside sqlsort.dll. When the function returns, execution lands on ESP, which points at the worm. A short jmp hops over embedded data into a NOP sled.

The worm doesn't get "called". It's reached by corrupting a return, which is why the stack matters so much for this sample.

The stack is the data section

There's no data segment and no import table. First the worm carves out workspace by pushing 0x01010101 24 times (96 bytes) and sets EBP = ESP. Everything after that is an EBP-relative local variable. The filler value is chosen so the payload has no null bytes, which would truncate the overflow, and the worm even builds 0x04000000 with an XOR instead of writing the zeros.

mov  eax, 01010101h
xor  ecx, ecx
mov  cl, 18h          ; 24 iterations
L: push eax
   loop L             ; 96 bytes of workspace
xor  eax, 05010101h   ; -> 04000000h with no null bytes in the code
push eax
mov  ebp, esp

Stack layout

EBP-0x54  UDP socket handle
EBP-0x50  sockaddr_in (random IP + port 1434)
EBP-0x4C  PRNG seed / state  (starts from GetTickCount)
EBP-0x48..0x40  saved handles: kernel32, GetTickCount name ptr, ws2_32
EBP-0x3C  "sendto"
EBP-0x34  "socket"
EBP-0x2C  "kernel32.dll"
EBP-0x20  "GetTickCount"
EBP-0x10  "ws2_32.dll"

Strings built backwards

API names are pushed as little-endian dwords, last chunk first, so they read correctly in memory. Short endings use a 16-bit mov cx so the upper bytes stay zero and the string is null-terminated for free.

push ecx              ; NUL
push 6C6C642Eh        ; ".dll"
push 32336C65h        ; "el32"
push 6E72656Bh        ; "kern"  -> kernel32.dll

That's the main tell when you're analyzing it: a long run of push imm32 with printable ASCII constants means stack strings, and tools like strings will never see them.

Finding its APIs

With no imports, the worm borrows sqlsort.dll's own import table. It calls LoadLibraryA through a known IAT slot for kernel32.dll and ws2_32.dll, then calls GetProcAddress through another slot. Because that slot differs between builds, it checks that the target starts with the expected prologue bytes (55 8B EC 51) and falls back to a second address if not.

esi = [IAT: LoadLibraryA]     ; call [esi]
esi = [IAT: GetProcAddress?]  ; check first dword == 51EC8B55h
                              ; no match -> use the backup slot

It resolves GetTickCount and calls it. The return value isn't for timing, it's the seed for the target generator. Then it resolves socket, creates a UDP socket (AF_INET, SOCK_DGRAM, protocol 17) and resolves sendto, keeping the function pointer in ESI for the rest of its life.

Picking victims without a multiply

The target generator is a linear congruential generator, seed = seed * 214013 + increment. Instead of imul, the worm builds the multiplier from lea, shifts, an add and a sub, which keeps the encoding tiny and free of null bytes:

lea  ecx, [eax+eax*2]   ; 3x
lea  edx, [eax+ecx*4]   ; 13x
shl  edx, 4             ; 208x
add  edx, eax           ; 209x
shl  edx, 8             ; 53504x
sub  edx, eax           ; 53503x
lea  eax, [eax+edx*4]   ; 214013x   (0x343FD)
add  eax, ebx           ; + increment
mov  [ebp-4Ch], eax     ; new state, also the next target IP

I like this part because the whole generator is eight instructions and you can verify the constant by hand. The new state is stored back at EBP-0x4C and doubles as the destination address.

The spread loop

push 10h                 ; tolen = sizeof(sockaddr_in)
lea  eax, [ebp-50h]      ; to
push eax
xor  ecx, ecx
push ecx                 ; flags = 0
xor  cx, 0178h           ; len = 376
push ecx
lea  eax, [ebp+3]        ; buf = start of worm body
push eax
mov  eax, [ebp-54h]      ; socket
push eax
call esi                 ; sendto(s, buf, 376, 0, &to, 16)
jmp  short PRNG          ; never returns

Single datagram, no handshake, no reply expected. That's why it spread so fast: with UDP there's nothing to wait on, so the only limit is how quickly sendto can be called and how fast the uplink is.

wg2 vs. Slammer

language        C++                     hand-written asm shellcode
size            full PE32               376 bytes
transport       HTTP/HTTPS (TCP)        one UDP datagram
control         C2 loop, 11 commands    none
persistence     beacon loop             none (memory only)
goal            remote administration   replicate

Detection and defense notes

  • Network: a host sending a flood of identical ~376-byte UDP packets to port 1434 across wide address ranges is the whole signature. Flow-based detection (fan-out rate to one port) works even if the payload changes.
  • Exposure: the resolution service shouldn't be reachable from untrusted networks. Filtering 1434/udp at the edge stops this outright.
  • Memory-only: nothing touches disk, so file-based AV has nothing to scan. Patching the SQL Server flaw is the real fix.
  • Analysis tip: when a sample has no imports and a wall of push imm32 ASCII, decode the stack strings first. The rest of the logic falls out of those names.

What I took away

  • Drawing the stack diagram first made the disassembly readable. Without it, every [ebp-xx] is a mystery.
  • Tiny does not mean simple. Null-byte avoidance shaped almost every instruction choice.
  • Comparing it with wg2 showed me how different malware can be. One waits for orders. The other never stops to listen.
