tagline: SAST reads your code, DAST attacks your running app, and each finds things the other cannot. The hard skill is deciding which findings are real.
sheet: appsec
:: simple
Automated security testing comes in a few flavors:

- **SAST** (static application security testing): analyzes source code or bytecode without running it. Finds injection patterns, hard-coded secrets, unsafe functions. Fast, runs on every commit, but produces **false positives** and cannot see runtime configuration.
- **DAST** (dynamic): attacks a running application from outside, like an attacker would, and watches the responses. Finds misconfiguration, missing headers, reflected XSS. Needs a running environment and cannot point to the line of code.
- **IAST** (interactive): an agent inside the running app watches data flow during tests. More precise, but needs instrumentation.
- **SCA** (software composition analysis): scans your dependencies for known vulnerabilities (next chapter).
- **Manual code review and pentest**: still finds the logic and authorization flaws tools miss.

Tools you will meet: Semgrep, CodeQL, SonarQube, Bandit (Python), SpotBugs (Java) for SAST; OWASP ZAP and Burp Suite for DAST.
:: mid
### What each finds best
- SAST: SQL injection through string concatenation, `eval` of user input, weak crypto calls, secrets in code, dangerous deserialization.
- DAST: missing security headers, cookie flags, TLS config, reflected and stored XSS, open redirects, exposed admin pages, error leakage.
- Neither is good at: broken access control (user A reads user B's record), business logic abuse, race conditions. Those need tests written by a human, and review.

### Triage workflow
1. **Is it reachable?** Can untrusted input actually reach this line?
2. **Is it exploitable?** Is there sanitization or a framework protection in the path?
3. **What is the impact?** Data exposed, code run, or a harmless test file?
4. Mark it **true positive**, **false positive** (with a reason) or **accepted risk**, and ticket the fixes with an owner.

Suppress findings in code or config with a comment explaining why, so the next person does not redo the analysis.

### A Semgrep rule
```code
rules:
  - id: sql-string-concat
    languages: [python]
    message: SQL built by string formatting, use parameters
    severity: ERROR
    pattern: cursor.execute("..." + $X)
```
Custom rules turn a bug you just fixed into a check that stops it coming back.

### ZAP in CI
`zap-baseline.py -t https://staging.example.test` does a passive scan; `zap-full-scan.py` actively attacks. Run against a staging copy, never production, and with an agreed scope.
:: complex
### Putting it in the pipeline
A common setup: pre-commit hooks for secrets and linters; on pull request, SAST and SCA with results as review comments; on merge to staging, DAST; before release, a gate that fails on new **high** findings. Gate on **new** findings only, or the first scan blocks everything and the tool gets turned off.

### Reducing noise
Tune rule sets to your frameworks, baseline existing findings and track burn-down, and measure the false-positive rate per rule. Disable rules nobody acts on. A scanner with 4,000 open findings is a scanner nobody reads.

### Limits to remember
- A clean scan is not a secure app.
- Taint analysis loses track across services, reflection and templates.
- DAST coverage depends on crawling: authenticated areas and single-page apps need configured logins and API definitions (OpenAPI).
- Scanners can hurt: active scans send attack payloads and create data. Use test data and rate limits.

### Reporting
For each real finding: title, location, evidence, impact, reproduction steps, fix guidance and a reference (CWE ID, OWASP category). Developers fix what they can reproduce and understand.

nikto -h URL | quick web server checks
### terms
CWE | Common Weakness Enumeration, catalog of bug types (CWE-89 is SQL injection)
false positive | a finding that is not a real vulnerability
taint analysis | tracking untrusted input from source to dangerous sink
baseline | the set of existing findings you accept for now
