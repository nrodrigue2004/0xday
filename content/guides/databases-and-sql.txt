tagline: Databases are where the valuable data lives. Learn tables, keys, normalization, transactions and indexes, then run real SQLite in your browser to find the account whose balance was tampered with.
:: simple
A **relational database** stores data in **tables**: rows (records) and columns (fields). Each table has a **primary key** that uniquely identifies a row, and a **foreign key** in one table points at the primary key of another, which is how tables relate.

**SQL** is how you ask questions. The sandbox runs real **SQLite** (the first run downloads it once):

```
$ sqlite3 bank.db ".tables"
$ sqlite3 bank.db "SELECT * FROM accounts;"
```

The four basic operations are **CRUD**: Create (`INSERT`), Read (`SELECT`), Update (`UPDATE`), Delete (`DELETE`).

> Other databases (PostgreSQL, MySQL, SQL Server) use the same SQL with small differences. MongoDB and Redis are **NoSQL**: documents or key-value pairs instead of tables.

### Picking the right kind of database
**Relational** (PostgreSQL, MySQL, SQLite, SQL Server) stores structured data with relationships and strong consistency. **Document** (MongoDB) stores JSON-like objects, flexible. **Key-value** (Redis) is a fast cache. **Graph** (Neo4j) is for relationships. **Time-series** and **search** (Elasticsearch, which is the engine behind Security Onion) are for logs and metrics. Most apps start well with a relational database.

### Design in four steps
Identify the things (tables), give each a primary key, connect them with foreign keys, and avoid duplicating data. A table of orders should store `customer_id`, not the customer's name and address on every row.
:: mid
### Relationships and JOINs
One customer has many transactions: a **one-to-many** relationship. A `JOIN` combines tables on the key that links them, and `GROUP BY` + `SUM` / `COUNT` turns many rows into one per group:

```
$ sqlite3 bank.db "SELECT a.owner, COUNT(*) FROM accounts a JOIN txns t ON t.account_id = a.id GROUP BY a.owner;"
```

### Normalization
Store each fact **once**. If the owner's name is copied into every transaction row, changing it means updating hundreds of rows, and some will be missed. Normal forms (1NF, 2NF, 3NF) are rules for splitting tables so data can't contradict itself.

### Transactions and ACID
A **transaction** groups changes so they all happen or none do (moving money: subtract here, add there). **ACID** = Atomic, Consistent, Isolated, Durable.

### Normal forms in plain words
1NF: one value per cell, no repeating groups. 2NF: every column depends on the whole key. 3NF: columns depend on the key and nothing else. If changing one fact means editing many rows, you need to split a table. Denormalize on purpose only for read performance, and document why.

### Backups and recovery
Take regular full backups plus transaction log or point-in-time recovery, store copies off the host, encrypt them, and test restores. Know the two numbers: **RPO** (how much data you can afford to lose) and **RTO** (how long you can be down).

### Common tasks
Export with `pg_dump` or `mysqldump`, import with `psql < file.sql`, check running queries with `pg_stat_activity` or `SHOW PROCESSLIST`, and find slow ones with the slow query log and `EXPLAIN`.
:: complex
### Integrity as a security control
The **I** in the CIA triad. Databases protect it with constraints (`NOT NULL`, `UNIQUE`, `CHECK (balance >= 0)`, foreign keys), transactions, and **audit trails**. A classic check: does a stored total match the sum of the records it's supposed to summarize? If not, someone changed one without the other.

```
$ sqlite3 bank.db "SELECT account_id, SUM(amount) FROM txns GROUP BY account_id;"
```

### Indexes and performance
An **index** is a sorted lookup structure (usually a B-tree) on a column, turning a full table scan into a quick search. It speeds up reads and slows down writes. `EXPLAIN QUERY PLAN` shows whether a query uses one.

### Database security
- **SQL injection**: always parameterized queries (`?` placeholders), never string concatenation
- **Least privilege**: the web app's DB user can't `DROP TABLE` or read the HR schema
- **Encryption** at rest (TDE) and in transit (TLS), **tokenization** or masking for card numbers
- **Backups** tested by actually restoring them, and database activity monitoring

### Securing a database server
Do not expose it to the internet; bind to localhost or a private network and firewall it. Remove default accounts and sample databases. Separate accounts for the application (limited rights), migrations (schema changes) and admins. Enable TLS, encrypt at rest, turn on audit logging, patch regularly, and never store passwords in plain text (hash with Argon2id or bcrypt). Mask or encrypt sensitive columns, and restrict who can run ad hoc queries on production.

### Transactions and isolation
ACID: Atomic (all or nothing), Consistent (rules hold), Isolated (concurrent work does not interfere), Durable (committed means saved). Isolation levels trade speed for safety; the anomalies to know are dirty reads, non-repeatable reads and phantom reads. Race conditions in application code (check balance, then withdraw) need a transaction with locking or a constraint.

### design
Primary key | uniquely identifies a row
Foreign key | column that references another table's key
Index | structure that speeds lookups at a cost to writes
Constraint | rule the database enforces (NOT NULL, UNIQUE, CHECK)
Normalization | removing duplicated data across tables
View | saved query that behaves like a table
### acid
Atomicity | all steps happen or none do
Consistency | data stays valid under the rules
Isolation | simultaneous transactions do not corrupt each other
Durability | committed data survives a crash
