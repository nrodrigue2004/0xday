tagline: Hardening means removing everything an attacker could use before they show up. Learn baselines, least privilege and the usual misconfigurations on Linux and Windows, then audit a server and find its backdoor account.
:: simple
A fresh install is built to *work*, not to be *safe*: default passwords, extra services, broad permissions. **Hardening** is shrinking the **attack surface**:
- remove or disable what you don't need (services, software, ports, accounts)
- change every default password, and enforce strong ones
- patch, and keep patching
- give every user and service only the access it needs (**least privilege**)
- turn on logging and a host firewall

Start by seeing what the box exposes. Which services are listening?

```
$ cat ~/audit/listening.txt
```

> The **CIS Benchmarks** and DISA STIGs are free, detailed hardening checklists for almost every OS and app. Hardening is mostly working through one.

### The hardening loop
1. **Inventory**: what is on this machine (software, services, ports, accounts)?
2. **Baseline**: what should it look like? Use a published benchmark (CIS Benchmarks, DISA STIGs, Microsoft security baselines) instead of inventing your own.
3. **Apply**: change settings, ideally through automation (Group Policy, Ansible, scripts) so every machine matches.
4. **Verify**: scan with a tool (Lynis, OpenSCAP, CIS-CAT, Microsoft Security Compliance Toolkit) and read what failed.
5. **Repeat**: configurations drift, and new patches arrive every month.

Hardening is a trade: every control costs some convenience. Document exceptions rather than silently skipping them.
:: mid
### Linux: accounts and SSH
`/etc/passwd` has one line per account: `name:x:UID:GID:comment:home:shell`. Only `root` should have UID **0**. Service accounts should have a `nologin` shell. Pull the fields you care about with `awk -F:`:

```
$ awk -F: '{print $1, $3, $7}' ~/audit/etc/passwd
```

SSH is the front door. Check the settings that matter: no root login, no passwords (keys only), no empty passwords:

```
$ grep -E "^(PermitRootLogin|PasswordAuthentication|PermitEmptyPasswords)" ~/audit/etc/ssh/sshd_config
```

### Windows: the same ideas, different tools
Group Policy enforces baselines across a domain. Typical wins: disable SMBv1 and LLMNR, enforce account lockout, turn on Windows Defender and the firewall, deploy LAPS (a unique local admin password per machine), and remove users from the local Administrators group.

```

```

### Linux checklist
- Patches: `apt update && apt upgrade`, turn on unattended security updates.
- Accounts: no empty passwords (`awk -F: '($2=="")' /etc/shadow`), only root has UID 0, lock unused accounts, use sudo with named users.
- SSH: `PermitRootLogin no`, `PasswordAuthentication no` once keys work, `AllowUsers` list, maybe a non-default port to cut log noise (not a real defense).
- Services: `systemctl list-unit-files --state=enabled`, disable what you do not use. `ss -tulpn` should show only what you expect.
- Firewall: default deny incoming with ufw or nftables, open only needed ports.
- Files: world-writable files and SUID binaries reviewed, `/tmp` mounted `noexec,nosuid` where possible.
- Logging: auditd or journald with remote forwarding, time sync on.
- Extras: `fail2ban`, AppArmor or SELinux left on, kernel parameters (`sysctl`) such as disabling IP forwarding when not routing.

### Windows checklist
- Patches through Windows Update or WSUS, third-party software included.
- Local admin: rename or disable the built-in Administrator, use **LAPS** so every machine has a unique admin password.
- Accounts: standard users for daily work, strong password and lockout policy, MFA for admins.
- Defender on, with tamper protection, ASR rules and cloud protection; BitLocker on laptops.
- Firewall on for all profiles, inbound default block.
- Remove SMBv1, disable LLMNR/NetBIOS if not needed, restrict RDP to a VPN or gateway with NLA.
- PowerShell: script block logging and transcription, constrained language mode where practical.
- Audit policy and Sysmon forward to the SIEM.

### Privilege escalation is a hardening checklist in reverse
Attackers who land as a normal user look for exactly the misconfigurations hardening removes:
- **SUID binaries** that let anyone run something as root (`find / -perm -4000`)
- **sudo rules** that are too broad (`(ALL) NOPASSWD: ALL`, or sudo on editors and interpreters that can spawn a shell)
- **world-writable** files run by root (cron scripts, services)
- extra **UID 0** accounts, weak file permissions on `/etc/shadow`

```
$ cat ~/audit/suid.txt
$ grep -v "^#" ~/audit/etc/sudoers | grep -v "^$"
```

GTFOBins lists how almost every common binary can be abused when it's SUID or allowed via sudo. If `find`, `vim` or `python3` is on that list, it's a root shell.

### Baselines and drift
Harden once, then keep it that way: define a baseline (CIS level 1), apply it with automation (Ansible, GPO, Intune), and scan for **drift** regularly (OpenSCAP, Lynis, Microsoft Security Compliance Toolkit).

### Benchmarks, scoring and exceptions
CIS Benchmarks come in Level 1 (sensible, little breakage) and Level 2 (stricter, may affect function). Apply Level 1 widely, Level 2 to sensitive systems after testing. Keep a register of exceptions with owner, reason and review date. A finding you decided to accept is fine, an undocumented one is a gap.

### Common misconfigurations attackers look for
World-writable service paths, unquoted service paths with spaces, scheduled tasks running as SYSTEM with editable scripts, `NOPASSWD` entries in sudoers, SUID copies of `find`, `vim` or `python`, readable backups and `.bash_history`, passwords in scripts, shares open to Everyone, and old protocols such as telnet, FTP and SMBv1. Compare with GTFOBins (Linux) and LOLBAS (Windows) to see why each is dangerous.

### Immutable and automated
The strongest posture is to stop hand-editing servers. Build from a template or an Ansible role, rebuild when something drifts, keep the config in git, and treat any manual change as an incident to be explained.

:: hint
On Linux, what makes an account root is not its name but its UID. Which field in /etc/passwd is the UID?
:: hint
`awk -F: '$3 == 0' ~/audit/etc/passwd`
:: solution
`awk -F: '$3 == 0 {print $1}' ~/audit/etc/passwd` prints `root` and **sysupdate**. `sysupdate` has UID 0 (so it is root to the kernel), a real shell `/bin/bash` and a home in `/var/lib/.sysupdate`, and the sudoers file also gives it `NOPASSWD: ALL`. Fix: delete the account, check `/etc/shadow` and `authorized_keys` for its credentials, and investigate how it got there. While you're in there: `PermitRootLogin yes` and `PasswordAuthentication yes` in sshd_config should both be `no`, and `/usr/bin/find` shouldn't be SUID.
