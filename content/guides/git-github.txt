tagline: Git remembers everything, including the secret you deleted. Learn commits, branches and pull requests, then dig a leaked API key out of a repository's history.
:: simple
**Git** tracks changes to files over time. Each **commit** is a snapshot with a message, an author and a unique ID (a SHA hash). You can see who changed what, when, and go back to any version. **GitHub** hosts Git repositories online and adds pull requests, issues and CI.

The everyday loop:

```
$ git status
$ git log --oneline
```

- `git add file` stages a change, `git commit -m "message"` saves the snapshot
- `git push` sends commits to GitHub, `git pull` gets others' commits
- A **branch** is a separate line of work; merge it back when it's done

> Write commit messages that say *why*, not just *what*. Future you will read them during an outage.
:: mid
### Branches and pull requests
Teams don't commit straight to `main`. You make a branch, push it, and open a **pull request** (PR): a request to merge, where others review the diff and CI runs the tests. **Branch protection** can require reviews and passing checks before merging.

```
$ git branch -a
$ git show --stat a41c9e2
```

### Seeing changes
`git diff` shows uncommitted changes; `git show <sha>` shows exactly what one commit changed; `git log -p file` shows a file's whole history, change by change.
:: complex
### Secrets in history
Deleting a secret in a new commit **doesn't remove it**: the old commit still contains it, and anyone who clones the repo gets the whole history. Bots scan public GitHub for leaked keys within minutes of a push.

```
$ git log --oneline --all -- config/settings.py
$ git log -p --all -S "API_KEY" --oneline
```

`-S "text"` (the "pickaxe") finds commits that added or removed that text.

### If you leak a secret
1. **Rotate it immediately**. Assume it's compromised the moment it was pushed
2. Then clean history if needed (`git filter-repo`, BFG) and force-push, knowing forks and clones may still have it
3. Prevent it: `.gitignore` for `.env` files, pre-commit secret scanning (gitleaks), GitHub push protection, and secrets in a vault or CI secrets, never in code

### Supply chain
Signed commits, protected branches, required reviews and pinned dependency versions all exist because a malicious commit or package can reach production through Git.

:: hint
`git log --oneline` shows a commit about removing a key. The key itself is in the commit *before* that.
:: hint
`git log -p --all -S "AKIA" --oneline` finds commits that added or removed text containing AKIA.
:: solution
`git log --oneline` shows `b7d21f0 remove hardcoded creds` right after `9c3e11a add S3 upload for reports`. `git show 9c3e11a` (or the pickaxe search for `AKIA`) shows the added line `AWS_ACCESS_KEY_ID = "AKIAQX7EXAMPLE4CF2DL"` plus its secret key. Removing it later didn't help: it's in history and was pushed to GitHub. The key ID is **AKIAQX7EXAMPLE4CF2DL**. Response: deactivate and rotate the key in IAM now, check CloudTrail for any use since the push, then scrub history and turn on push protection.
