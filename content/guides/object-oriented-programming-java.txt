**Object-oriented programming** (OOP) models a program as **objects**: things that have data (**fields**) and behavior (**methods**). A **class** is the blueprint, an object is one thing built from it:

`class User { String name; boolean isAdmin() { ... } }` then `User u = new User("riley");`

The four pillars:
- **Encapsulation**: keep fields `private` and let the class control how they change
- **Inheritance**: `class Admin extends User` reuses and extends a class
- **Polymorphism**: one call, `shape.area()`, does the right thing for a Circle or a Square
- **Abstraction**: expose *what* an object does, hide *how*

### The four ideas
- **Encapsulation**: keep data private and expose behavior. Callers cannot put an object into an invalid state.
- **Abstraction**: show what something does, hide how. An interface is a promise.
- **Inheritance**: a class reuses and extends another (`class Admin extends User`).
- **Polymorphism**: code written against the parent works with any child (`User u = new Admin();` and `u.canDelete()` runs the Admin version).

A **class** is a blueprint, an **object** is one instance built from it with `new`. **Fields** hold state, **methods** hold behavior, a **constructor** sets the object up.
:: mid
### Encapsulation is a security boundary
If a class keeps `roles` private, the only way to change them should be through methods that check the rules (`grantRole()` that requires an admin). That only holds if the class never hands its internals to outsiders. Returning a **mutable** internal object (a `List`, an array, a `Date`) from a getter gives the caller a live handle to your private state.

### Interfaces and abstract classes
An **interface** is a contract (`interface Authenticator { boolean verify(String user, char[] pw); }`) that several classes can implement: LDAP, local, SSO. Code depends on the interface, so you can swap implementations or mock them in tests.

### Composition over inheritance
Deep inheritance trees get fragile. Often it's cleaner for a class to *have* a helper object than to *be* a subclass.

### A small worked example
```
public class Account {
    private final String id;
    private long cents;
    public Account(String id, long cents) { this.id = id; this.cents = cents; }
    public void withdraw(long amount) {
        if (amount <= 0 || amount > cents) throw new IllegalArgumentException("bad amount");
        cents -= amount;
    }
    public long balance() { return cents; }
}
```
There is no setter for `cents`, so every change goes through a method that enforces the rules. That one design choice prevents a large class of bugs and security flaws.

### static, final and visibility
`private` (this class), package-private (default, same package), `protected` (subclasses too), `public` (everyone). `static` belongs to the class, not an object. `final` fields cannot be reassigned, `final` classes cannot be extended, `final` methods cannot be overridden. Default to the narrowest visibility that works.

### Overriding and overloading
Overriding replaces a parent method in a child (use `@Override`, the compiler then catches typos). Overloading is several methods with the same name and different parameters. `toString`, `equals` and `hashCode` are the methods you override most; if you override `equals`, override `hashCode` too.
:: complex
### Defensive copies and immutability
- Return `List.copyOf(roles)` or `Collections.unmodifiableList(roles)` instead of `roles`
- Copy mutable arguments in constructors too, or the caller keeps a reference
- Prefer **immutable** classes (`final` fields, no setters, Java `record`s): they're thread-safe and can't be tampered with after validation
- Make security-sensitive classes `final` so a subclass can't override `isAdmin()`

### SOLID, briefly
**S**ingle responsibility, **O**pen/closed, **L**iskov substitution, **I**nterface segregation, **D**ependency inversion. Each one makes code easier to test, and testable code is code whose security checks you can actually prove work.

### Design principles you can recite
SOLID: single responsibility, open for extension but closed for modification, Liskov substitution (a child must work anywhere its parent does), interface segregation (many small interfaces), dependency inversion (depend on interfaces, not concrete classes). Prefer composition (an object has another object) over inheritance for reuse.

### Patterns you will run into
**Factory** (create objects without naming the class), **Builder** (step-by-step construction of complex objects), **Singleton** (one instance, often overused), **Strategy** (swap an algorithm), **Observer** (notify listeners), **Decorator** (wrap to add behavior). Knowing the names makes code reviews quicker.

### Security-minded OOP
Make classes immutable when you can, copy mutable inputs and outputs (see defensive copies), validate in constructors, do not leak internals through getters that return live collections, and make classes `final` unless designed for inheritance, because subclasses can break your invariants.

:: solution
`getRoles()` returns `roles` itself, the private `ArrayList`, not a copy. So `r` in `BadgePlugin.decorate()` and `u.roles` are **the same object** (the trace shows `same_object=true`). When the plugin adds `"ADMIN"` to what it thinks is a display list, it writes straight into the user's private roles, and `isAdmin()` returns true. The leaky method is **getRoles**. Fix: `return List.copyOf(roles);` (read-only copy), and only change roles through a method that checks the caller's authority.

import java.util.*;

public class User {
    private final String name;
    private final List<String> roles = new ArrayList<>();

    public User(String name) { this.name = name; roles.add("STUDENT"); }

    public List<String> getRoles() {
        return roles;
    }

    public boolean isAdmin() { return roles.contains("ADMIN"); }
}

class BadgePlugin {   // third-party plugin that draws role badges
    static void decorate(User u) {
        List<String> r = u.getRoles();
        r.add("ADMIN");                 // "preview the admin badge"
        System.out.println("badges: " + r);
    }
    public static void main(String[] args) {
        User u = new User("riley");
        decorate(u);
        System.out.println("admin? " + u.isAdmin());
    }
}
