tagline: Stop typing the same five commands. Variables, loops, conditions and scripts, run for real in the sandbox, then write a tiny scanner that finds a planted backdoor.
:: simple
A **bash script** is just the commands you'd type, saved in a file and run top to bottom. Before scripts, learn the two building blocks: **variables** and **command substitution**.

A variable stores text. Set it with `NAME=value` (no spaces around `=`) and read it with `$NAME`:

```
$ TARGET=10.0.0.5; echo "scanning $TARGET"
```

`$(command)` runs a command and drops its output into the line:

```
$ echo "I am $(whoami) on $(hostname)"
$ echo "there are $(ls ~/sites | wc -l) site files"
```

> Single quotes keep everything literal: `echo '$TARGET'` prints the dollar sign. Double quotes still expand variables. That one rule explains half of all bash bugs.

### A script, line by line
```
#!/usr/bin/env bash
set -euo pipefail
name="${1:-world}"
echo "hello, $name"
```
The first line (**shebang**) says which program runs it. `set -euo pipefail` makes the script stop on errors (`-e`), on undefined variables (`-u`) and when any part of a pipe fails. `$1` is the first argument and `${1:-world}` gives it a default. Save it, make it executable with `chmod +x script.sh`, and run it with `./script.sh nate`.

### Variables and quoting
`x=5` (no spaces around `=`), read with `$x` or `${x}`. Always quote expansions (`"$x"`), because unquoted values break on spaces and glob characters. `$(command)` captures output. `$?` is the last exit code, `$#` is the number of arguments, `$@` is all of them.
:: mid
Scripts get useful when they **repeat** and **decide**.

A `for` loop runs the same commands once per item:

```
$ for f in ~/sites/*.conf; do echo "checking $f"; done
```

`if` runs a command and checks whether it succeeded (exit code 0). `grep -q` is perfect for this: it prints nothing and just succeeds or fails.

```
$ if grep -q "ssl on" ~/sites/shop.conf; then echo "shop: tls"; else echo "shop: NO TLS"; fi
```

`$((...))` does integer math, which is handy for counters:

```
$ N=0; for f in ~/sites/*.conf; do N=$((N + 1)); done; echo "$N configs"
```

Put lines like these in a file and run it with `bash file.sh`. `$1`, `$2`... are the arguments you pass:

```
$ cat ~/bin/audit.sh
$ bash ~/bin/audit.sh ~/sites
```

### Conditions and loops
```
if [[ -f "$file" && -r "$file" ]]; then echo ok; elif [[ -d "$file" ]]; then echo dir; else echo missing; fi
for host in web1 web2 db1; do ping -c1 -W1 "$host" >/dev/null && echo "$host up"; done
while read -r line; do echo "$line"; done < hosts.txt
case "$1" in start) echo go;; stop) echo halt;; *) echo "usage";; esac
```
Test flags: `-f` file, `-d` directory, `-e` exists, `-z` empty string, `-n` non-empty, `-eq -ne -lt -gt` for numbers, `==` and `!=` for strings.

### Functions, arrays, and parsing arguments
```
log() { printf '%s %s\n' "$(date +%T)" "$*" >&2; }
hosts=(web1 web2 db1)
for h in "${hosts[@]}"; do log "checking $h"; done
```
`getopts` handles `-v -f file` style flags. Return values come from `return N` (an exit code) or from echoing a result and capturing it with `$(...)`.

### Everyday tasks
Loop over files (`for f in *.log`), rename in bulk (`mv "$f" "${f%.log}.txt"`), parse CSV columns with `cut` or `awk`, run commands on many hosts with `ssh host cmd`, and schedule with cron. Print errors to stderr (`>&2`) and exit non-zero on failure.
:: complex
### 1. Exit codes are the real booleans
Every command returns a number: `0` means success, anything else is failure. `$?` holds the last one. `&&` runs the next command only on success, `||` only on failure:

```
$ grep -q root /etc/passwd && echo "found root" || echo "no root"
$ ls /nope; echo "exit code: $?"
```

### 2. Reading files line by line
`while read line; do ...; done < file` walks a file one line at a time, which is how most log and inventory scripts work:

```
$ while read h; do echo "would ping $h"; done < ~/hosts.txt
```

### 3. Write scripts that don't hurt you
- Start real scripts with `#!/usr/bin/env bash` and `set -euo pipefail` (stop on errors, unset variables and failed pipes)
- Always quote variables: `"$f"`, or a filename with a space becomes two arguments
- Never build commands out of untrusted input. `eval "$user_input"` is command injection waiting to happen
- Prefer `[[ ]]` over `[ ]` in bash, and `$(...)` over backticks

> The sandbox supports one-line `for`, `while read` and `if` blocks plus `bash script.sh`, which covers most of what security scripts do.

### Safety and robustness
- Quote everything. Use `--` before filenames that might start with `-`.
- Use `mktemp` for temporary files and `trap 'rm -f "$tmp"' EXIT` to clean up.
- Never build commands from untrusted input (`eval` and unquoted variables lead to command injection).
- Validate input with patterns before using it; check that required tools exist (`command -v jq`).
- Use `shellcheck script.sh` to catch bugs automatically. It is the single best habit.
- Avoid parsing `ls` output; use globs or `find -print0` with `xargs -0`.

### Debugging
`bash -x script.sh` prints every command as it runs, `set -x` and `set +x` turn tracing on and off inside, and `echo` to stderr at decision points helps. If it works in your terminal but not in cron, suspect the PATH and the working directory.

There are a lot of configs in `~/sites`. Write a loop (or finish `~/bin/hunt.sh`) that checks every `.conf` file and prints the ones containing `proxy_pass` to an address **outside** 10.0.0.0/8.

:: hint
Start with a loop that prints each file and its proxy_pass lines: `for f in ~/sites/*.conf; do echo "== $f"; grep proxy_pass "$f"; done`
:: hint
Several configs proxy to internal 10.x addresses, which is normal. Filter those out with a second grep: `grep proxy_pass "$f" | grep -v "10\."`
:: hint
Combine it with `if`: `for f in ~/sites/*.conf; do if grep proxy_pass "$f" | grep -qv "10\."; then echo "$f"; fi; done`
:: solution
The one-liner:

`for f in ~/sites/*.conf; do if grep proxy_pass "$f" | grep -qv "10\."; then echo "$f"; fi; done`

prints only `/home/ops/sites/billing.conf`, which has `proxy_pass http://203.0.113.50:8443;` hidden under a `/healthz` location, so every health check (and anything else sent there) is shipped to an outside host. `api.conf` and `shop.conf` also use proxy_pass, but to internal 10.0.x backends. The answer is **billing.conf**.

:: file /home/ops/bin/audit.sh
#!/usr/bin/env bash
# usage: bash audit.sh <dir>   -> report TLS status of every nginx site config
DIR=$1
COUNT=0
for f in $DIR/*.conf; do
  COUNT=$((COUNT + 1))
  if grep -q "ssl on" $f; then
    echo "[tls]    $f"
  else
    echo "[NO TLS] $f"
  fi
done
echo "$COUNT configs checked"
