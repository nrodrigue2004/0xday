tagline: The OS decides who runs, what memory they get and which files they can touch. Learn processes, scheduling, virtual memory and permissions, then step through a setuid program and catch a race condition that reads a root-only file.
:: simple
An **operating system** (Windows, Linux, macOS, Android) sits between programs and hardware. Its core, the **kernel**, does four big jobs:
- **Processes**: starts programs, gives each one a turn on the CPU
- **Memory**: gives each process its own space and keeps them apart
- **Files**: organizes storage and enforces who can read or write what
- **Devices**: talks to disks, network cards and keyboards through **drivers**

Programs run in **user mode** and can't touch hardware directly. To open a file they make a **system call** (`open`, `read`, `write`) and the kernel, running in **kernel mode**, does it for them after checking permissions.

### What the OS actually does
It shares one machine among many programs safely. The **kernel** controls the CPU (scheduling), memory (virtual memory and protection), storage (file systems), devices (drivers) and security (users, permissions). Programs run in **user mode** with limited rights and ask the kernel for anything privileged through **system calls** (open, read, write, fork, exec).

### Processes and threads
A **process** is a running program with its own memory. A **thread** is a path of execution inside it, sharing that memory. The OS switches rapidly between them (**context switch**). Every process has a PID, a parent, an owner and a state: running, ready, sleeping or zombie (finished but not yet collected).
:: mid
### Processes and scheduling
A **process** is a running program with its own memory, open files and a PID. It can have several **threads** that share that memory. The **scheduler** switches between them many times per second (a **context switch**), using policies like round robin and priorities. States: running, ready, blocked (waiting for I/O).

### Memory
Every process sees its own **virtual address space**. The kernel maps it to physical RAM in **pages** (usually 4 KB) using page tables, and the CPU's MMU enforces it, so one process can't read another's memory. When RAM runs out, pages go to **swap**. Protections like **ASLR** (random addresses) and **NX/DEP** (data pages can't execute) make memory bugs harder to exploit.

### Permissions and setuid
Linux files have an owner, a group and `rwx` bits for each. A **setuid** program runs as its *owner* (often root) no matter who starts it. That's how `passwd` can write `/etc/shadow`. It's also why every setuid binary is a privilege escalation target.

```
$ print link
```

### Memory
Each process sees its own **virtual address space**, which the OS maps to physical RAM in pages. Protections mark pages readable, writable or executable. **Swap** moves idle pages to disk, which is slow. Typical layout: code, data, heap (grows up, `malloc`), stack (grows down, function calls). Out-of-memory conditions kill processes (the Linux OOM killer).

### Files and permissions
Everything is a file in Unix. Permissions are owner/group/other × read/write/execute; Windows uses ACLs on files and registry keys. Links: a **hard link** is another name for the same data, a **symbolic link** is a path pointer (attackers abuse them in races). Mounting attaches a file system at a directory.

### Boot process
Firmware (BIOS/UEFI) → boot loader (GRUB, Windows Boot Manager) → kernel → init system (systemd) → services → login. Secure Boot and measured boot with a TPM check that each stage is signed and unmodified. Rootkits and bootkits aim for these early stages.
:: complex
### Race conditions and TOCTOU
A **race condition** is a bug where the result depends on timing. The classic OS one is **TOCTOU** (time of check to time of use): a program **checks** something about a file, then later **uses** the file, and an attacker changes what the name points to in between, usually by swapping a **symlink**.

Here the setuid program asks `access()` "can the *real* user read this path?" (yes, it's their own file), sleeps briefly, then calls `open()` *as root*. If the attacker swaps `/tmp/r.txt` to point at `/etc/shadow` during that gap, root opens the shadow file.

```
$ break 16
$ continue
$ print opened
$ back
```

### Fixes
- Don't check-then-use. **Drop privileges** (`seteuid(getuid())`) and just `open()`; the kernel checks permission at the moment of use
- Open first, then check the open handle with `fstat()` (the handle can't be swapped)
- `O_NOFOLLOW` to refuse symlinks, and avoid world-writable dirs like `/tmp` (Linux's `fs.protected_symlinks` helps too)
- Better still, don't make it setuid: audit setuid binaries with `find / -perm -4000`

### Synchronization and deadlock
When threads share data they need locks, semaphores or atomic operations. Deadlock needs four conditions at once (mutual exclusion, hold and wait, no preemption, circular wait); break any one to prevent it. A **race condition** is when the result depends on timing, and a **TOCTOU** bug is a check followed by a use where the world changes in between.

### Security mechanisms
Privilege separation (user vs kernel, root vs normal), access control, ASLR (randomizes addresses), DEP/NX (data not executable), stack canaries, sandboxing and containers (namespaces and cgroups on Linux), seccomp (filter system calls), capabilities (split up root's powers), SELinux/AppArmor (mandatory access control), and virtualization-based isolation.

### Tools to look inside
Linux: `strace` (system calls), `ltrace`, `lsof`, `/proc/PID/`, `top`, `vmstat`, `dmesg`. Windows: Task Manager, Process Explorer, Process Monitor, `Get-Process`, `perfmon`. Watching what a program asks the kernel to do is the fastest way to understand it.

:: solution
At line 9, `link` is `/tmp/r.txt -> /home/student/mine.txt`, so `access()` (which checks the **real** uid 1001) says OK. During the `usleep()` on line 13 the attacker's loop swapped the symlink, and at line 14 `link` is `/tmp/r.txt -> /etc/shadow`. `open()` runs with **euid 0**, so it succeeds, and lines 16 to 17 print the start of the shadow file. The file opened was **/etc/shadow**. Fix: drop privileges before opening (or open with the user's rights and `fstat` the handle), use `O_NOFOLLOW`, and question why this tool is setuid at all.

#include <stdio.h>
#include <unistd.h>
#include <fcntl.h>

// /usr/local/bin/report is setuid root: it runs as root for every user,
// so users can print report files they own. It checks first, then opens.
int main(int argc, char **argv) {
    const char *path = argv[1];
    if (access(path, R_OK) != 0) {          // check: can the REAL user read it?
        puts("permission denied");
        return 1;
    }
    usleep(50000);                           // (formatting the header)
    int fd = open(path, O_RDONLY);           // use: opened with euid 0
    char buf[256];
    ssize_t n = read(fd, buf, sizeof buf);
    write(1, buf, n);
    return 0;
}
