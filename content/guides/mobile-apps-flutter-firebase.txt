**Flutter** builds apps for Android, iOS and the web from one codebase written in **Dart**. Everything on screen is a **widget**: a `Text`, a `Button`, a `Column` holding other widgets. A **StatelessWidget** just draws; a **StatefulWidget** holds data that changes and redraws when you call `setState()`.

**Firebase** is Google's backend-as-a-service:
- **Auth**: sign-in with email, Google, Apple, phone
- **Firestore**: a NoSQL database of **collections** and **documents** (JSON-like)
- **Storage** for files, **Cloud Functions** for server code

> In a Firebase app the client talks straight to the database. The only thing standing between a user and everyone's data is the **security rules**.

### How the pieces fit
**Flutter** (Dart language) draws the same UI on Android and iOS from one codebase. Everything is a **widget**: layout, buttons, text, the app itself. **Firebase** is Google's backend as a service: **Authentication** (sign-in), **Firestore** (a document database), **Cloud Storage** (files), **Cloud Functions** (server code), **Cloud Messaging** (push notifications) and **Analytics**. The app talks to Firebase directly from the device, which is why security rules matter so much.

### Widgets and state
`StatelessWidget` draws from its inputs; `StatefulWidget` holds data that changes and calls `setState`. For bigger apps use Provider, Riverpod or Bloc to share state. Hot reload shows code changes instantly during development.

### How the pieces connect
The app signs in with Firebase Auth and gets an ID token. Every Firestore read and write sends that token, and the **rules** decide using `request.auth.uid` (who is asking) and `resource.data` (the document).

```

```

### Things that are *not* secrets
The `google-services.json` / `firebaseOptions` API key is meant to be public: it identifies the project, it doesn't authorize anything. Real secrets (a payment provider's secret key, an admin SDK service account) must never be in the app, because anyone can unpack an APK and read every string.


### A typical flow
1. Sign in with Firebase Auth (email, Google, Apple).
2. Read the signed-in user's ID (`FirebaseAuth.instance.currentUser!.uid`).
3. Read and write documents under that user, for example `users/{uid}/notes`.
4. Listen for live updates with `snapshots()` and rebuild the UI from the stream.
5. Handle offline, loading and error states (every network call has all three).

### The OWASP Mobile Top 10, applied
- **Insecure data storage**: tokens in plain `SharedPreferences` instead of `flutter_secure_storage` (Keychain / Keystore)
- **Insecure communication**: no TLS or no certificate pinning for high-risk apps
- **Insecure authentication / authorization**: hiding the admin button in the UI but not checking the role in the rules or server
- **Code tampering and reverse engineering**: APKs decompile easily (jadx, apktool). Use obfuscation (`--obfuscate --split-debug-info`), Play Integrity / App Attest via **Firebase App Check**, and never trust the client

### Rules patterns
- deny by default: `allow read, write: if false;` at the root
- owner only: `allow read, write: if request.auth != null && request.auth.uid == userId;`
- validate writes: `request.resource.data.keys().hasOnly([...])`, type and size checks
- roles from **custom claims** (`request.auth.token.admin == true`), never from a field the user can edit
- test rules with the **Firebase Emulator** and rules unit tests before every release

### MDM in the enterprise
Company phones are managed with **MDM** (Intune, Jamf): enforce a PIN and encryption, push or block apps, separate work and personal data (containerization), and remote-wipe a lost device.

### Firestore security rules
Without rules, anyone with the app's config can read or write your database. Start from deny-all and add narrow allowances:

```
match /users/{uid}/notes/{id} {
  allow read, write: if request.auth != null && request.auth.uid == uid;
}
```
Validate data shape in rules (`request.resource.data.keys().hasOnly([...])`), never trust fields like `role` that the client sets, and test with the Firebase emulator before deploying. The Firebase config values in the app are identifiers, not secrets; **rules and server-side checks** are the security.

### Mobile-specific security
Store tokens in secure storage (Keychain, Keystore via `flutter_secure_storage`), not shared preferences. Use HTTPS only and consider certificate pinning for sensitive apps. Obfuscate release builds (`--obfuscate --split-debug-info`) knowing it only slows reverse engineering. Do not embed API keys that grant real power; call a Cloud Function that holds them. Restrict permissions to what the app needs, and test on a rooted device or emulator to see what an attacker sees.

### Enterprise angle
MDM (Intune, Jamf) pushes apps, enforces passcodes and encryption, separates work and personal data and can wipe a lost device. Understand app-store distribution, managed app configuration and BYOD policy.

The mobile team wants sign-off on StudyBuddy v2.0. Users keep **private notes** and their **profile** (including a phone number for study-group SMS).

Review `firestore.rules` against `data-model.md`. One rule exposes a whole collection of private data to **any signed-in user**, not just its owner.

Resolve the ticket with the **name of that collection**.
:: answer
profiles
:: hint
For each `match` block, ask: who does this rule allow? `request.auth != null` means "anyone with an account", and anyone can make an account.
:: hint
Compare with `data-model.md`: which collection is supposed to be owner-only but has no `uid ==` check?
:: solution
`notes/{userId}` correctly checks `request.auth.uid == userId`, and `groups` is meant to be readable by members. But `match /profiles/{userId}` says `allow read: if request.auth != null;`. Since sign-up is open, **anyone** can create an account and then list every profile, with phone numbers. The collection is **profiles**. Fix: `allow read, write: if request.auth != null && request.auth.uid == userId;`, move the fields group members need into a separate public `displayProfiles` collection, add a rules unit test for "user A can't read user B", and block the release until it passes.
:: verify

:: file /home/reviewer/review/firestore.rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // private notes: owner only
    match /notes/{userId}/items/{noteId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }

    // user profiles (name, school, phone for SMS reminders)
    match /profiles/{userId} {
      allow read: if request.auth != null;
      allow write: if request.auth != null && request.auth.uid == userId;
    }

    // study groups: members can read, owner can edit
    match /groups/{groupId} {
      allow read: if request.auth != null && request.auth.uid in resource.data.members;
      allow write: if request.auth != null && request.auth.uid == resource.data.owner;
    }

    // everything else: denied
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
