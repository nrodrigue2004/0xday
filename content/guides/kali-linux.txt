tagline: Kali is a toolbox, not a skill. Learn what's in it, how to run it safely in a homelab, and how to keep your own attack box from becoming the easiest target on the network.
:: simple
**Kali Linux** is a Debian-based distribution that comes with hundreds of security tools preinstalled: scanners, web proxies, password auditors, forensics and wireless tools. It's what pentesters, CTF players and students boot into.

In a homelab, Kali usually runs as a **VM** on a separate network segment, so practice traffic never touches your real network. Its default user is `kali` and tools live in the menu by category, or are just commands:

```
$ cat /etc/os-release
$ cat ~/tool-categories.txt
```

> Kali is for authorized testing on systems you own or have permission to test. The tools are legal; using them on other people's systems isn't.

### What Kali is, and is not
Kali is a Debian-based Linux distribution packed with security tools (nmap, Burp Suite, Metasploit, John, Wireshark, aircrack-ng and hundreds more). It is not a magic hacking button: the tools are all free and run on other systems too, Kali just saves you installing them. It is meant to be used by someone with permission to test, and it is a poor daily-driver OS since it favors tools over safety (older versions even ran as root by default).

### Ways to run it
A VM (VirtualBox, VMware or Proxmox) is the safest and easiest. WSL on Windows works for command-line tools. Live USB leaves no trace on the host. Bare metal is for Wi-Fi hardware work. For a homelab, one Kali VM on the LAB network is the standard.
:: mid
### Keeping it current
Kali is a rolling release: tools update constantly. Update before every engagement, and install extra tools from its repositories with `apt`:

```
$ apt list --upgradable
$ apt search gobuster
```

### Know where things live
- Wordlists: `/usr/share/wordlists/` (rockyou is gzipped by default)
- Nmap scripts: `/usr/share/nmap/scripts/`, Metasploit: `msfconsole`
- Web: Burp Suite, ZAP, gobuster/feroxbuster, sqlmap, nikto

```
$ ls /usr/share/wordlists
```

### Organize your work
Make a folder per target with `nmap/`, `loot/`, `notes.md`, and save every scan with `-oA`. A pentest is only as good as its report, and the report is only as good as your notes.

### The tool families
- **Information gathering**: nmap, dnsrecon, theHarvester, whois
- **Vulnerability analysis**: nikto, openvas/gvm, sqlmap
- **Web**: Burp Suite, ffuf, gobuster, wfuzz
- **Passwords**: John the Ripper, hashcat, hydra
- **Exploitation**: Metasploit, searchsploit
- **Sniffing**: Wireshark, tcpdump, responder, bettercap
- **Forensics and reversing**: autopsy, binwalk, ghidra, radare2
- **Reporting**: cherrytree, notes and screenshots

### Everyday workflow
Create a folder per engagement (`~/engagements/lab-2026-11/{recon,loot,notes,screens}`), save every scan with `-oA`, keep a running notes file with timestamps, and snapshot the VM before you start so a bad exploit does not cost you the setup. `tmux` keeps sessions alive over SSH and splits the screen.

### Wordlists
They live in `/usr/share/wordlists/` (`rockyou.txt.gz` must be unzipped first) and `/usr/share/seclists/` if you install SecLists. Big lists are not always better, a targeted list built from the target's names and seasons often beats a giant one.
:: complex
### Your attack box is a target too
A Kali VM full of credentials, client data and open services is attractive. Harden it like any server:
- change the default password, or better, disable password SSH login entirely
- don't leave services like SSH, a Python web server or a reverse-shell listener running and exposed after you're done
- keep client data encrypted and delete it when the engagement ends
- snapshot a clean baseline and revert between engagements

```
$ cat ~/audit/ss-tulpn.txt
```

### Safe homelab layout
Put Kali and vulnerable targets on an **isolated** internal network (a pfSense LAN or Proxmox bridge with no route to your home LAN), and give the lab internet only when you need updates. That way a vulnerable VM never sits on the same network as your family's devices.

### Legal and ethical rules
Written permission, defined scope, defined time window, and a way to stop. Practice on your own lab, deliberately vulnerable machines (Metasploitable, DVWA, Juice Shop), and platforms that invite it (TryHackMe, Hack The Box, picoCTF), and bug bounty programs within their rules. Never test a network you do not own or have a contract for.

### Keeping the attack box safe
Do not expose its services to the LAN, do not store real credentials or client data on it longer than needed, encrypt the disk if it holds engagement data, and treat anything you download (exploits from the internet) as untrusted: read it before you run it. Pull updates from the official repository only (`apt update && apt full-upgrade`).

:: brief
Before connecting your Kali VM to a client network, you run a quick self-audit. The results are in `~/audit`.

One service is listening on **all interfaces** and still accepts the **default credentials**. That's the first thing anyone on the client network would find.

Submit the **port number** of that service.
:: answer
22
:: hint
`cat ~/audit/ss-tulpn.txt` shows what's listening. `0.0.0.0` means every interface, `127.0.0.1` means local only.
:: hint
Now check which of those services still uses the default login. Look at `~/audit/sshd_config` and `~/audit/credcheck.txt`.
:: solution
`ss -tulpn` shows SSH on `0.0.0.0:22`, a Python web server on `0.0.0.0:8000` and PostgreSQL on `127.0.0.1:5432` (local only, fine). `credcheck.txt` shows `kali:kali` still works over SSH, and `sshd_config` allows password authentication. The answer is port **22**. Fix: `passwd`, set `PasswordAuthentication no` and use keys, and stop the leftover `python3 -m http.server` on 8000.
