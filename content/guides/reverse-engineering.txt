tagline: Reverse engineering is reading a program you don't have the source for. Learn how compiled code maps back to logic, then step through a crackme in a debugger and pull the password out of memory.
:: simple
When you compile a program, the readable source code is gone. What ships is **machine code**: bytes the CPU executes. **Reverse engineering** (RE) is working backwards from that to understand what the program does, without the source.

Two kinds of tools do the work:
- A **disassembler/decompiler** (Ghidra, IDA) turns the bytes back into assembly and rough C, so you can *read* it (static analysis)
- A **debugger** (gdb, x64dbg) runs the program one instruction or line at a time, so you can *watch* it (dynamic analysis)

The lab on this page is a debugger. Try it: start the program, step one line, and look at the variables.

```
$ start
$ step
$ info locals
```

> The highlighted line in the source pane is the line about to run, and the panel on the right shows variables right now. Values that just changed turn amber.

### The idea
Reverse engineering is working out what a program does from the program itself. You use it to understand malware, check a vendor's claims, find vulnerabilities, recover lost source, and solve crackme and CTF challenges. Two approaches that work together: **static** (read the code without running it) and **dynamic** (run it in a debugger and watch).

### A first pass takes minutes
`file prog` for the type and architecture, `strings prog` for messages and hints (often "Wrong password!" gives away where the check is), `ltrace` or `strace` to see library and system calls, and `objdump -d prog` or Ghidra to read the logic. Start from an interesting string, find where it is used, and read backward to the comparison that decides which message is printed.
:: mid
You rarely step through a whole program. You find the interesting spot, put a **breakpoint** there, and let the program run until it hits it.

Here the interesting spot is the loop in `check()` that builds `buf`. Break on line 12, run to it, then inspect:

```
$ break 12
$ continue
$ print i
$ print secret[i]
```

`continue` again jumps to the next time line 12 runs (the next loop iteration). `back` steps backwards, which real gdb can do with `record` / `reverse-step`.

```
$ continue
$ print secret[i]
$ back
```

> Reading the decompiled code first tells you where to break. Then the debugger tells you the actual values, which is often faster than doing the math by hand.

### Ghidra workflow
Create a project, import the binary, run auto-analysis, open the **Symbol Tree** and find `main` (stripped binaries lack names: look at `entry`, then the first argument of `__libc_start_main`). The **Decompiler** window shows C-like code. Rename variables (`L`), retype them (`Ctrl+L`), follow cross-references (`X`), and read the **Defined Strings** window for text to anchor on. Treat decompiler output as a strong hint, not truth.

### Patterns to recognize
- A loop over bytes with `xor` and a constant is simple encryption or obfuscation.
- `strcmp` or `memcmp` against a literal is a hard-coded password.
- A table of 256 values suggests a lookup-based cipher (RC4, AES S-box constants).
- Calls to `socket`, `connect`, `CreateProcess`, `RegSetValue` reveal capabilities.
- A large switch on a number is a command dispatcher.

### Dynamic analysis
Set a breakpoint at the comparison, run, look at registers and memory to see what is compared with what, and change a register or a jump to see another path. Watch system calls with `strace`, files with Process Monitor, and network with Wireshark.
:: complex
### 1. What the compiler leaves behind
Decompiled code is a reconstruction. Variable names are gone (Ghidra calls them `local_28`, `param_1`), loops become `do/while` with gotos, and constants show up as raw hex. Renaming things as you understand them is most of the job. This crackme's names were added by hand.

### 2. Recognizing the pattern
- `x ^ KEY` in a loop over bytes is **XOR encoding**: the secret is stored scrambled so `strings` won't show it
- `strcmp(input, buf)` means `buf` must hold the real password by the time it's called, fully decoded
- The return value of a function ends up in the `rax` register on x86-64, so "did the check pass?" is `$rax` after the call

### 3. Static vs dynamic, and why both
You can solve this statically: XOR each `secret` byte with `0x6b` yourself. Or dynamically: stop at the `strcmp` and read `buf`. Malware authors know this, so real samples add anti-debugging (checking for a debugger, timing checks, VM detection) to make the dynamic route harder. That's the point of patching anti-VM checks, like in my [anti-VM patching post](../posts/anti-vm-patching.html).

### Anti-analysis tricks
Programs may detect debuggers (`IsDebuggerPresent`, `ptrace` self-attach, timing checks), run only in certain environments, encrypt strings until needed, pack the real code, use control flow flattening or opaque predicates, and generate code at runtime. Counters: patch the check, use a debugger hiding plugin, dump memory after unpacking, and emulate small functions (angr, Unicorn, Frida) to avoid running everything.

### Frida and instrumentation
Frida injects JavaScript into a running process to hook functions, print arguments and return values, and change behavior without editing the binary, on desktop and mobile. It is the quickest way to see what an app sends before it encrypts it.

### Habits that pay off
Keep notes of every renamed function and address, work from the outside in, write small scripts to replicate algorithms you find, and verify understanding by writing a keygen or a decoder. Reading compiler output for your own C code is the best training for recognizing patterns in other people's.

:: hint
The decoded password must be complete in `buf` by the time `strcmp` runs. Which line is that?
:: hint

:: hint
At line 15, `print buf` (or look at the variables panel).
:: solution
`check()` XORs each byte of `secret` with `0x6b` into `buf`, then calls `strcmp(input, buf)`. Break on line 15 and `continue`, and the variables panel shows `buf = "pr0xm0x"`. You can confirm it statically: `0x1b ^ 0x6b = 0x70`, which is `p`, and so on. The password is **pr0xm0x**. Patching the `strcmp` result (or the jump after it) would also bypass the check, which is how many cracks work.

#include <stdio.h>
#include <string.h>

// check() recovered from crackme.exe with Ghidra, renamed by hand
static const unsigned char secret[7] = {0x1b, 0x19, 0x5b, 0x13, 0x6, 0x5b, 0x13};
#define KEY 0x6b

int check(const char *input) {
    char buf[8];
    if (strlen(input) != 7) return 0;
    for (int i = 0; i < 7; i++) {
        buf[i] = secret[i] ^ KEY;
    }
    buf[7] = 0;
    return strcmp(input, buf) == 0;
}

int main(void) {
    const char *guess = "letmein";
    if (check(guess)) puts("access granted");
    else puts("access denied");
    return 0;
}
