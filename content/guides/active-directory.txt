tagline: Active Directory is the phone book and the keyring of a Windows network. Learn domains, OUs, users, groups and how permissions really flow, then find the account that's secretly a Domain Admin.
:: simple
In a company, hundreds of Windows machines and users need to trust the same logins. **Active Directory Domain Services** (AD DS) is the central database that makes that work. A server running it is a **Domain Controller** (DC). When you log into a work PC, the DC checks your password and tells the PC who you are.

The building blocks:
- **Domain**: the security boundary, like `corp.local`
- **Users** and **computers**: objects in the directory
- **Groups**: collections of users, used to grant access ("Finance Share Readers")
- **OUs** (organizational units): folders to organize objects and to target Group Policy

```
$ cat ~/ad/structure.txt
$ cat ~/ad/users.csv
```

> Grant access to **groups**, not to individual users. When someone changes jobs, you move them between groups instead of hunting down every permission.
:: mid
### Groups inside groups
Groups can contain other groups (**nesting**). The recommended Microsoft pattern is **AGDLP**: put **A**ccounts into **G**lobal groups (by role, like "Finance Staff"), put global groups into **D**omain **L**ocal groups (by resource, like "Finance Share RW"), and assign **P**ermissions to the domain local group.

Nesting is powerful and easy to lose track of: a user's real access is the sum of every group they're in, **directly or through nesting**.

```
$ cat ~/ad/groups.txt
$ grep "Domain Admins" ~/ad/groups.txt
```

### Authentication
Domain logins use **Kerberos**: the DC gives you a ticket-granting ticket (TGT) at logon, and you trade it for service tickets to reach file shares, SQL servers and so on. Older **NTLM** still shows up as a fallback and is weaker.
:: complex
### Why attackers love AD
Owning AD means owning every machine that trusts it. Common paths, all of which are misconfigurations a defender can find first:
- **Nested group membership** that quietly grants admin rights (BloodHound maps these paths as a graph)
- **Kerberoasting**: service accounts with SPNs and weak passwords
- **AS-REP roasting**: accounts with "Do not require Kerberos preauthentication"
- **Stale privileged accounts**, shared admin passwords, and admins logging into workstations (leaving credentials in memory)

### Defending it
- Keep **Domain Admins** tiny and used only on DCs (the tiered admin model)
- Separate admin accounts from daily-use accounts (`nate` vs `adm.nate`)
- Audit privileged group membership **recursively**, on a schedule, and alert on changes (event IDs 4728/4732/4756 = member added to a security group)
- Use LAPS for local admin passwords, gMSAs for service accounts, and disable NTLM where you can

```
$ grep -E "4728|4732|4756" ~/ad/security.evtx.txt
```

Audit says Domain Admins should have exactly **two** human members: `adm.nate` and `adm.jrivera`.

A direct look at the group shows just those two. But group nesting counts, and one other **user** ends up with Domain Admin rights through a chain of nested groups.

Resolve the ticket with that user's **username**.
:: answer
t.nguyen
:: hint
Start from the Domain Admins line in `groups.txt`. Which members are groups rather than users?
:: hint
Follow each nested group down: find its line and see who its members are. Keep going until you reach users.
:: hint
The event log shows when the nesting was added. `grep 4728 ~/ad/security.evtx.txt`
:: solution
`Domain Admins` contains `adm.nate`, `adm.jrivera` and the group **IT-Tier0-Ops**. `IT-Tier0-Ops` contains the group **Helpdesk-Escalation**, which contains **t.nguyen** (a help desk tech's everyday account). So t.nguyen is effectively a Domain Admin. The security log shows `Helpdesk-Escalation` being added to `IT-Tier0-Ops` (event 4728/4756) on Oct 30 by `adm.jrivera`, probably as a "temporary" fix. The answer is **t.nguyen**. Fix: remove the nesting, give the help desk delegated rights only on the OUs they support, and alert on changes to Tier 0 groups.
