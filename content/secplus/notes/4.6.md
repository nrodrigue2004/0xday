Identity and access management (IAM) decides who gets in, what they can do, and how that is kept under control. Expect scenario questions that ask for the best model or factor.

### Identity and access management

- **Provisioning**: creating accounts and assigning access when someone joins. **De-provisioning**: removing access promptly when they leave or change role. Delays here are a leading cause of insider and former-employee incidents.
- **Permission assignments and implications**: least privilege, need to know. Over-permission accumulates ("permission creep") when people change roles; review periodically.
- **Identity proofing**: verifying a person is who they claim before issuing credentials (documents, in-person checks, knowledge checks).
- **Federation**: trust between organizations so one login works across them. The identity provider (IdP) authenticates; the service provider (SP) relies on it.
- **Single sign-on (SSO)**: authenticate once, access many systems. Convenient, but a compromised SSO account exposes many systems, so protect it with MFA.
- **Standards:**
  - **LDAP**: directory access protocol (Active Directory speaks it).
  - **SAML (Security Assertions Markup Language)**: XML-based federation and SSO, common in enterprise and between organizations.
  - **OAuth**: **authorization** framework letting an app act on your behalf with limited scope, without your password ("allow this app to read my calendar").
  - **OpenID Connect (OIDC)**: identity layer built on OAuth for authentication.
  - **Kerberos**: ticket-based authentication in Active Directory. Uses a key distribution center and timestamps (clocks must be in sync).
  - **RADIUS/TACACS+**: centralized AAA for network access (TACACS+ encrypts the whole payload and separates authentication, authorization and accounting).
- **Interoperability**, **attestation** (proving a device or software is in a known good state).
- **Password vaulting / privileged access management (PAM)**: store admin credentials in a vault, check them out for a limited time, record sessions, and rotate secrets. **Just-in-time (JIT) permissions** grant elevated access only when needed.

### Access control models

| Model | Who decides | Description |
| --- | --- | --- |
| **Mandatory (MAC)** | The system/administrator, using labels | Subjects and objects have labels (e.g. Secret, Top Secret); users can't override. Very strict, used in military |
| **Discretionary (DAC)** | The **owner** of the resource | Owner sets who can access (Windows file sharing). Flexible but easy to misconfigure |
| **Role-based (RBAC)** | The **role** | Permissions attached to job roles; users get roles. Scales well |
| **Rule-based** | A set of **rules** | Access governed by rules such as time of day or source IP, same for everyone |
| **Attribute-based (ABAC)** | **Attributes** | Decisions use attributes of the user, resource, action and environment (department, clearance, location, time) |
| **Time-of-day restrictions** | Time | Access limited to specific hours |
| **Least privilege** | Principle | Only the minimum access needed |

> Quick tell: "labels/clearance" → MAC. "Owner decides" → DAC. "Job function/group" → RBAC. "Attributes/context" → ABAC. "Rules/ACL with conditions" → rule-based.

### Multifactor authentication (MFA)

Factors are **different categories** of proof. Two passwords are not two factors.

| Factor | Examples |
| --- | --- |
| **Something you know** | Password, PIN, security answer |
| **Something you have** | Smart card, hardware token, phone app, security key (FIDO2) |
| **Something you are** | Fingerprint, face, iris, voice |
| **Somewhere you are** | Location, IP, geofence |
| **Something you do** | Behavior: gait, typing rhythm |

- **OTP types**: **HOTP** (counter-based), **TOTP** (time-based, 30-second codes in authenticator apps). Push notifications and SMS codes are weaker (SIM swapping, push fatigue); **FIDO2/WebAuthn security keys** and passkeys resist phishing.
- **Biometrics** are measured by **FAR** (false acceptance: an impostor gets in), **FRR** (false rejection: a legitimate user is locked out), and the **CER/EER** (crossover error rate where they are equal; lower is better). Biometrics are convenient but cannot be changed if stolen.
- **Authentication, authorization and accounting** all remain separate steps.

### Password security

- Modern guidance (NIST SP 800-63B): **length over complexity**, allow long passphrases, check against breached/common password lists, no forced periodic changes without evidence of compromise, don't use security questions or hints.
- Rules you still see: minimum length, complexity, **history** (no reuse), **maximum/minimum age**, **lockout** after failed attempts, **expiration**.
- **Password managers** generate and store unique passwords per site.
- **Passwordless** options: passkeys, security keys, biometrics plus device.
- Stored passwords must be **salted and hashed** with a slow algorithm.
- **Account types**: user, **privileged** (admin; use separate accounts and PAM), **service** (non-interactive; rotate credentials, restrict logon), **guest**, **shared** (avoid; breaks accountability).
- **Account policies**: expiration for contractors, disable on termination, location and time restrictions, **impossible travel** detection.

### Exam traps

- **OAuth** = authorization; **OIDC** = authentication layer on top; **SAML** = XML federation/SSO.
- **FAR** lets the wrong person in; **FRR** keeps the right person out.
- A password plus a PIN is **one factor** (both something you know).
- **Kerberos** needs synchronized clocks.
- **RBAC** is the best fit for large, role-structured organizations.
- **MAC** is the strictest; **DAC** is the most flexible.
