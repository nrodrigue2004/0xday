tagline: How software teams decide what to build and how they work: requirements, user stories, Scrum and Kanban, estimation, code review and technical debt.
:: simple
Writing code is the easy part. The hard parts are knowing **what** to build and keeping a team working in step. A **software development life cycle (SDLC)** is the sequence of activities: requirements, design, implementation, testing, deployment, maintenance.

Two ways to run it:
- **Waterfall**: finish each phase completely before the next. Good when requirements are fixed and mistakes are expensive to fix later (medical devices, avionics). Poor when the customer learns what they want only by seeing the software.
- **Agile**: work in short cycles, show working software often, change direction when you learn something. Most modern teams are some flavor of agile.

The **Agile Manifesto** values: individuals and interactions over process, working software over documentation, customer collaboration over contracts, responding to change over following a plan. The right-hand things still matter, the left-hand things matter more.

Vocabulary you will hear every day:
- **User story**: a small piece of value from a user's view: "As a student, I want to reset my password so that I can log in when I forget it."
- **Backlog**: the ordered to-do list of stories.
- **Sprint**: a fixed time box (1-4 weeks) in which the team finishes a chosen set of stories.
- **Stand-up**: a 15-minute daily sync: what I did, what I will do, what blocks me.
- **Definition of done**: the shared checklist a story must meet (code reviewed, tests pass, deployed, documented).
:: mid
### Requirements
- **Functional**: what the system does ("a user can reset a password by email").
- **Non-functional (quality attributes)**: how well it does it: performance, security, availability, usability, maintainability. These drive architecture and are forgotten most often.
- **Acceptance criteria** make a story testable. Given/When/Then style: *Given* a registered user, *When* they request a reset, *Then* an email with a single-use link valid for 30 minutes is sent.
- Good requirements are specific, testable and traceable. "The page should be fast" is not; "95% of requests complete in under 300 ms" is.
- Use cases, prototypes and talking to real users find requirements that nobody wrote down.

### Scrum
Roles: **product owner** (decides priority and value), **scrum master** (removes obstacles, coaches the process), **developers**. Events: sprint planning, daily stand-up, sprint review (demo to stakeholders), retrospective (what do we improve?). Artifacts: product backlog, sprint backlog, the increment. Scrum is a framework, not a bag of ceremonies: the point is the feedback loops.

### Kanban
Visualize work as cards on a board (To do, Doing, Review, Done), and set **WIP (work in progress) limits** per column so the team finishes things before starting new ones. Measure **cycle time**. Fits support and operations work where tasks arrive continuously. Many teams mix: "scrumban".

### Estimation
Teams use **story points** (relative size; Fibonacci 1, 2, 3, 5, 8) or t-shirt sizes, discuss differences in **planning poker**, then track **velocity** (points finished per sprint) to forecast. Estimates are about uncertainty, not promises. Break big stories down; if it cannot be estimated, run a time-boxed **spike** to learn first.

### Code review
A second pair of eyes on every change. Review for correctness, tests, readability, security (input validation, auth checks, secrets), and design. Keep PRs small (under about 400 lines). Be kind and specific: comment on the code, not the person; separate "must fix" from "nit". Reviews spread knowledge and are one of the cheapest defect-finding methods known.

### Technical debt
Shortcuts that make the next change slower, like a loan: sometimes worth taking, but it accrues interest. Track it visibly, pay it down continuously (the "boy scout rule": leave the code a little cleaner), and tie big payoffs to risk or delivery speed when arguing for time. Dead code, no tests, out-of-date dependencies and missing documentation all count.
:: complex
### Estimating honestly and planning with uncertainty
The **cone of uncertainty**: early estimates can be off by a factor of 4 either way. Reduce risk by building the scariest part first, using ranges ("3 to 6 weeks"), and re-forecasting from real throughput rather than guesses. Beware **Brooks' law**: adding people to a late project makes it later, because onboarding and communication grow faster than output. Hofstadter's law: it always takes longer than you expect, even when you account for that.

### Working agreements that keep teams fast
- Small batch sizes, thin vertical slices (UI to database) that can be released, not horizontal layers.
- **Trunk-based development** and CI so integration is never a big-bang event ([CI/CD chapter](cicd.html)).
- **Pairing and mob programming** for hard or risky work and onboarding.
- **Blameless postmortems**: after an outage ask how the system allowed the failure, not who to blame. Write down timeline, impact, causes, and tracked actions.
- **Architecture decision records (ADRs)**: short documents capturing a decision, its context and trade-offs, so the reasoning survives staff turnover.
- Write documentation where people look: README with how to run/test, runbooks for on-call, API specs (OpenAPI).

### Security in the process
- Add **abuse cases** and **threat modeling** (STRIDE) to design discussions: for each feature, how could someone misuse it?
- Security acceptance criteria in stories ("password reset tokens are single-use").
- Include security in the definition of done: dependency scan clean, no secrets, review by someone who knows the area.
- A **security champion** inside each team connects developers with the security group.
See the [secure SDLC chapter](architecture.html).

### Metrics: use with care
Velocity, burn-down charts and lines of code are easy to game and bad as targets (Goodhart's law: when a measure becomes a target it stops being a good measure). Prefer outcome measures: lead time, change failure rate, customer satisfaction, incidents.

### Team and career skills this builds
Writing clear tickets and PR descriptions, estimating, breaking down ambiguous work, saying "I don't know yet, here is how I will find out", and communicating risk early. Interviewers ask behavioral questions about these; prepare a short story for a disagreement in code review, a deadline slip and a bug you introduced.

### Interview checks
- Waterfall versus agile: when would you choose each?
- Write a user story and acceptance criteria for "forgot password".
- What does a good PR look like? What do you look for as a reviewer?
- Scrum versus Kanban in one minute.
