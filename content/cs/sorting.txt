:: simple
**Sorting** puts items in order so you can search them fast (binary search), merge them, spot duplicates and group them. You almost always call the built-in `sorted()` or `Arrays.sort()`. You learn the algorithms because interviews ask about them and because the *ideas* (divide and conquer, invariants, trade-offs) show up everywhere.

The three simple sorts, all O(n²) in the worst case:
- **Selection sort**: find the smallest item, put it first, repeat on the rest. Always about n²/2 comparisons, even on sorted input.
- **Insertion sort**: grow a sorted prefix. Take the next item and slide it left until it fits, like sorting playing cards in your hand. Fast on nearly-sorted data (O(n)).
- **Bubble sort**: swap neighbors that are out of order, repeatedly. Easy to teach, rarely worth using.

The three fast sorts, O(n log n):
- **Merge sort**: split in half, sort each half, merge the two sorted halves. Predictable and stable, needs O(n) extra space.
- **Quicksort**: pick a **pivot**, put smaller items left and larger right, recurse on both sides. Fastest in practice on arrays, but a bad pivot choice gives O(n²).
- **Heapsort**: build a max-heap, then repeatedly remove the largest. In place, no bad case, not stable.

### Insertion sort and the invariant
```
def insertion_sort(a):
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:   # shift bigger items right
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
```
**Loop invariant**: before each pass, `a[0:i]` is sorted. Each pass keeps it true while extending it by one. When `i` reaches `n`, the whole array is sorted. Naming the invariant is how you prove a loop correct.

### Merge sort
```
def merge_sort(a):
    if len(a) <= 1: return a
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:        # <= keeps equal items in order: stable
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    return out + left[i:] + right[j:]
```
There are log₂ n levels of splitting, and each level merges n items in total, so the work is **n log n** in every case. Cost: O(n) extra memory.

### Quicksort
```
def quicksort(a, lo=0, hi=None):
    if hi is None: hi = len(a) - 1
    if lo >= hi: return
    pivot = a[(lo + hi) // 2]
    i, j = lo, hi
    while i <= j:
        while a[i] < pivot: i += 1
        while a[j] > pivot: j -= 1
        if i <= j:
            a[i], a[j] = a[j], a[i]; i += 1; j -= 1
    quicksort(a, lo, j); quicksort(a, i, hi)
```
Average O(n log n). The worst case (always picking the smallest or largest as pivot, like "first element" on already-sorted data) is O(n²) and recursion depth n. Fixes: random pivot, median-of-three, and recursing on the smaller side first so the stack stays O(log n). **Introsort** (used by C++ `std::sort`) switches to heapsort when recursion gets too deep.

### Heaps and heapsort
A **binary heap** is an array where the children of index `i` are at `2i+1` and `2i+2` and every parent is at least as big as its children (max-heap). Building the heap takes O(n); each of the n removals costs O(log n). In place, O(1) extra space, O(n log n) always, but poor cache behavior and not stable.

### Stable vs unstable
A sort is **stable** if equal keys keep their original order. It matters when you sort by two keys: sort by date, then (stable) by name, and the dates stay ordered within each name. Stable: insertion, merge, bubble, Timsort, counting. Not stable: selection, quicksort, heapsort.

### Why n log n is the floor
A comparison sort decides the order using only "is a < b?" questions. There are n! possible orderings, and each yes/no answer at best halves the possibilities, so you need at least log₂(n!) questions. By Stirling's approximation, log₂(n!) is about n log₂ n. **No comparison sort can beat Ω(n log n)** in the worst case.

### Beating it by not comparing
- **Counting sort**: for integer keys in 0..k, count how many of each, then write them out. O(n + k).
- **Radix sort**: sort by the last digit, then the next, using a stable counting sort at each digit. O(d·(n + k)) for d digits. It sorts fixed-width IP addresses, timestamps and strings fast.
- **Bucket sort**: spread items into buckets by value range, sort each bucket. Great when values are uniform.
These only work when keys have a known, bounded form.

### What real libraries do
- **Timsort** (Python, Java objects): finds natural runs in the data, extends short runs with insertion sort, then merges with rules that keep it stable. O(n) on already-sorted input, O(n log n) worst case.
- **Introsort** (C++ `std::sort`): quicksort that falls back to heapsort at depth 2·log n and to insertion sort for tiny ranges.
- **External sort**: when data does not fit in RAM, sort chunks, write them out, then k-way merge. This is how databases and `sort(1)` handle huge files.
- Sorting is also a security topic: an attacker who controls input can trigger quicksort's O(n²) case if the pivot is predictable (algorithmic complexity DoS).

### Quickselect
To find the k-th smallest item you do not need a full sort. Partition like quicksort, then recurse only into the side that contains position k. Average O(n), worst O(n²). The median-of-medians variant guarantees O(n).

### Interview checks
- Which sorts are stable, and why does it matter?
- Why is quicksort faster than merge sort in practice despite the same average? (In place, cache friendly, small constants.)
- Sort a list of 1 million 16-bit integers fast. (Counting sort, k = 65,536.)
- What is the best sort for a nearly-sorted list? (Insertion sort or Timsort.)
