> **Rules first.** Everything here is for understanding, defending and practicing on **systems you own, a signed scope, or intentionally vulnerable training apps** (OWASP Juice Shop, DVWA, WebGoat, PortSwigger Web Security Academy, TryHackMe rooms). Testing a real site without permission is illegal in most places (in the US, the CFAA), even if you "only looked". Labs on this site use fictional data and simulated systems.

Almost every web vulnerability comes from one mistake: **the application trusts input or a request it should have checked.** The **OWASP Top 10** is the standard ranked list of the most common classes. The ones to know:

| Class | One-line idea | Core fix |
|---|---|---|
| **Broken access control** (incl. IDOR) | you can reach things that aren't yours by changing an id or URL | server checks ownership/role on every request |
| **Injection** (SQL, OS command, LDAP) | input is treated as code by an interpreter | parameterized queries, no shell-outs, input validation |
| **XSS** (cross-site scripting) | input ends up in a page as script that runs in other users' browsers | output encoding, CSP, `HttpOnly` cookies |
| **CSRF** (cross-site request forgery) | another site makes your logged-in browser send a request | anti-CSRF tokens, `SameSite` cookies |
| **Broken authentication / sessions** | weak passwords, no lockout, guessable or stolen sessions | MFA, rate limits, good session handling |
| **Security misconfiguration** | defaults, debug pages, open storage, verbose errors | hardening baselines, remove what you don't use |
| **Vulnerable and outdated components** | a library or CMS with a known CVE | inventory, patching, dependency scanning |
| **SSRF** (server-side request forgery) | you make the *server* fetch a URL it shouldn't (internal services, cloud metadata) | allow-list destinations, block internal ranges |
| **Cryptographic failures** | plaintext transport/storage, weak hashing | TLS everywhere, strong password hashing |
| **Logging and monitoring failures** | nobody noticed | log security events, alert, practice response |

Ground rule that fixes a large share of these: **validate on the server, authorize on the server, encode on output, and keep secrets out of the client.** See [how web apps work](how-web-apps-work.html).

### Injection (SQL injection as the model case)
Vulnerable code builds a query by gluing text together:

```code
query = "SELECT * FROM users WHERE name = '" + name + "' AND pass = '" + pw + "'"
```
If `name` contains SQL syntax (a quote and a comment marker, the classic textbook example), the input changes the *structure* of the query, for example turning the password check into a condition that is always true. The result is login bypass, data theft, or modification. Secure version:

```code
cursor.execute("SELECT * FROM users WHERE name = ? AND pass_hash = ?", (name, hash))
```
Placeholders send the query and values separately, so the database never parses the input as SQL. Same idea for **OS command injection** (don't build shell strings from input; call APIs with argument lists) and **NoSQL/LDAP injection**. Detection: errors containing SQL fragments, requests with quotes, `UNION`, `--`, `SLEEP(` in parameters, and responses far larger than normal.

### XSS
The app echoes user input into a page without encoding. **Reflected** (in a link or search box), **stored** (saved, e.g. a comment, hits everyone who views it), **DOM-based** (client-side JS writes unsafe data into the page). Impact: script runs as the victim on your site, so it can read page data, act as them, or steal a session cookie that isn't `HttpOnly`. Fixes: **contextual output encoding** (HTML, attribute, JS, URL), frameworks that auto-escape (React, templates), **Content-Security-Policy**, sanitizing rich text with a vetted library.

### CSRF
Your browser attaches your cookies to any request to the site, including ones triggered by a hostile page. Example: a hidden form that posts "change email" to your bank while you're logged in. Fixes: a per-session **anti-CSRF token** the attacker can't know, `SameSite=Lax/Strict` cookies, checking `Origin`/`Referer`, requiring re-auth for sensitive actions, and never changing state with GET.

### Broken access control and IDOR
Changing `/orders/1002` or `?user_id=7` returns someone else's data because the server only checks "logged in". Also: forced browsing to `/admin`, privilege flags the client can set, missing function-level checks, directory listing. Fix: deny by default, one central authorization layer, check ownership on every object. See [APIs, REST and JSON](apis-rest-json.html).

### SSRF
A feature that fetches a URL for you (image import, webhook, PDF render) can be pointed at `http://localhost`, internal admin panels, or the cloud **metadata service** (`169.254.169.254`), which can hand out credentials. Fixes: allow-list hosts, resolve and block private/loopback/link-local addresses, enforce IMDSv2 on cloud hosts, egress filtering.

### File upload, deserialization, open redirect
- **Unrestricted upload**: a server-side script uploaded as an "image" and then executed. Check type by content, rename files, store outside the web root, serve from a separate domain, never execute uploads.
- **Insecure deserialization**: untrusted serialized objects rebuilt by the server can run code. Don't deserialize untrusted data; use plain JSON with validation.
- **Open redirect**: `?next=` sends users anywhere, which makes phishing links look legitimate. Allow-list redirect targets.

### Defensive controls by layer
| Control | Stops | Limit |
|---|---|---|
| Parameterized queries, ORM used correctly | SQL injection | raw-SQL escapes in the ORM still bite |
| Output encoding + CSP | XSS | CSP needs tuning, encoding must match context |
| Authz middleware, deny by default | broken access control | logic flaws need tests |
| `SameSite` + CSRF tokens | CSRF | token must be validated, not just present |
| WAF | known patterns, virtual patch while you fix | bypassable, noisy, not a fix |
| Rate limits, lockout, MFA | brute force, credential stuffing | needs monitoring |
| SAST / DAST / dependency scan in CI | many bugs before release | false positives, blind to logic |
| Pen test / bug bounty | what automation misses | point in time |

### Secure development habits
Threat model a feature before building it (what can go wrong, who attacks it). Use framework defaults instead of rolling your own auth or crypto. Code review for authorization checks. Keep dependencies and base images updated. Write abuse-case tests (user A requests user B's object) next to your normal tests. Treat the OWASP Cheat Sheet Series and ASVS as your checklist.

### Detecting attacks in logs
Web access logs (combined format) and WAF logs are the sensor. Hunting patterns:
- Many 404s for odd paths from one IP: scanning (`/.env`, `/wp-admin`, `/phpmyadmin`).
- Requests with `'`, `%27`, `UNION`, `SELECT`, `<script`, `../`, `${jndi:` in parameters: probing for injection, XSS, traversal.
- A run of 500s on one parameter, then a 200 with a huge `bytes` value: an injection that worked.
- Sequential id access with many 200s from one account: IDOR sweep.
- Same account from several countries or user agents in a short time: session theft.
Map findings to **MITRE ATT&CK** (T1190 exploit public-facing application) and escalate per your IR process ([incident response](../learn/incident-response.html), [log analysis](../learn/log-analysis.html), [Security Onion / SIEM](../learn/siem-security-onion.html)).

### Practicing legally
Run an intentionally vulnerable app in your own lab (Docker on the [homelab](../homelab.html), isolated from your real network). Walk the OWASP list: find one instance, explain why it happens, write the fix, and write the detection (a Sigma or WAF rule). That loop (break, fix, detect) is what interviewers want to hear. For bounty programs, read the scope and rules of engagement first and stay inside them.
