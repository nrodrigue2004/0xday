:: simple
After NX made the stack non-executable, putting your own code in a buffer stopped working. **Return-oriented programming (ROP)** is the response: the program is full of small pieces of its own code, and any piece that ends in `ret` can be borrowed.

- A **gadget** is a few instructions followed by `ret`, for example `pop rdi; ret`
- `ret` takes the next value off the stack and jumps to it. If an overflow has filled the stack with a list of addresses, each `ret` jumps to the next gadget in the list
- Chained together, gadgets form a tiny program built entirely out of existing code, so NX never sees any new code run

Why `pop rdi; ret` is the famous one: on 64-bit Linux the **first argument of a function goes in `rdi`**. To make the program call `win(0xdeadbeef)` the attacker needs `rdi = 0xdeadbeef` first. The stack holds: the address of the gadget, then the value that `pop rdi` will load, then the address of `win`. The `ret` after the pop jumps to `win` with the argument already in place.

### Anatomy of the stack during a chain
After the overflow reaches the saved return address, the stack looks like this (toy numbers, lowest address first):

```code
[ padding up to the return address ]
[ address of gadget: pop rdi; ret  ]   <- the function's ret jumps here
[ 0x00000000deadbeef                ]   <- pop rdi loads this into rdi
[ address of win()                  ]   <- the gadget's ret jumps here
```
Each `ret` consumes one slot. A longer chain just continues the list.

### Finding gadgets
Tools scan a binary's executable bytes for instruction sequences that end in `ret` (and any starting offset counts, even in the middle of a longer instruction):
- `ROPgadget --binary ./prog`
- `ropper -f ./prog --search "pop rdi"`
- `objdump -d ./prog | grep -B2 ret`

The result is a list of `address : instructions`. A larger binary or a linked libc has thousands of gadgets, enough to do anything. Small programs may have only a few.

### Why mitigations matter here
- **No PIE** means gadget addresses are fixed and known: the situation in the [mitigations lab](mitigations.html)
- **PIE + ASLR** means the attacker must leak an address first
- **Canaries** stop the overflow from reaching the return address silently
- **CET shadow stacks / CFI** check every `ret`, which breaks the chain

### The defender's view
ROP is not invisible: `ret` instructions that do not match a prior `call` are the signature. Endpoint tools and hardware features watch for that (Intel CET, Windows CFG/CIG and kernel mitigations). On the logging side, look for crashes with an instruction pointer inside library code or at a non-function address, repeated service restarts with a crash address of the form `0x4141414141`, and unusual child processes started by a service (`/bin/sh` from a web server).
:: complex
### Turing-complete from gadgets
With enough gadgets you get loads, stores, arithmetic, conditionals (gadgets that change the stack pointer by a computed amount) and calls. Compilers can even be built that turn a program into a ROP chain. The practical lesson is that "no injected code" is not a safety guarantee.

### Calling conventions
The registers a gadget has to set depend on the platform: System V x86-64 (Linux) uses `rdi, rsi, rdx, rcx, r8, r9`; 32-bit x86 passes arguments on the stack; ARM uses `r0` to `r3` and the gadgets pop into those. Windows x64 uses `rcx, rdx, r8, r9`.

### Variations (names worth knowing)
- **ret2libc**: return into a library function such as `system` with a chosen argument (the original NX bypass)
- **ret2win**: a CTF form: just return into a function that prints the flag
- **SROP**: abuse the signal-return mechanism to set all registers with one gadget
- **JOP/COP**: chains built from `jmp` or `call` gadgets, to avoid `ret` checks
- **Data-only attacks**: change variables (like `is_admin`) and never touch control flow, which is why CFI is not the end of the story

### Practice responsibly
Work only on practice binaries (ROP Emporium, pwn.college, Exploit Education) inside a VM. The toy listing in this chapter is fictional and has no connection to a real product. Exploit development against systems you do not own or have permission to test is illegal, and the same techniques taught here are what a penetration test report describes in prose, not in working chains.

### Reporting an overflow
A useful finding states: the vulnerable function and input, the mitigations present (`checksec` output), whether control of the instruction pointer is demonstrated, and a fix (bounds-checked copy, canary, PIE, safer language for the component). You do not need a working chain to make a high-severity report once control of the return address is shown.

### gadget terms
gadget | a few instructions ending in ret
chain | a list of gadget addresses and values on the stack
pop rdi; ret | puts the next stack value into the first-argument register
ret2libc | return into a library function with chosen arguments
ret2win | return into a function that already prints the flag (CTF)
CET shadow stack | hardware check that every ret goes where its call came from
### commands

ropper -f ./prog --search "pop rdi" | find a specific gadget
objdump -d ./prog | disassemble to read gadgets in context
python3 -c 'print(hex(...))' | build addresses and values
gdb ./prog | check crash state and registers

`win(int key)` in the toy binary `vault` (fictional, no PIE) prints the flag only if `key == 0xdeadbeef`. A review found an overflow, so the open question is whether the program contains the gadget needed to pass an argument: one that loads the first-argument register `rdi` from the stack.

`gadgets.txt` is the gadget listing for the binary. Find the gadget `pop rdi ; ret` and submit its **address**, written as `0x...`.
:: answer
0x401233
0x0000000000401233
401233
:: hint
`cat gadgets.txt`. Each line is `address : instructions`.
:: hint
`grep "pop rdi" gadgets.txt`
:: hint
Beware lookalikes: `pop rdi ; pop rbp ; ret` also loads rdi but takes two stack slots, and `pop rsi ; ret` loads the wrong register. The answer is the exact `pop rdi ; ret`.
:: solution
`0x401233 : pop rdi ; ret` is the gadget. A chain for this toy would be: padding up to the return address, `0x401233`, `0xdeadbeef`, then the address of `win`. The `ret` of the overflowed function jumps to the gadget, `pop rdi` loads the key, and the gadget's `ret` goes to `win` with the argument in place. A defender stops it by removing the overflow, enabling a canary and PIE, and building with CET (a shadow stack rejects the first `ret`).
