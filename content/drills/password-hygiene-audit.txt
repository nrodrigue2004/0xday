tagline: Audit a made-up lab for password reuse, missing MFA and weak SSH setup. Find the one password that protects too much.
:: simple
The most common way a small lab or a small company gets owned is boring: one password used in many places. Someone gets it once (a phishing page, a leaked database, a shoulder surf) and tries it everywhere.

Three habits fix most of it:

1. **A password manager.** One long unique password per system, generated, never typed from memory. You remember one strong passphrase for the vault.
2. **MFA** on anything that supports it, especially anything that can administer something else (hypervisor, firewall, domain controller). Prefer an authenticator app or a hardware key over SMS.
3. **SSH keys** instead of SSH passwords. A key cannot be guessed from the network and cannot be reused on another site by accident.

The lab below is a fictional lab, not yours. The skill is the audit: list every credential, find the pattern, rank the risk.
:: mid
### What an audit looks at

For each system and account:

- **Is the password unique?** Password managers and audit tools can show a short *fingerprint* (a few characters of a hash) so you can spot duplicates without ever seeing the password. The inventory in this lab uses that idea.
- **Is MFA on?** For admin accounts, no MFA is the biggest gap after reuse.
- **How old is it?** "Never changed" on a default account is a red flag.
- **How do you log in over SSH?** Password logins can be guessed, and root login over SSH removes one hurdle for an attacker.

### Finding duplicates

Count how many times each fingerprint appears:

```
$ cut -d, -f5 ~/audit/inventory.csv | sort | uniq -c | sort -rn
```

A count above 1 means that one secret opens more than one door.

### Blast radius

If the top fingerprint leaks, which systems fall? List them:

```
$ grep ',7c4a8d,' ~/audit/inventory.csv | cut -d, -f1
```

Use whatever fingerprint your own count put on top. Then ask which of those systems can reach or manage the others. A hypervisor password that matches a firewall password means one leak controls the whole lab.
:: complex
### Fix order

Do not try to fix everything in one afternoon. Rank by blast radius:

1. Rotate the reused password on the **most powerful** systems first (hypervisor, firewall, domain controller), with a fresh generated password for each.
2. Turn on MFA for those same accounts.
3. Move SSH to keys: generate a key pair per client (`ssh-keygen -t ed25519`), put the public key in `authorized_keys`, test a second login from a new terminal, and only then set `PasswordAuthentication no`. Keep a console session open while you change it, so you can undo a mistake.
4. Disable direct root login (`PermitRootLogin no`) and use a named admin account with `sudo`.
5. Put the rest into the password manager over a week or two.

### Defensive details

- A **vault** is protected by one passphrase and its own MFA. Back up the vault and the recovery codes somewhere offline.
- Store **recovery codes** separately from the vault.
- A shared `authorized_keys` entry with no comment cannot be traced to a person or machine. Use one key per client, with a comment, and remove old keys when a laptop goes away.
- Deliberately vulnerable lab targets (like Metasploitable) are an exception. Keep them isolated and never reuse a real password on them.

### What an attacker does with a reused password

*Credential stuffing*: take one known pair and try it against every service. It works because people reuse. Rate limits and MFA stop it; unique passwords make it pointless.

### Common mistakes

- Treating "I only reuse it on the lab" as safe. The lab is where the hypervisor and the domain controller live.
- Enabling MFA but keeping a bypass such as a shared recovery code in a note file.
- Setting `PasswordAuthentication no` before the key login works, and locking yourself out.
