tagline: Regular expressions from zero to useful, applied to web logs. Count the path traversal attempts, including the encoded ones.
:: simple
A **regular expression** (regex) is a pattern that describes text. Instead of searching for one exact word, you describe a shape: "three digits, a dash, four digits". `grep -E` takes a regex and prints the lines that match.

```
$ grep -E "404" ~/logs/access.log
$ grep -cE "POST" ~/logs/access.log
```

Most characters match themselves. The special ones are:

- `.` any single character
- `*` the previous thing, zero or more times
- `+` one or more, `?` zero or one
- `[abc]` one of a, b or c; `[0-9]` a digit; `[^0-9]` anything but a digit
- `^` start of line, `$` end of line
- `a|b` a or b
- `( )` group things together
- `\` makes a special character plain: `\.` is a real dot

> The classic beginner bug: an unescaped dot. `10.0.0.5` also matches `10a0b0c5`. Write `10\.0\.0\.5`.

### grep flags you will use daily

`-E` extended regex (use it always), `-i` ignore case, `-v` invert (lines that do *not* match), `-c` count lines, `-o` print only the matching part, `-n` line numbers.
:: mid
### Building a pattern in steps

Match an IPv4 address loosely:

```
[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+
```

Shorter with a repeat count: `([0-9]{1,3}\.){3}[0-9]{1,3}`. This also matches `999.1.1.1`, which is not a real address. For log triage "close enough" is fine; for validation it is not.

### Shorthand classes

In GNU grep and most tools: `\d` digit (not in plain `grep -E`, use `[0-9]`), `\s` whitespace, `\w` word character, `\b` word boundary. The POSIX forms `[[:digit:]]`, `[[:space:]]`, `[[:alpha:]]` work everywhere.

### Greedy versus lazy

`.*` takes as much as it can. On `a "b" and "c"`, the pattern `".*"` matches the whole `"b" and "c"`. The fix without lazy quantifiers is to exclude the delimiter: `"[^"]*"` matches `"b"` then `"c"` separately.

### Pulling out just the part you want

```
$ grep -oE "[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+" ~/logs/access.log | sort | uniq -c | sort -rn
$ sed -E 's/^([0-9.]+) .*"(GET|POST) ([^ ]+).*/\1 \3/' ~/logs/access.log
```

`-o` prints only the match. In `sed`, parentheses **capture** a piece and `\1` pastes it back.

### Think like an attacker

The pattern you write only catches what you imagined. Attackers write the same thing many ways: `../`, `..%2f`, `%2e%2e/`, `%2E%2E%2F`, `....//`. Always ask what the same attack looks like **encoded**, and match case-insensitively with `-i`.
:: complex
### Anchors and boundaries

`^GET` only at line start. `\.php$` only at line end. `\bcat\b` matches the word `cat` but not `concat`. Anchoring makes patterns both faster and more precise.

### Alternation and grouping

`(\.\.|%2e%2e)(/|%2f)` reads as: either two dots or the encoded form, followed by either a slash or its encoded form. Parentheses limit where the `|` applies. Without them, `\.\.|%2e%2e/|%2f` means three different things.

### Backreferences

`\1` repeats what group 1 matched. `([a-z])\1` finds doubled letters. Handy to spot `aaaa` in DGA-looking domains or repeated tokens.

### Lookahead, and why grep -E does not have it

Perl-style regex (`grep -P`, Python `re`, JavaScript) supports lookahead: `foo(?!bar)` is "foo not followed by bar". POSIX `grep -E` does not. If you need it, use `grep -P` or `python3`.

### Performance and danger

Some patterns can take **exponential** time on crafted input (ReDoS): nested repeats such as `(a+)+$` against `aaaaaaaaaaaaaaaaaaaa!`. If you write regex for a server that handles untrusted input, prefer simple linear patterns, set timeouts, or use an engine that guarantees linear time.

### Regex in the detection world

Regex powers SIEM searches (`rex` in Splunk, `regexp` in Elastic), Sigma rules (`|re`), Suricata (`pcre:`) and YARA. The same habits apply: escape the dots, anchor where you can, think about encodings and case, and test against a **sample of normal traffic** too, because a rule that catches the attack and also 4,000 normal lines is not usable.

### How to test a pattern

1. Count what it catches: `grep -cE 'pattern' file`.
2. Look at the hits: `grep -E 'pattern' file | head`.
3. Look at the misses you expected to hit and the hits you did not expect (`-v` and reading).
4. Only then trust the number.
:: lab
style: shell
host: web01
user: analyst
cwd: /home/analyst
:: brief
The web server log is at `~/logs/access.log`. Someone from `192.0.2.200` has been trying **path traversal** (climbing out of the web folder with `../`) to read system files. They did not always write it plainly: some requests encode the slash or the dots.

Count how many **log lines** contain a path traversal attempt: a double dot or its encoded form (`%2e%2e`, any case), followed by a slash or its encoded form (`%2f`).

Beware: some **harmless** requests also contain two dots (a file named `report..pdf`, for example). Submit the **number of lines**.
:: answer
7
:: hint
First try `grep -c "\.\./" ~/logs/access.log`. The count is too low, so look at the traversal lines you missed with `grep "192.0.2.200" ~/logs/access.log`.
:: hint
Build the pattern in two halves: the dots part `(\.\.|%2e%2e)` and the slash part `(/|%2f)`. Add `-i` so `%2E` counts too.
:: hint
`grep -ciE "(\.\.|%2e%2e)(/|%2f)" ~/logs/access.log`
:: solution
The pattern `(\.\.|%2e%2e)(/|%2f)` with `-i` catches all seven: plain `../../etc/passwd`, `..%2f..%2f` (encoded slashes), `%2e%2e/` (encoded dots), `%2E%2e%2f` (mixed case), and `....//` (which still contains `../` once the server strips the inner one). The plain `\.\./` pattern finds only part of them. The five decoys are legitimate and do not match, because a `..` that is not followed by a slash, like `report..pdf` or `..+in+bash`, is not a traversal. All seven came from `192.0.2.200`, so you can confirm with `grep -c 192.0.2.200`.

The lesson: count, look at the hits, look at what you missed, then trust the number.
:: verify
grep -ciE "(\.\.|%2e%2e)(/|%2f)" ~/logs/access.log
