01 simple // the idea in plain words

Git tracks changes to files over time. Each commit is a snapshot with a message, an author and a unique ID (a SHA hash). You can see who changed what, when, and go back to any version. GitHub hosts Git repositories online and adds pull requests, issues and CI.

The everyday loop:

$ git status
$ git log --oneline
  • git add file stages a change, git commit -m "message" saves the snapshot
  • git push sends commits to GitHub, git pull gets others' commits
  • A branch is a separate line of work; merge it back when it's done

Write commit messages that say *why*, not just *what*. Future you will read them during an outage.

The mental model

Git saves snapshots (commits) of your project, each with a message, an author and a pointer to its parent. A repository is the folder plus its history. A branch is a movable label on a commit. GitHub hosts a remote copy so you can back up, share and collaborate. Three places hold your files: the working directory (what you see), the staging area (what will go in the next commit) and the repository (committed history).

The daily loop

git status
git add file.txt
git commit -m "Explain why, not just what"
git push

Commit small, commit often, write messages in the imperative ("Fix login redirect"). git pull brings in other people's work first.

02 mid // how it's actually used

Branches and pull requests

Teams don't commit straight to main. You make a branch, push it, and open a pull request (PR): a request to merge, where others review the diff and CI runs the tests. Branch protection can require reviews and passing checks before merging.

$ git branch -a
$ git show --stat a41c9e2

Seeing changes

git diff shows uncommitted changes; git show <sha> shows exactly what one commit changed; git log -p file shows a file's whole history, change by change.

Branches and merging

git switch -c fix/login-bug
git commit -am "Fix login redirect"
git switch main
git merge fix/login-bug

Merge keeps history as it happened; rebase replays your commits on top of the latest main for a straight line (never rebase commits other people already have). Conflicts appear when two branches edit the same lines: open the file, keep the right text between the <<<<<<< markers, remove the markers, then git add and commit.

Undoing things

git restore file discards unstaged edits, git restore --staged file unstages, git commit --amend fixes the last commit message, git revert <commit> makes a new commit that undoes another (safe for shared branches), git reset --hard <commit> throws away work (dangerous), and git reflog shows where HEAD has been, which rescues "lost" commits.

Pull requests

A PR proposes merging a branch. Good ones are small, explain the reason, link the issue, and pass automated checks. Reviewers look for correctness, security and clarity. Protect main with required reviews and checks.

03 complex // what the pros do

Secrets in history

Deleting a secret in a new commit doesn't remove it: the old commit still contains it, and anyone who clones the repo gets the whole history. Bots scan public GitHub for leaked keys within minutes of a push.

$ git log --oneline --all -- config/settings.py
$ git log -p --all -S "API_KEY" --oneline

-S "text" (the "pickaxe") finds commits that added or removed that text.

If you leak a secret

  1. Rotate it immediately. Assume it's compromised the moment it was pushed
  2. Then clean history if needed (git filter-repo, BFG) and force-push, knowing forks and clones may still have it
  3. Prevent it: .gitignore for .env files, pre-commit secret scanning (gitleaks), GitHub push protection, and secrets in a vault or CI secrets, never in code

Supply chain

Signed commits, protected branches, required reviews and pinned dependency versions all exist because a malicious commit or package can reach production through Git.

Useful investigation commands

git log --oneline --graph --all, git blame file (who changed each line), git log -S"password" (when a string appeared or vanished), git diff main..feature, git show <commit>, and git bisect (binary search for the commit that introduced a bug).

Repository security

Turn on secret scanning and push protection, use .gitignore for .env and keys, require signed commits where it matters, enable Dependabot or similar for vulnerable dependencies, pin GitHub Actions to commit SHAs, give Actions the minimum permissions:, and review third-party workflow code. If a secret is committed, rotate it first; rewriting history (git filter-repo) is cleanup, not a fix.

Workflows

Trunk-based development (small changes straight to main with feature flags) suits fast CI; GitHub Flow (short branches plus PRs) is the common default; Git Flow (develop, release, hotfix branches) suits versioned releases. Pick one and write it down.
