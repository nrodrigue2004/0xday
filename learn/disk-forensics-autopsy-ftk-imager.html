Disk forensics starts with a perfect copy and a hash, and ends with a timeline. Learn FTK Imager for acquisition and Autopsy for analysis, then find a deleted file by its hash.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Disk forensics is examining a drive's contents without changing them. Two jobs, two tools:

  • FTK Imager acquires: it makes a bit-for-bit image of a drive (.E01 or raw .dd) and records its hash.
  • Autopsy analyzes: it opens the image read-only, lists files (including deleted ones), builds timelines and runs keyword and hash searches.

The rule that everything else follows: never work on the original. Image it, hash it, store the original, examine a copy.

$ sha256sum case/disk.dd
$ cat case/acquisition.txt

Words to know

  • Image: an exact copy of a drive or partition, including free space and deleted data
  • Hash: SHA-256 (or MD5) of the image. If it matches at acquisition and again later, nothing changed
  • Write blocker: hardware or software that stops the examiner's machine writing to the evidence drive
  • Chain of custody: the log of who held the evidence, when, and why
  • Unallocated space: disk area no file currently owns; deleted data often survives there

02 mid // how it's actually used

Acquiring with FTK Imager

  1. Attach the source through a write blocker (or use a read-only mount)
  2. File > Create Disk Image > pick Physical Drive > format E01 (compressed, stores case info) or raw
  3. Fill in case number, evidence number, examiner, notes
  4. Turn on Verify images after they are created; keep the hash report beside the image

FTK Imager can also add an image as evidence, browse its file tree read-only, export files, and capture memory or protected registry files from a live system.

Autopsy workflow

  1. New case, add a data source (the image), let ingest modules run: hash lookup, file type id, recent activity, keyword search, extension mismatch
  2. File Views > Deleted Files: entries still in the file table but marked deleted
  3. Data Artifacts: browser history, USB devices, recent documents, installed programs, web downloads
  4. Timeline: every file and artifact timestamp on one axis (MACB: modified, accessed, changed, born)
  5. Keyword search and hash set matches; tag items and export a report

Deleted does not mean gone

Deleting removes the directory entry or flags it free, but the data stays until overwritten. Where it hides: deleted entries still in the file table, unallocated space (carve it by file signature), the recycle bin ($Recycle.Bin), shadow copies, and slack space. SSDs with TRIM can really erase it, so say so in a report.

Evidence you check on Windows

NTUSER.DAT (recent files, run keys), $MFT (file records, timestamps), Prefetch (programs run), UsrClass.dat, browser profiles, setupapi.dev.log and USBSTOR (plugged-in USB drives), event logs.

03 complex // what the pros do

Timeline discipline

Timestamps lie in two ways: clocks are wrong, and the filesystem updates some times on copy and move. Note the machine's timezone, then compare several sources before claiming a time. A file copied to a USB drive keeps its modified time but gets a new created time on the destination: created later than modified is a copy signature.

Anti-forensics to expect

Wiping tools, timestomping (altered times: compare $STANDARD_INFORMATION with $FILE_NAME in the MFT), renamed extensions (check the file signature, not the name), encrypted containers, and data in alternate data streams. Extension mismatch ingest catches the second one.

Hash sets

A known-good set (NSRL) filters out the operating system so you read what is left. A known-bad set flags files you already care about, like the stolen document's hash. Matching a hash proves content, even if the filename changed.

Verifying and reporting

Re-hash the image before and after the case. A report states what was examined, what tools and versions, what was found with path and timestamps, and what it does not show. Findings and opinions go in separate paragraphs.

Command line equivalents (Sleuth Kit)

Autopsy sits on The Sleuth Kit: mmls shows partitions, fls -r -o 2048 image.dd lists files with deleted ones starred, icat extracts by inode, istat shows an inode's metadata, tsk_recover pulls deleted files, blkls dumps unallocated space for carving.

ref reference // commands and terms, also on the cheatsheet

acquisition

sha256sum disk.dd
hash an image; compare with the acquisition record
dd if=/dev/sdb of=disk.dd bs=4M conv=noerror,sync
raw copy from a read-only attached drive (Linux)
ewfinfo disk.E01
show case metadata of an E01 image
ewfverify disk.E01
verify an E01 image against its stored hash

sleuth kit

mmls disk.dd
partition table with sector offsets
fls -r -o 2048 disk.dd
recursive file list; deleted entries marked with *
icat -o 2048 disk.dd 4417
extract the file with inode 4417
istat -o 2048 disk.dd 4417
metadata and timestamps for one inode
tsk_recover -o 2048 disk.dd out/
recover deleted files into out/
fsstat -o 2048 disk.dd
filesystem type, cluster size, serial

autopsy views

Deleted Files
file-table entries flagged deleted
Data Artifacts
browser, USB, recent docs, programs, downloads
Timeline
every timestamp on one axis
Hash Lookup
compare against known-good and known-bad sets
Extension Mismatch
name says .jpg, signature says .zip

terms

E01
EnCase image format with compression, hashes and case metadata
MFT
NTFS master file table, one record per file
MACB
modified, accessed, changed, born timestamps
Unallocated space
not owned by any file; may hold deleted data
File carving
rebuilding files from signatures, ignoring the file table
Chain of custody
log of who handled the evidence
