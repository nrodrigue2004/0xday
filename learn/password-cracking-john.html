Password security is mostly about how passwords are stored. Learn what hashes are, how to tell hash formats apart, and why salts and slow algorithms matter, then audit a server's password storage like a defender.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

Systems shouldn't store your password itself. They store a hash: the output of a one-way function. At login they hash what you typed and compare the two. The same input always produces the same hash, and a tiny change produces a completely different one:

$ echo -n "correct horse" | sha256sum
$ echo -n "correct horsf" | sha256sum

Tools like John the Ripper and hashcat are used by pentesters and auditors to test whether stored hashes would hold up against guessing. Defenders care about the result: *how hard would these hashes be to guess?*

A long, unique passphrase plus MFA beats any complexity rule. Length matters far more than symbols.

Passwords are never stored (when done right)

A good system stores a hash: a one-way fingerprint of the password. At login it hashes what you typed and compares. Nobody, including admins, should be able to read your password. An attacker who steals the hash file can't "reverse" it, but they can guess: hash many candidate passwords and see if any match. That guessing is cracking, and the speed depends on the algorithm.

Only on systems you own

Cracking is an audit tool: test your own lab accounts, a CTF, or an authorized penetration test. Cracking real people's leaked hashes or other organizations' data is not practice, it is a crime.

02 mid // how it's actually used

Reading hash formats

On Linux, /etc/shadow stores hashes as $id$salt$hash. The id tells you the algorithm:

  • $1$ MD5-crypt (old, fast, weak)
  • $5$ SHA-256-crypt, $6$ SHA-512-crypt (salted, many rounds)
  • $y$ yescrypt (modern default on Debian/Ubuntu), $2b$ bcrypt
  • ! or * means the account can't log in with a password
$ cut -d: -f1,2 ~/audit/shadow
$ cut -d: -f2 ~/audit/shadow | cut -c1-3 | sort | uniq -c

On Windows, local and domain passwords are stored as NT hashes (unsalted MD4), which is why protecting the SAM and NTDS.dit files matters so much.

Cracking modes

  • Wordlist: try known passwords (rockyou.txt has 14 million real leaked ones).
  • Rules: mutate each word (add digits, capitalize, leetspeak), which turns summer into Summer2026!.
  • Incremental / brute force: try every combination up to a length. Only practical for short passwords.
  • Mask: pattern-based brute force, like ?u?l?l?l?l?d?d for one capital, four lowercase, two digits.
  • Hybrid: wordlist plus mask appended.

Workflow with John

unshadow passwd shadow > hashes.txt
john --wordlist=/usr/share/wordlists/rockyou.txt hashes.txt
john --show hashes.txt

If John cannot tell the format, specify it: --format=sha512crypt. Tools like zip2john, ssh2john and office2john extract a hash from a file so it can be cracked. hashid or hash-identifier guesses the type from its look.

03 complex // what the pros do

Why salts and slow hashes

  • A salt is a random value stored next to each hash and mixed into it. Two users with the same password get different hashes, and precomputed lookup tables (rainbow tables) become useless
  • A slow algorithm (bcrypt, scrypt, yescrypt, Argon2, PBKDF2 with many iterations) makes every single guess expensive. A fast hash like plain MD5 or SHA-256 is the wrong tool for passwords, because fast is exactly what an attacker wants

What an audit recommends

  • Migrate legacy formats: users get the new algorithm the next time they log in
  • Lock or remove accounts that don't need a password at all
  • Enforce length (14+), block known-breached passwords (NIST SP 800-63B), add MFA
  • Monitor for the access that would let someone steal hashes in the first place
$ grep -E "^[^:]+:[^!*]" ~/audit/shadow | cut -d: -f1

Speed by algorithm

On the same GPU, MD5 and NTLM are tested at billions per second, SHA-256 at hundreds of millions, while bcrypt, scrypt and Argon2 manage thousands because they were designed to be slow and memory-heavy. That gap is why how a password is stored matters as much as the password itself. A salt makes identical passwords hash differently, defeating precomputed tables and forcing the attacker to crack each hash separately.

Online attacks versus offline

Offline cracking (stolen hash file) has no limits except compute. Online attacks (guessing against a live login) can be slowed by lockouts, rate limits and MFA. Spraying one password across many accounts evades per-account lockouts, so also alert on many failures from one source and on failures across many users.

What to recommend

Length beats complexity: a 16-plus character passphrase, a password manager to generate unique passwords, MFA everywhere (security keys best), screening new passwords against known-breached lists (Have I Been Pwned), storing with Argon2id or bcrypt with a unique salt, and no forced rotation without evidence of compromise (NIST guidance).
