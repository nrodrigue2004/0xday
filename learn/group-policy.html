Group Policy is how one admin configures ten thousand Windows machines. Learn where GPOs link, the LSDOU order that decides who wins, and how to troubleshoot with gpresult, then find why a security setting isn't applying.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

A Group Policy Object (GPO) is a bundle of settings (password rules, firewall, drive mappings, software, desktop restrictions) that Active Directory pushes to computers and users. You create a GPO once and link it to a site, the domain, or an OU, and every machine or user in that scope gets it.

  • Computer Configuration applies at boot to the machine, whoever logs in
  • User Configuration applies at logon to the user, wherever they log in
  • Machines refresh policy about every 90 minutes; gpupdate /force does it now
$ cat ~/gpo/links.txt

The idea in one picture

A Group Policy Object (GPO) is a bundle of settings. You link it to a domain, a site or an OU, and every computer or user inside that container receives the settings automatically at startup, logon and every 90 minutes or so. Settings are split into Computer Configuration (applies to the machine) and User Configuration (follows the person).

Typical things GPOs do: map network drives, set the password policy, install software, push printers, block USB storage, set the desktop wallpaper, turn on the firewall, and configure Windows Update.

02 mid // how it's actually used

LSDOU: who wins

When GPOs conflict, they're applied in order Local, Site, Domain, OU (parent OU first, then child OU). Each later one overwrites earlier ones, so the closest OU wins. Two exceptions:

  • Enforced on a link makes that GPO win over everything below it
  • Block Inheritance on an OU stops parent GPOs from applying (except enforced ones)

Within one container, GPOs with a lower link order number win.

$ grep -i "lockout\|password" ~/gpo/settings.txt

Troubleshooting with gpresult

gpresult /r (summary) or gpresult /h report.html shows which GPOs applied, which were filtered out and why (security filtering, WMI filters, disabled links):

$ gpresult /r

Tools you will use

  • Group Policy Management Console (GPMC): create, link, back up and review GPOs.
  • gpupdate /force on a client to refresh now; gpresult /r or gpresult /h report.html to see what applied and why.
  • Group Policy Modeling and Results inside GPMC to predict or confirm effects.
  • Event Viewer → Applications and Services → Microsoft → Windows → GroupPolicy for errors.

Filtering and targeting

Security filtering decides which users or computers a GPO applies to (default: Authenticated Users). WMI filters restrict by hardware or OS. Loopback processing applies user settings based on the computer, useful for kiosks and labs. Enforced stops lower levels from overriding and Block Inheritance stops higher ones, use both sparingly because they make troubleshooting painful.

Preferences vs policies

Policies are enforced and grayed out for the user; Preferences set a value once and let the user change it (drive maps, shortcuts, registry values). Preferences used to store passwords in XML in SYSVOL, encrypted with a key Microsoft published, which is why that feature was removed and why old cpassword entries are a finding.

03 complex // what the pros do

Security baselines through GPO

Most Windows hardening is GPO: account lockout and password length, disabling LLMNR and NetBIOS, SMB signing, restricting who can log on locally, Windows Firewall rules, LAPS, AppLocker/WDAC, PowerShell logging (script block logging, event 4104). Microsoft's Security Compliance Toolkit ships ready-made baseline GPOs.

One important exception: domain password and lockout policy only works from a GPO linked at the domain level (for domain accounts). The same settings in an OU GPO only affect local accounts on those machines. Different policies per group need Fine-Grained Password Policies.

Attack surface

GPOs are also an attack path: anyone who can edit a GPO linked to an OU can run code on every machine in it. Old Group Policy Preferences stored passwords (cpassword) in SYSVOL with a published key, which is why that feature was removed and why SYSVOL is worth auditing.

$ grep -ri "cpassword" ~/gpo/sysvol

Change management for GPOs

Never edit the Default Domain Policy beyond password and Kerberos settings. Create new, well-named GPOs (SEC - Workstation Baseline, USR - Drive Maps). Test on a pilot OU first, back up before changes (Backup-GPO), and document each GPO's purpose. Keep the number of GPOs applied to a machine small, since every one adds logon time.

Troubleshooting order

  1. Is the computer in the OU you think? (Get-ADComputer)
  2. Is the GPO linked and enabled there? Is the link order right?
  3. Security filtering and WMI filters: does the object pass?
  4. Replication: is SYSVOL the same on all DCs?
  5. Client side: DNS resolves the domain, time is in sync (Kerberos), gpresult shows it as applied or denied.
