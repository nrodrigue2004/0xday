A web app is a browser, an API and a database passing JSON back and forth. Learn HTTP, REST, React and MongoDB from a security angle, then decode session tokens to catch a forged admin request.

1simple2mid3complex4hands-on

01 simple // the idea in plain words

A modern web app has three parts:

  • Frontend: runs in the browser (React, TypeScript). Draws the page, sends requests
  • Backend / API: runs on a server (Node.js + Express). Checks who you are, applies the rules, talks to the database
  • Database: stores the data (MongoDB keeps JSON-like documents)

They talk over HTTP. A request has a method (GET read, POST create, PUT/PATCH update, DELETE), a path, headers and maybe a body. The response has a status code: 2xx OK, 3xx redirect, 4xx your fault (401 not logged in, 403 not allowed, 404 not found), 5xx server's fault.

$ cat ~/api/request.http
$ curl -s https://api.shop.local/products/7

Never trust the frontend. Anyone can skip your React app and send requests straight to the API with curl.

02 mid // how it's actually used

REST and JSON

A REST API maps resources to URLs: GET /api/orders lists, GET /api/orders/12 reads one, POST /api/orders creates. Data travels as JSON.

Sessions and JWTs

After login, the API gives the client a token to send with every request (Authorization: Bearer <token>). A JWT is three base64url parts joined by dots: header.payload.signature. The payload is readable by anyone, only the signature protects it from being changed:

$ cat ~/api/token.txt
$ cut -d. -f2 ~/api/token.txt | base64 -d

React's safety net

React escapes values you render, which blocks most XSS by default. It's bypassed by dangerouslySetInnerHTML, by putting user input into href (javascript: URLs), and by server-side templates that don't escape.

03 complex // what the pros do

The OWASP Top 10, as it shows up in this stack

  • Broken access control: the API checks you're logged in but not that order 12 is *yours* (IDOR). Every endpoint must check ownership and role on the server
  • Injection: MongoDB has NoSQL injection: sending {"password": {"$ne": null}} instead of a string makes the query match any password. Validate types (zod, joi) and never pass raw request bodies into queries
  • Cryptographic failures / broken auth: JWTs signed with a weak secret, or a server that accepts "alg": "none" (no signature at all)
  • Security misconfiguration: verbose error stack traces, open CORS (Access-Control-Allow-Origin: * with credentials), MongoDB exposed to the internet without auth
$ cut -d. -f1 ~/api/token.txt | base64 -d
$ cat ~/api/login-attempts.log

Defense in depth

Server-side validation, parameterized queries, HttpOnly + Secure + SameSite cookies, a Content Security Policy, rate limiting on login, and logging of every authorization failure.

04 hands-on // sandbox shell

The shop's API logs every request with its JWT. Someone got admin access to /api/admin/users without an admin account.

The four admin requests are in ~/api/admin-requests.log. Decode each token's header and payload. One token was forged: it claims to be admin but has no valid signature at all, and the server accepted it.

Submit the request ID of the forged request, e.g. submit req-1000.
