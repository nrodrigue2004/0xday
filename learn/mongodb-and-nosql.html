01 simple // the idea in plain words

A relational database (MySQL, SQLite) stores rows in tables with a fixed set of columns. MongoDB stores documents: JSON-like objects that can nest and differ from each other. Documents live in collections, collections live in a database.

{ "_id": 1, "name": "Ava", "roles": ["admin", "dev"], "address": { "city": "Baton Rouge" } }

Rough translation: table = collection, row = document, column = field, JOIN = $lookup (or just embed the data).

When MongoDB fits

Data that is naturally one nested object (a user with their settings and posts), a schema that changes often, or a quick prototype. When data is highly connected and needs strict rules and many joins (money, inventory), a relational database is usually safer. A social feed (posts with embedded comments and likes) suits MongoDB; a multi-branch supermarket where stock and sales must always add up suits a relational schema like the Supermarket DBMS.

02 mid // how it's actually used

CRUD in the shell (mongosh)

  • insert: db.users.insertOne({ name: "Ava", age: 21 })
  • read: db.users.find({ age: { $gt: 18 } }), db.users.findOne({ name: "Ava" })
  • update: db.users.updateOne({ name: "Ava" }, { $set: { age: 22 } })
  • delete: db.users.deleteOne({ name: "Ava" })

Query operators

Operators start with $: comparison ($eq $ne $gt $gte $lt $in), logic ($and $or $not), arrays ($all $elemMatch), and updates ($set $inc $push $pull). A projection picks fields: find({}, { name: 1, _id: 0 }).

Indexes

Without an index a query scans every document. db.users.createIndex({ email: 1 }, { unique: true }) makes lookups fast and enforces uniqueness. Use explain() and look for IXSCAN (index) versus COLLSCAN (full scan).

Schema design: embed or reference

Embed data that is read together and belongs to one parent (comments inside a post, up to a sane size). Reference (store the other document's _id) when data is shared, large or grows without limit. Documents have a 16 MB cap.

Aggregation pipeline

Stages run in order, each feeding the next:

db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$customer", total: { $sum: "$amount" } } },
  { $sort: { total: -1 } }, { $limit: 5 }
])

From code

In Node with Mongoose you define a schema and model (User.find({ email })). In Spring Boot it is a MongoRepository. Either way, the driver turns your objects into BSON documents.

03 complex // what the pros do

NoSQL injection

No SQL strings, but you can still inject. If the server passes the request body straight into a query, an attacker sends operators instead of values:

{ "user": "admin", "pass": { "$ne": "" } }

becomes find({ user: "admin", pass: { $ne: "" } }): "password is not empty", so any password matches. $gt, $regex and $where do similar damage. Defenses: validate that fields are plain strings, strip keys starting with $ (or use express-mongo-sanitize), set the schema type (String), never use $where with user input, and never store plain passwords (hash with bcrypt/argon2).

Securing a MongoDB server

Older installs listened on all interfaces with no authentication, and thousands got wiped and held for ransom. Check: bindIp is localhost or a private interface, authentication is enabled with a least-privilege user per app, TLS between app and database, firewall port 27017, and regular backups (mongodump) you've actually tested restoring.

Transactions and consistency

Single-document writes are atomic, which is why embedding works so well. Multi-document transactions exist (replica set required) but cost performance. If a design needs them everywhere, it probably wants a relational database.

Replication and sharding

A replica set (one primary, secondaries) gives failover and read scaling. Sharding splits a huge collection across servers by a shard key. Pick a key with good spread: a monotonically increasing key puts all new writes on one shard.

Reading the logs as a defender

Log failed logins with the *shape* of the request, not just the username. A body with $ne, $gt, $regex or $where in a login route is an attack, successful if the response is a session token.

04 hands-on // sandbox shell

The login endpoint POST /api/login passes the request body straight to User.findOne(...). Its log, login.log, shows each attempt's source IP, the JSON body and the HTTP status (200 = logged in, 401 = refused). All addresses are from the documentation range and the data is fictional.

Most entries are normal. One request logged in as admin without knowing the password, by sending an operator instead of a password string.
