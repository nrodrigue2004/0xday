A memory image is a frozen copy of RAM: running processes, network connections and secrets that never touch the disk. Learn what Volatility 3 reads out of it, then find the process that doesn't belong.

01 simple // the idea in plain words

Memory forensics means analyzing a copy of a computer's RAM. Disk forensics shows what was stored; memory shows what was running: every process, open network connection, loaded DLL and sometimes passwords or decrypted malware that only exist in memory.

Volatility is the standard open-source framework for it. You point it at an image file (mem.raw) and run a plugin that walks one kernel structure and prints a table.

$ vol -f mem.raw windows.info
$ vol -f mem.raw windows.pslist

Why capture RAM first

RAM is lost at power-off, so in an incident it comes before the disk image (order of volatility). Typical tools: WinPmem, DumpIt, FTK Imager's "Capture Memory", or a hypervisor snapshot (.vmem file). Hash the image and write the time down.

The first three plugins

  • windows.info: confirms the OS build, so the right symbols load
  • windows.pslist / windows.pstree: what was running, and who started it
  • windows.netscan: which connections and listeners existed

02 mid // how it's actually used

Process list vs pstree

pslist reads the kernel's list of processes. pstree draws the same data as parent and child. Learn the normal Windows shape, because malware breaks it:

  • System (PID 4) starts smss.exe; wininit.exe starts services.exe, lsass.exe
  • services.exe starts every svchost.exe (with -k <group> in the command line)
  • explorer.exe starts what the user launches
  • there is exactly one lsass.exe, and it has no children

A svchost.exe whose parent is explorer.exe or winword.exe, or a name like svch0st.exe, is a classic tell.

Hidden processes: psscan

Rootkits unlink a process from the list. windows.psscan scans raw memory for process structures instead of following the list. A process that appears in psscan but not pslist is hiding (or has already exited).

Network, command lines and DLLs

  • windows.netscan: protocol, local and foreign address, state, owning PID
  • windows.cmdline: the exact command line each process started with
  • windows.dlllist --pid 4172: modules loaded by one process
  • windows.handles --pid 4172: files, registry keys and mutexes it holds open

Injection and code hunting

windows.malfind lists memory regions that are executable and not backed by a file on disk, which is how injected shellcode usually looks. Dump the region, hash it, then analyze it like any sample (see the malware analysis guide).

$ vol -f mem.raw windows.malfind --pid 4172 --dump

Persistence and credentials

windows.registry.hivelist and windows.registry.printkey --key "Software\Microsoft\Windows\CurrentVersion\Run" show autoruns. windows.hashdump and windows.lsadump pull credentials, which only belongs in an authorized investigation.

03 complex // what the pros do

Method: from a suspicion to a timeline

  1. windows.info, hash the image, note the capture time
  2. pstree: look for the wrong parent, wrong path, wrong user
  3. cmdline and dlllist for each suspect; compare the on-disk path with where it really runs from
  4. netscan: tie the PID to a remote address, then look that IP up in proxy or firewall logs
  5. malfind for injection, psscan for hiding
  6. dump the process or region (windows.pslist --pid N --dump), hash it, submit for analysis
  7. write the timeline using process create times, then pair it with disk and network evidence

Symbols and versions

Volatility 3 needs symbol tables for the exact kernel build, and downloads them for Windows. If a plugin returns nothing, confirm windows.info works first. Volatility 2 used profiles (--profile=Win7SP1x64) and different plugin names (pslist, netscan, malfind); old tutorials use those.

Linux and macOS images

Volatility 3 has linux.pslist, linux.bash, linux.lsof and matching macOS plugins, but needs a symbol file built for that exact kernel. Collect it in the same step as the image (dwarf2json against the kernel's debug info).

What memory cannot tell you

A clean pslist does not mean a clean machine: the image is one moment in time, kernel rootkits can lie to plugins that trust kernel data, and a process that already exited leaves only fragments. Say what the image shows, and what it can't.

Writing it up

Report the image name and SHA-256, plugin and version, the finding with PID, parent, path, command line and connection, and the evidence you dumped. Keep conclusions separate from guesses.

ref reference // commands and terms, also on the cheatsheet

vol3 basics

vol -f mem.raw windows.info
OS build, architecture, kernel base, capture time
vol -f mem.raw -h
list every available plugin
vol -f mem.raw -r csv windows.pslist
export a table as CSV
vol -f mem.raw -o out/ windows.pslist --pid 4172 --dump
dump a process's executable into out/

vol3 plugins

windows.pslist
processes from the kernel's list, with PPID and create time
windows.pstree
same data drawn as a parent/child tree
windows.psscan
pool scan, finds hidden and exited processes
windows.cmdline
command line each process started with
windows.netscan
TCP/UDP connections and listeners with owning PID
windows.dlllist
DLLs loaded by a process
windows.handles
open files, keys, mutexes per process
windows.malfind
executable memory with no file behind it (injection)
windows.filescan
file objects found in memory
windows.registry.printkey
read a registry key from the image
windows.svcscan
Windows services, including unusual binary paths

reading the output

PPID mismatch
svchost not started by services.exe, or Office spawning cmd
Path mismatch
system name running from \Users, \Temp or \ProgramData
Two lsass.exe
one is fake; the real one is started by wininit.exe
psscan only
hidden or terminated process
RWX region
injected code candidate from malfind
