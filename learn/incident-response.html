When something gets in, a plan beats panic. Learn the incident response life cycle and live triage on a Linux box, then find how an attacker made sure they'd get back in.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

An incident is anything that threatens the confidentiality, integrity or availability of systems or data: malware, a stolen account, a data leak. Incident response (IR) is the plan for handling one. The CompTIA / NIST-style life cycle:

  1. Preparation: tools, playbooks, contacts, logging, before anything happens
  2. Detection & analysis: notice it, confirm it's real, scope it
  3. Containment: stop the spread (isolate the host, disable the account)
  4. Eradication: remove the cause (malware, backdoors, the vulnerability)
  5. Recovery: restore and monitor
  6. Lessons learned: what to do better next time

The sandbox is a compromised web server. First triage question: what's running right now?

$ cat ~/triage/ps.txt

Contain before you clean. If you delete the malware first, you lose the evidence and the attacker learns you've noticed.

The lifecycle

NIST describes four phases, SANS six; they say the same thing: Prepare (tools, contacts, logging, playbooks), Detect and analyze (is it real, how bad), Contain (stop the spread, short term then long term), Eradicate and recover (remove the cause, restore from known-good), and Lessons learned (what do we change). Most of the real skill is calm, ordered work under pressure.

First five minutes

Do not power off a compromised machine (you lose memory evidence), do not delete anything, write down what you see and the time, tell the right person, and isolate the machine from the network if it is spreading (unplug the cable or disable the switch port, rather than shutting down).

02 mid // how it's actually used

Live triage: processes, connections, users

Look for processes running from odd places (/tmp, /dev/shm, hidden directories), as the wrong user, or with no parent you'd expect:

$ grep -E "/tmp|/dev/shm|/\." ~/triage/ps.txt

Then network connections. Map each established connection to a process (PID) and ask whether it should exist:

$ grep ESTAB ~/triage/netstat.txt

And logins: who's logged in now and recently, and from where:

$ cat ~/triage/last.txt

On a live system you'd run ps auxf, ss -tulpan and last -a yourself. Save the output to files with timestamps, because the state changes while you look.

Evidence handling

Keep a log: who, what, when, where. Collect the most volatile data first (order of volatility: CPU and memory, network connections, running processes, disk, logs, backups). Work on copies, hash the originals (sha256sum), and use write blockers for disks. A chain of custody record shows who held the evidence and when, which matters if it ever reaches court.

Severity and communication

Rate by impact (data involved, systems affected, business function) and spread. Decide who needs to know: IT, management, legal, HR, and possibly customers or regulators. Use a separate channel in case email is compromised, and keep updates short and factual with times.

Containment options

Network isolation, disable the account, block the IOC (IP, domain, hash) at firewall and DNS, revoke tokens and sessions, and snapshot the VM before changing it. Pick the least destructive action that actually stops the damage, and note every action so you can undo it later.

03 complex // what the pros do

Persistence: how attackers come back

Getting in is hard; staying in is the goal. Every IR has to find and remove persistence, or the attacker returns after you "clean up". Common places on Linux:

  • cron: /etc/crontab, /etc/cron.d/*, /var/spool/cron/crontabs/<user>
  • systemd services/timers: new units in /etc/systemd/system
  • SSH keys: an extra line in ~/.ssh/authorized_keys
  • shell startup: .bashrc, .profile, /etc/profile.d/
  • new accounts, especially with UID 0, and sudoers changes

On Windows: Run keys in the registry, scheduled tasks, services, WMI subscriptions, startup folders.

$ ls -la ~/triage/etc/cron.d
$ cat ~/triage/etc/crontab

Scoping

One compromised host is rarely the whole story. Take every IOC (indicator of compromise) you find, such as IPs, domains, file hashes and usernames, and search for them across the environment, in the SIEM, EDR and other hosts' logs.

Playbooks worth having

Phishing (retrieve the message, find all recipients, check who clicked, reset and revoke), ransomware (isolate, identify the strain, check backups, do not pay without legal advice), compromised account (reset, revoke sessions, review mailbox rules and OAuth grants, check logins), malware on a host (isolate, image, analyze, reimage), and data leak (scope what left, preserve logs, notify as required).

Root cause and the report

After recovery, write a blameless timeline: initial access, execution, persistence, lateral movement, impact, detection time, containment time. List what worked, what failed and the specific changes (a rule, a patch, a policy) with owners and dates. Measure mean time to detect and to respond so improvement is visible.

Indicators and frameworks

Map findings to MITRE ATT&CK techniques, record IOCs (hashes, IPs, domains, file paths, registry keys), and share them with your SIEM and blocklists. The IR plan should be tested in a tabletop exercise before it is needed.
