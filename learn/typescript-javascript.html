The language of the browser, and of a lot of malware droppers. Learn JavaScript from first values to closures, run real code in the sandbox, then decode an obfuscated payload.

01 simple // the idea in plain words

JavaScript runs in every browser and, through Node.js, on servers. A program is a list of statements. You store values in variables with const (can't be reassigned) or let (can), and print them with console.log.

The sandbox runs real JavaScript with node -e '<code>':

$ node -e 'const name = "0xDay"; console.log("hello, " + name)'
$ node -e 'console.log(7 * 6, typeof 42, typeof "42")'

A function is a reusable block that takes inputs and returns an output:

$ node -e 'function double(n) { return n * 2 } console.log(double(21))'

TypeScript is JavaScript plus type labels (function double(n: number): number). The compiler checks the types and then strips them out, so what actually runs is plain JavaScript.

JavaScript in one page

JavaScript runs in browsers and on servers (Node.js). let and const declare variables (use const unless it changes), functions can be written as function f(a) {} or const f = a => a * 2, and objects { name: "nate", role: "analyst" } and arrays [1, 2, 3] carry most data. Strings can use template literals (backticks around the text, with ${name} placeholders). JavaScript is loosely typed and coerces: "5" + 1 is "51" but "5" - 1 is 4, and == converts types while === does not, so always use ===.

TypeScript is JavaScript plus types

interface User { id: number; name: string; admin?: boolean }
function greet(u: User): string { return `hi ${u.name}`; }

The compiler (tsc) checks the types and then strips them, producing plain JavaScript. Types catch mistakes like passing a string where a number is expected, but they exist only at compile time, so data from the outside world (network, user input) still needs runtime validation.

02 mid // how it's actually used

Most real JavaScript is moving data around: arrays (lists), objects (key/value records) and JSON (objects as text, the format every web API speaks).

The three array methods you'll see everywhere:

  • map transforms every item
  • filter keeps items that pass a test
  • reduce folds the list into one value

ports.js in the sandbox holds a fake scan result. Read it, then run it:

$ cat ports.js
$ node ports.js

Arrow functions (p => p.open) are just short functions. Template strings use backticks and ${}:

$ node -e 'const hosts = ["10.0.0.5", "10.0.0.9"]; hosts.map((h, i) => console.log(`${i}: ${h}`))'
$ node -e 'console.log(JSON.stringify({ user: "nathan", admin: false }))'

Async: promises and async/await

async function getUser(id) {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error(res.status);
  return res.json();
}

fetch returns a promise; await pauses the function until it settles. Errors become exceptions you catch with try/catch. Promise.all([...]) runs things in parallel. The event loop is single threaded, so a long loop freezes everything.

Arrays and objects you use daily

map, filter, reduce, find, some, includes, spread ([...a, ...b], {...obj, x: 1}), destructuring (const { id, name } = user), optional chaining (user?.profile?.email) and nullish coalescing (value ?? "default").

The browser and the DOM

document.querySelector, addEventListener, textContent (safe) versus innerHTML (can execute attacker markup), localStorage, and the Network tab in developer tools. View Source and DevTools are how you read what any page is really doing.

03 complex // what the pros do

1. Strings are just numbers

Every character has a numeric code. "A".charCodeAt(0) is 65, and String.fromCharCode(65) is "A". That's the basis of almost every obfuscation trick: shift, XOR or encode the codes so the text doesn't look like a URL anymore.

$ node -e 'console.log([..."hi"].map(c => c.charCodeAt(0)))'
$ node -e 'console.log(String.fromCharCode(104, 105))'

2. XOR and base64

XOR (^) flips bits with a key, and XOR-ing twice with the same key gives you the original back: (c ^ k) ^ k === c. Base64 (btoa / atob) turns bytes into safe printable text. Droppers often stack them: XOR the URL, then base64 it.

$ node -e 'const k = 0x2a; const x = 104 ^ k; console.log(x, x ^ k)'
$ node -e 'console.log(btoa("hi"), atob("aGk="))'

3. Closures, async and why attackers love eval

  • A closure is a function that remembers variables from where it was created, the trick behind private state and module patterns
  • async/await lets code wait on network calls without freezing the page
  • eval(string) runs a string as code, so a dropper only needs to *decode* a string and eval it. As an analyst you do the opposite: swap eval for console.log and read what it would have run

Never run an unknown script to "see what it does". Copy only the decoding logic, and print instead of executing.

Node and npm

npm init, npm install pkg, npm audit, npx tool. package.json lists dependencies and scripts; package-lock.json pins exact versions and should be committed. Supply chain attacks hit npm often (typosquatting, malicious updates, install scripts), so review new dependencies, prefer fewer of them, and use npm ci in builds.

Security essentials

XSS (escape output, never put untrusted data in innerHTML, use a Content-Security-Policy), prototype pollution (be careful merging untrusted objects), eval and new Function on input, regex denial of service, insecure Math.random for tokens (use crypto.getRandomValues), and trusting client-side checks (always re-validate on the server).

Reading obfuscated JavaScript

Malicious scripts hide strings with String.fromCharCode, base64 (atob), hex escapes and XOR loops, then run the result with eval. Replace the final eval with console.log in a safe environment (Node in a VM) to see the real code, or run a beautifier first. The lab in this guide walks through that idea.
