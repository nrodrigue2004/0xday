An IDS is a tripwire for network traffic. Learn how Snort rules are built, read alerts, and write the rule that would have caught an attack.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

An IDS (intrusion detection system) watches network traffic and raises an alert when a packet matches a pattern of known-bad activity. An IPS does the same but sits inline and can drop the packet. Snort and Suricata are the classic open-source ones, and both use the same rule language.

A rule has a header (what traffic to look at) and options (what to look for):

$ cat ~/rules/local.rules

Read the first rule as a sentence: *alert* on *tcp* traffic from *any* source to the web server on port *80*, when the payload *contains* /etc/passwd, with this message and ID number (sid).

alert only logs. In IPS mode, drop blocks the packet and logs it.

The two modes

An IDS only watches and alerts (it sits on a copy of the traffic, like a security camera). An IPS sits inline and can also drop packets (a guard at the door). Start in alert-only mode, tune, and only then consider blocking, because a false positive in IPS mode breaks real traffic.

Anatomy of a rule

alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (msg:"WEB admin probe"; flow:to_server,established; content:"/admin"; http_uri; sid:1000001; rev:1;)

Header: action, protocol, source, source port, direction, destination, destination port. Options in parentheses: msg is the alert text, content is the bytes to find, flow limits to a connection state and direction, sid is the unique ID (use 1,000,000 and up for your own rules) and rev is the revision.

02 mid // how it's actually used

Reading alerts

Snort's "fast" alert format puts everything on one line: time, [gid:sid:rev], message, classification, priority, protocol and the source and destination:

$ head -3 ~/logs/alert.fast
$ grep -o "\[1:[0-9]*:[0-9]*\] [^[]*" ~/logs/alert.fast | sort | uniq -c | sort -rn

Rule options you'll see most

  • content:"..." match bytes in the payload, nocase makes it case-insensitive
  • http_uri, http_header restrict a match to one part of the HTTP request
  • pcre:"/.../" a regular expression, for when a fixed string isn't enough
  • flow:to_server,established only match after the TCP handshake, client to server
  • threshold / detection_filter only alert after N hits in T seconds (brute force rules)
$ grep "detection_filter" ~/rules/local.rules

More rule options

  • pcre:"/regex/i" matches a regular expression, powerful but slower than content
  • nocase ignores case, offset/depth/within/distance constrain where in the payload to look
  • threshold: type both, track by_src, count 5, seconds 60 fires only after five hits from one source in a minute
  • classtype:attempted-admin and priority put the alert in a category
  • reference:cve,2021-44228 links to the vulnerability
  • Fast pattern matching: put the most distinctive content first, because the engine searches that string and only then checks the rest

Variables and files

HOME_NET must be set to your real internal ranges, or half the rules never match. Rules live in /etc/snort/rules/ (or /etc/suricata/rules/), local rules go in local.rules, and snort -T -c snort.conf tests the config before you restart. Output alerts to alert_fast for reading and to unified2/JSON for tools.

03 complex // what the pros do

False positives and tuning

A rule that fires on legitimate traffic trains analysts to ignore it. Tuning means making the match more specific (add flow, limit to http_uri, add a second content), adding thresholds, or suppressing a rule for one known-good host. Count which rules fire most and from where before deciding:

$ grep "1000003" ~/logs/alert.fast | grep -o "[0-9.]*:[0-9]* ->" | sort | uniq -c

Evasion, and why it's hard to win

Attackers dodge signatures with encoding (%2e%2e%2f for ../), fragmentation, TLS (the IDS can't read encrypted payloads without decryption), and changing their tools until the bytes don't match. That's why modern IDS pair signatures with protocol anomaly detection and why Snort has preprocessors (Snort 3: inspectors) that normalize HTTP before rules run.

Placement

An IDS on a SPAN/tap port sees a copy of traffic (passive, can't block). An IPS inline must be fast and must decide what happens when it fails: fail-open (traffic flows unchecked) or fail-closed (the network goes down).

Snort vs Suricata

Both read the same style of rules. Suricata is multi-threaded, understands more protocols natively and writes EVE JSON that feeds straight into Security Onion. Snort 3 is also multi-threaded and has a new rule syntax. Learn one and the other is a day of reading.

Tuning workflow

  1. Run alert-only for a week on a normal network.
  2. Sort alerts by count; the top five are usually noise.
  3. For each: is the behavior legitimate? If yes, suppress that source or destination, or threshold it. Do not disable the whole rule if one host is the problem.
  4. Keep a record of every suppression with a reason.
  5. Test new rules with a replayed PCAP (snort -r capture.pcap -c snort.conf -A alert_fast) before they go live.

What network IDS cannot see

Encrypted payloads (you only see metadata unless you decrypt), traffic that never crosses your sensor (east-west on the same switch), and low-and-slow activity below your thresholds. Pair it with host logs.
