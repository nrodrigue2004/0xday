01 simple // the idea in plain words

Digital forensics is collecting and examining digital evidence so you can say, with proof, what happened: which files existed, who touched them, and when.

Two rules come before any analysis:

  • Don't change the evidence. Work on a copy (an *image*) made through a write blocker, never the original drive
  • Prove it's unchanged. Hash the image when you make it and again when you're done. Same hash, same data
$ cat ~/case/chain-of-custody.txt
$ sha256sum ~/case/evidence/notes.txt

The chain of custody records every person who handled the evidence, when, and why. Without it, evidence can be thrown out.

The ground rules

  1. Preserve: never work on the original. Make a forensic image with a write blocker, hash it (SHA-256), and work from a copy.
  2. Document: record every step, tool and time. Another examiner should be able to repeat your work and get the same result.
  3. Analyze: look at files, deleted data, logs, browser history, USB history, user activity and memory.
  4. Report: state facts, separate them from opinion, and say what you could not determine.

Digital evidence is easy to change by accident (just booting a disk alters timestamps), so the process matters as much as the findings.

02 mid // how it's actually used

File names lie, file signatures don't

A file's extension is just part of its name. What it actually is lives in its first few bytes, the magic number (file signature):

  • FF D8 FF JPEG, 89 50 4E 47 (.PNG) PNG, 25 50 44 46 (%PDF) PDF
  • 50 4B 03 04 (PK..) ZIP, which is also DOCX, XLSX and APK
  • 4D 5A (MZ) Windows executable

Look at the first bytes with xxd:

$ ls -l ~/case/evidence/photos
$ head -c 16 ~/case/evidence/photos/beach.jpg | xxd

strings

Even binary files carry readable text: paths, URLs, usernames, metadata. strings pulls out every run of printable characters:

$ strings ~/case/evidence/photos/beach.jpg | head

Where Windows keeps evidence

  • Registry hives (NTUSER.DAT, SYSTEM, SOFTWARE, SAM): user activity, USB devices, installed programs, autostart keys.
  • Prefetch (C:\Windows\Prefetch): which programs ran and when.
  • Event logs (.evtx): logons, service installs, PowerShell activity.
  • Recycle Bin, LNK files and Jump Lists: files a user opened or deleted.
  • Browser profiles: history, downloads, cookies, cache.
  • $MFT, $UsnJrnl: the file system's own record of creation, modification and deletion.
  • hiberfil.sys, pagefile.sys: slices of memory saved to disk.

Where Linux keeps evidence

/var/log/ logs, ~/.bash_history, /etc/passwd and /etc/shadow, cron entries, ~/.ssh/ (known_hosts shows where someone connected), /tmp and /dev/shm for dropped tools, package manager logs and the systemd journal.

Deleted does not mean gone

Deleting a file usually removes only the directory entry; the data stays until overwritten. File carving recovers files from raw bytes using header and footer signatures (foremost, photorec, scalpel). SSDs with TRIM and encrypted disks reduce what you can recover.

03 complex // what the pros do

Timelines

Filesystems record MAC times for every file: Modified (content changed), Accessed, Changed (metadata changed, on NTFS: $MFT entry), plus Born/created on many systems. Sorting every timestamp on the disk into one super timeline (tools: fls + mactime from The Sleuth Kit, plaso/log2timeline) shows the sequence of events:

$ sort ~/case/timeline.csv | tail -6

Attackers timestomp (fake the timestamps) to hide. On NTFS that leaves the $FILE_NAME timestamps different from $STANDARD_INFORMATION, and a creation time later than the modification time is a classic giveaway.

Where else evidence hides

  • Deleted files: deleting removes the pointer, not the data, until it's overwritten. Carving tools (PhotoRec, foremost, Autopsy) find files by their signatures in unallocated space
  • Slack space at the end of clusters, alternate data streams on NTFS, volume shadow copies
  • Memory: running processes, network connections and decrypted keys exist only in RAM. Capture it before pulling the plug (order of volatility: registers/cache, RAM, network state, disk, logs, backups) and analyze with Volatility
  • Windows artifacts: Prefetch (what ran), LNK files and Jump Lists (what was opened), Registry (USB devices, recent docs), browser history
$ grep -i usb ~/case/timeline.csv

Memory forensics

RAM holds what disk never shows: running processes, network connections, injected code, decrypted data and encryption keys. Capture it first (WinPmem, LiME on Linux, or a VM snapshot's memory file), then analyze with Volatility: list processes (windows.pslist, windows.pstree), compare with windows.psscan to spot hidden ones, check windows.netscan for connections, windows.malfind for injected code, and windows.cmdline for arguments.

Tools worth knowing

Autopsy / Sleuth Kit (disk analysis, timelines), FTK Imager (imaging), Volatility 3 (memory), Plaso / log2timeline (super-timelines), exiftool (metadata), Wireshark (network), Eric Zimmerman's tools (registry, prefetch, MFT parsers), KAPE (fast triage collection).

Timeline thinking

Merge timestamps from every source into one ordered list, then ask what happened just before and after the key event. Be careful with time zones, clock skew and the difference between created, modified and accessed times. Anti-forensics (timestomping, log clearing, secure delete) shows up as gaps and contradictions.
