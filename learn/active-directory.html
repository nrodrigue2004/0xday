Active Directory is the phone book and the keyring of a Windows network. Learn domains, OUs, users, groups and how permissions really flow, then find the account that's secretly a Domain Admin.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

In a company, hundreds of Windows machines and users need to trust the same logins. Active Directory Domain Services (AD DS) is the central database that makes that work. A server running it is a Domain Controller (DC). When you log into a work PC, the DC checks your password and tells the PC who you are.

The building blocks:

  • Domain: the security boundary, like corp.local
  • Users and computers: objects in the directory
  • Groups: collections of users, used to grant access ("Finance Share Readers")
  • OUs (organizational units): folders to organize objects and to target Group Policy
$ cat ~/ad/structure.txt
$ cat ~/ad/users.csv

Grant access to groups, not to individual users. When someone changes jobs, you move them between groups instead of hunting down every permission.

The cast of characters

  • Domain: a company's directory, such as corp.example.com. Everything inside trusts the same authority.
  • Domain controller (DC): the server that holds the directory and answers logins. Usually two or more.
  • Object: a user, computer, group or printer. Each has attributes (name, password hash, group membership).
  • OU (organizational unit): a folder you use to organize objects and to attach policy.
  • Forest and trust: a forest is one or more domains that share a schema; trusts let users from one domain use resources in another.
  • SID: the unique ID Windows actually uses to identify an account. Names are just labels.

When someone logs into a work PC with their company account, the PC asks a domain controller to verify the password, and the DC replies with proof of who they are and which groups they are in.

02 mid // how it's actually used

Groups inside groups

Groups can contain other groups (nesting). The recommended Microsoft pattern is AGDLP: put Accounts into Global groups (by role, like "Finance Staff"), put global groups into Domain Local groups (by resource, like "Finance Share RW"), and assign Permissions to the domain local group.

Nesting is powerful and easy to lose track of: a user's real access is the sum of every group they're in, directly or through nesting.

$ cat ~/ad/groups.txt
$ grep "Domain Admins" ~/ad/groups.txt

Authentication

Domain logins use Kerberos: the DC gives you a ticket-granting ticket (TGT) at logon, and you trade it for service tickets to reach file shares, SQL servers and so on. Older NTLM still shows up as a fallback and is weaker.

Everyday administration tasks

Resetting a password, unlocking an account, adding a user to a group, moving a laptop to the right OU, and disabling an account for a leaver are 90% of help-desk AD work. In Active Directory Users and Computers you do these with a right-click; in PowerShell they are one-liners (see the reference). Always disable and move a leaver rather than deleting, so you can recover the account and its SID.

Key protocols

  • DNS: AD depends on it. If a PC cannot find the DC through DNS, logins fail. Most AD outages are DNS problems.
  • LDAP (389/636): how clients query the directory.
  • Kerberos (88): ticket-based authentication; a user gets a ticket-granting ticket (TGT) at login, then service tickets as needed.
  • NTLM: the older challenge-response fallback, still around and still abused.
  • SMB (445): file shares and the SYSVOL folder that distributes Group Policy.

Account states you will see

Locked out (too many bad passwords, clears itself or an admin unlocks it), disabled (admin switched it off), expired (password or account date), and "must change password at next logon". Event IDs: 4624 logon, 4625 failed logon, 4740 lockout, 4720 account created, 4728/4732 added to a privileged group.

03 complex // what the pros do

Why attackers love AD

Owning AD means owning every machine that trusts it. Common paths, all of which are misconfigurations a defender can find first:

  • Nested group membership that quietly grants admin rights (BloodHound maps these paths as a graph)
  • Kerberoasting: service accounts with SPNs and weak passwords
  • AS-REP roasting: accounts with "Do not require Kerberos preauthentication"
  • Stale privileged accounts, shared admin passwords, and admins logging into workstations (leaving credentials in memory)

Defending it

  • Keep Domain Admins tiny and used only on DCs (the tiered admin model)
  • Separate admin accounts from daily-use accounts (nate vs adm.nate)
  • Audit privileged group membership recursively, on a schedule, and alert on changes (event IDs 4728/4732/4756 = member added to a security group)
  • Use LAPS for local admin passwords, gMSAs for service accounts, and disable NTLM where you can
$ grep -E "4728|4732|4756" ~/ad/security.evtx.txt

Attack paths worth being able to describe

  • Password spraying: one common password tried against many accounts, staying under the lockout threshold.
  • Kerberoasting: any user can request a service ticket for an account with an SPN, then crack it offline. Defense: long random passwords on service accounts, or managed service accounts.
  • Pass-the-hash: NTLM hashes can be used as passwords without cracking them. Defense: no local admin reuse (LAPS), restricted admin logons, credential guard.
  • DCSync: an account with replication rights asks a DC for everyone's hashes. Defense: tightly limit and alert on replication rights.
  • Golden ticket: stolen krbtgt hash lets an attacker forge tickets. Defense: reset krbtgt twice after a compromise.
  • Delegation and ACL abuse: a user with write access over a group or an account can take it over. Tools like BloodHound map these paths.

Tiering

Keep three tiers: domain controllers and identity (tier 0), servers (tier 1), workstations (tier 2). Admins for a higher tier never log into a lower one, because their credentials would be left in memory on a machine that is easier to compromise.
