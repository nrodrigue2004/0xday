~/ai/attacking-ai

How AI systems get attacked: prompt injection, data poisoning, leaks and agent abuse, and how to build so one bad document cannot hijack your tools.

1simple2mid3complex4hands-on

01 simple // the idea in plain words

AI systems are software with a new kind of weakness: they follow instructions written in ordinary language, and they cannot reliably tell whose instructions they are.

The big ones

  • Prompt injection. Hidden or planted text tells the model to do something other than what the user asked. "Ignore previous instructions" is the cartoon version. The realistic version is a web page, email or PDF that contains instructions meant for an AI assistant that reads it.
  • Jailbreaks. Tricking a model into ignoring its safety rules.
  • Data poisoning. Corrupting the data a model learns from or retrieves from, so it behaves badly later.
  • Data leakage. Getting a model to reveal secrets from its prompt, its documents or its training data.
  • Excessive agency. The model is given more power than it needs (send email, run commands, read files), so a successful injection has real consequences.

The dangerous combination is an assistant that reads untrusted content, has access to something sensitive, and can send data out. Remove any one of the three and most of the damage goes away.

02 mid // how it's actually used

The OWASP Top 10 for LLM Applications (2025 edition)

  • LLM01 Prompt injection (direct, and indirect through content the model reads)
  • LLM02 Sensitive information disclosure
  • LLM03 Supply chain (models, datasets, plugins)
  • LLM04 Data and model poisoning
  • LLM05 Improper output handling (model output used unchecked in a shell, SQL query or web page)
  • LLM06 Excessive agency
  • LLM07 System prompt leakage
  • LLM08 Vector and embedding weaknesses (RAG stores)
  • LLM09 Misinformation
  • LLM10 Unbounded consumption (cost and denial of service)

Direct vs indirect injection

Direct: the user types the attack. Mostly a problem for policy bypass. Indirect: the attacker never talks to the model; they plant text where it will be read: a web page, a shared document, an email, a code comment, an issue ticket, even a filename. Hidden formatting (white text, HTML comments, tiny fonts) hides it from humans and not from the model. The indirect case is what threatens real deployments.

Other attack families

  • Evasion / adversarial examples: small input changes that flip a classifier's decision (malware tweaked to look benign)
  • Model extraction and membership inference: probing a model to copy it or learn whether a record was in its training data
  • Supply chain: poisoned model files (some formats can execute code when loaded), malicious packages and plugins

Mitigations that actually work

  • Least privilege for every tool an agent can call
  • Human approval for anything with side effects: sending, deleting, paying, running
  • Break the triad: if it reads untrusted content, do not also give it unrestricted outbound channels and secrets
  • Treat model output as untrusted input to whatever consumes it
  • Egress controls and logging so exfiltration attempts are visible
  • Keep secrets out of prompts; keep them in systems the model cannot read

03 complex // what the pros do

Why filters are not a fix

Input filters and "ignore malicious instructions" system prompts raise the cost of an attack and can catch known patterns, but language is open-ended and the same intent can be phrased endlessly. Treat prompt injection like XSS in the early years: it must be handled by architecture, with detection as a bonus. Design as if the model is already compromised and ask what it could reach.

Design patterns

  • Privilege separation: one component reads untrusted content and can only return structured data (no tools). A separate component with tools only sees that sanitized output.
  • Allow-lists for destinations, domains and file paths, enforced outside the model
  • Confirmation with context: show the human exactly what will be sent and where, not the model's description of it
  • Capability scoping per task, short-lived credentials, read-only by default
  • Rendering controls: block automatic image or link loading from model output, a common exfiltration channel (data encoded into a URL)
  • Red-team continuously: replay known injection corpora against your own app after each change

Frameworks to know

  • MITRE ATLAS: ATT&CK-style matrix of tactics and techniques against AI systems
  • NIST AI 100-2: taxonomy of adversarial machine learning attacks and mitigations
  • NIST AI Risk Management Framework: governance-level guidance
  • OWASP GenAI Security Project: the LLM Top 10 and related guidance

Links on the news and sources page.

Reading about agent protocols

Standards for connecting models to tools (such as the Model Context Protocol) expand the attack surface: every tool description and tool result is more text the model might obey. Review third-party tool servers like you would any dependency, and watch for tools whose descriptions or outputs contain instructions.
