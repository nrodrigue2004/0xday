Prompt injection, jailbreaks and data leakage from the defender's side: what they are, why wording cannot fix them, and the design that limits the damage. Lab: spot the flaw in a support bot.

1simple2mid3complex4hands-on

01 simple // the idea in plain words

A model reads instructions and data in the same channel: plain text. It cannot reliably tell "this is my operator's rule" from "this is a sentence inside the document I was asked to read". That is the root of every issue in this chapter. It is a design property, not a bug that one clever prompt will patch.

Three problems to know

  • Prompt injection: text the attacker controls ends up in the prompt and steers the model. *Direct* means the user types it. *Indirect* means it hides in something the model reads: a web page, an email, a ticket, a file. The longer story is in attacking AI.
  • Jailbreak: getting a model to ignore its safety training or policy, usually through role-play or reframing. A fix for one phrasing rarely covers the next.
  • Data leakage: the model reveals something it should not: text from its system prompt, another user's data pulled in by retrieval, or a secret someone pasted into a chat.

The rule of thumb

Never put anything in a prompt that you could not stand to see on a screen. And never give a model more power than the worst text it will ever read could safely use.

Defense is mostly what the model is allowed to do and see, not how firmly you tell it to behave.

02 mid // how it's actually used

Why "ignore malicious instructions" is not a control

You can add a line telling the model to refuse instructions found in documents. It helps against lazy attempts and fails against others, because the model is following instructions by reading text, and the attacker's text is also text. Treat such a line as a speed bump, never as the lock.

What a defender builds instead

  • Separate trust levels. Mark untrusted content with delimiters and tell the model it is data. This lowers accidental obedience; it does not stop a determined attacker.
  • Least privilege for tools. If the assistant can only read one folder and cannot send mail, an injection has little to steal and nowhere to send it.
  • Human approval for side effects (sending, deleting, paying, running code), showing the actual action and destination, not the model's description of it.
  • Treat output as untrusted. If model output is rendered as HTML, run as a command or put in a SQL query, escape or validate it like any user input.
  • No secrets in prompts. System prompts leak, by direct request and by paraphrase. Keep keys, internal pricing and private rules in systems the model cannot read, and make the code enforce them.
  • Scope retrieval per user. A retrieval step must only fetch documents the *current* user may see, enforced in the database query, not in the prompt.
  • Egress and logging. Log every tool call and block unexpected outbound destinations. An injection you can see is an injection you can respond to.

Jailbreak defense in practice

Layer it: a clear system policy, an input and output check (classifier or rules), rate limits per user, and abuse logging with a review path. Expect new phrasings and keep a regression set of known attempts (from public research such as the OWASP GenAI project) to rerun after every change. That is the same eval-set habit from the previous chapter, pointed at safety.

Leakage checklist

Does the prompt contain a secret? Can one user's data reach another's context? Do logs store prompts with personal data? Do you tell users not to paste credentials? Is training on your data switched on or off, and do you know which?

03 complex // what the pros do

The lethal combination

An assistant is dangerous when it has all three of: (1) untrusted input, (2) access to private data, (3) a way to send data out (email, a web request, even rendering a link or image whose URL carries data). Remove any one and the worst case drops sharply. When you review a design, draw the three circles and see where they overlap.

Architecture patterns

  • Dual model / quarantine: a model with no tools reads the untrusted content and returns only structured fields. A privileged model with tools sees those fields, never the raw text.
  • Capability tokens per task: short-lived, narrow credentials issued for one job, so a hijacked task cannot reach anything else.
  • Allow-lists enforced in code: destination domains, file paths and recipient addresses are checked by the tool wrapper, not requested of the model.
  • Output rendering controls: do not auto-load images or links from model output; strip or rewrite URLs before display.
  • Confirmation with provenance: show the human which document or message caused the request.

Measuring it

Write an injection test set for your own app on fictional data: documents carrying instructions of the kind your tools could act on, then assert that no forbidden tool call happened, whatever the model said. Judge the action log, not the chat text. Run it on every prompt, model or tool change. Track the results over time and treat a regression like a failed unit test.

Governance notes

Map findings to shared language: the OWASP Top 10 for LLM Applications (LLM01 prompt injection, LLM02 sensitive information disclosure, LLM07 system prompt leakage), MITRE ATLAS techniques, and NIST AI 100-2 for the adversarial ML taxonomy. Keep a record of which data classes are allowed in which AI tool, and train users on it. See also using AI well.

Scope of this site

This site teaches the defense side: recognizing the pattern, designing so it does little harm, and testing your own systems. It does not publish working attack kits, and the labs use fictional data and fictional companies. Test only systems you own or are authorized to test.
