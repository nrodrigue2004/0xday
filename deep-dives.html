Cybersecurity Homelab

A seven-VM enterprise network on a single Proxmox host, built so I have somewhere to practice both attacking and defending something that looks like a real company.

Proxmox VEpfSenseTailscaleWindows Server / ADWindows 11Ubuntu + DockerKaliMetasploitableSecurity OnionZeekSuricata

The idea

I wanted one environment where I could run an attack and then go watch what it looked like from the defender's chair, instead of treating offense and defense as separate worlds. Everything runs on one box: an i7-10900K with 64 GB of RAM and a 2 TB SSD, virtualized with Proxmox.

The whole thing is isolated. Nothing is published to the internet, remote access is over Tailscale only, and every public note uses placeholders instead of the real address plan.

Design decisions

pfSense sits between the upstream network and the lab segment and does all the routing, DHCP, DNS and firewalling. The rules are default-deny: the vulnerable boxes get no internet at all, and traffic is only allowed where an exercise needs it.

Security Onion watches a mirrored copy of the lab traffic on a sniffing interface with no IP of its own, so monitoring never changes what it's monitoring. Remote admin goes through Tailscale's subnet routing, which means I never had to forward a single port to reach the lab from outside.

Build log

Stood up Proxmox and carved the network into virtual bridges for the upstream path and the lab segment.

Installed pfSense and wrote the segmentation rules, with DHCP and DNS for the lab.

Built the Windows Server domain controller, created the lab.local domain, OUs, users and groups, then joined a Windows 11 workstation.

Added the Ubuntu box with DVWA and WebGoat in Docker, plus Kali and Metasploitable for controlled testing.

Deployed Security Onion against a span port and confirmed Zeek and Suricata were seeing lab traffic.

What I learned

Segmentation is the feature. Half of what makes the lab safe is just pfSense refusing traffic that has no reason to exist.

You can't defend what you can't see. Getting the mirror port right so Security Onion actually received traffic taught me more about network monitoring than any reading did.

Document as you go, and sanitize as you go. Writing public-safe notes forced me to be deliberate about what's an identifier and what's a concept.

What's next

Evidence-based attack-and-detection walkthroughs with sanitized screenshots, so the detections are backed by real telemetry instead of expectations. The attack chain on this site is the scripted version of exactly that.

Enterprise IT Support Lab

A Windows domain with a real help-desk ticketing system on top, built to practice the day-one work of IT support: AD, Group Policy, PowerShell, permissions, and actually closing a ticket.

ProxmoxWindows Server / ADWindows 11Group PolicyPowerShellNTFS / SMBUbuntuosTicketApachePHPMariaDB

The idea

The homelab is for security; this one is for the support fundamentals underneath it. I built a lab.local domain and stood up osTicket so I could work tickets end to end the way a help desk actually does, not just click around in Active Directory.

Design decisions

Windows Server runs Active Directory and a Finance SMB share. The share is protected with both share-level and NTFS permissions on purpose, so I could see layered access control behave the way it does in a real environment.

osTicket runs on Ubuntu with Apache, PHP and MariaDB, with an IT Support department and public help topics, so every exercise ends in a documented, closed ticket instead of a loose note.

The signature ticket

A user can sign in and reach the Finance share but gets access denied when they open it. The fix is a lesson in itself:

Reproduce it from the domain-joined workstation, check the user's AD group membership, find they're missing from Finance-Share-Read, add them with PowerShell, and have them sign out and back in so Windows issues a fresh token.

The sign-out is the whole point: group membership is baked into the access token at logon, so adding someone to a group does nothing for their current session. That one detail is behind a huge share of 'but I fixed it' tickets.

What I learned

PowerShell beats clicking. Provisioning a user, placing them in an OU, setting a password and adding them to a group is a few lines, and it's repeatable.

Group Policy is how one change reaches every machine. I used a GPO to map the Finance share as a drive automatically, then validated it with gpupdate and gpresult.

Closing the ticket matters as much as fixing the problem. Writing the resolution in osTicket is the part that makes it support work and not just tinkering.

What's next

More ticket scenarios: printer and GPO conflicts, roaming-profile issues, and account lockouts, each written up as a reproducible walkthrough.
