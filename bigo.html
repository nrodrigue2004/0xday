man big-o

~/bigo time complexity

Big-O answers one question: when the input gets bigger, how much more work does the code do? It ignores constants and small terms, so 3n + 20 is just O(n). It describes the growth, not the stopwatch time.

three levels

simple. Count the loops. No loop over the input: O(1). One loop: O(n). A loop inside a loop over the same input: O(n²). Cutting the problem in half each step: O(log n).

mid. Drop constants and keep the biggest term: n² + n is O(n²). Separate loops add (O(n + m)), nested loops multiply (O(n·m)). Watch for hidden loops: x in list, list.index(), string concatenation in a loop and slicing are all O(n) on their own. Space counts too: building a set of n items is O(n) extra memory.

complex. Big-O is an upper bound, Θ is a tight bound, Ω is a lower bound; interviews say "O" and mean Θ. Know best, average and worst case (quicksort is O(n log n) on average, O(n²) on a bad pivot) and amortized cost (appending to a dynamic array is O(1) amortized even though a resize is O(n)). For recursion, count calls × work per call: the master theorem gives T(n) = 2T(n/2) + O(n) = O(n log n) for merge sort. Comparison sorting can't beat O(n log n). Security angle: algorithmic complexity attacks (hash flooding, ReDoS) push code into its worst case on purpose.

the six you need

O(1) constant

Same work no matter how big the input is.

def first(a):
    return a[0]          # one step, 10 items or 10 million

seen in: Array index, hash map get/set, push/pop on a stack.

O(log n) logarithmic

Each step throws away half of what's left. A million items is about 20 steps.

def search(a, x):         # a is sorted
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == x: return mid
        if a[mid] < x: lo = mid + 1
        else: hi = mid - 1
    return -1

seen in: Binary search, balanced tree lookups, heap push/pop.

O(n) linear

Look at every item once. Double the input, double the work.

def biggest(a):
    best = a[0]
    for x in a:            # n steps
        best = max(best, x)
    return best

seen in: Scanning a log file, summing a list, x in list.

O(n log n) linearithmic

A log n amount of work for each of the n items. The floor for comparison sorting.

sorted(a)                  # Timsort
# merge sort: split in half (log n levels),
# merge each level (n work per level)

seen in: Merge sort, heapsort, average quicksort, sort-then-scan tricks.

O(n²) quadratic

Compare everything with everything. Fine at 100 items, painful at 100,000.

def has_dup(a):
    for i in range(len(a)):
        for j in range(i + 1, len(a)):   # nested loop over the same input
            if a[i] == a[j]: return True
    return False

seen in: Bubble/insertion sort, naive duplicate checks, all pairs.

O(2ⁿ) exponential

Every extra item doubles the work. n = 50 is already out of reach.

def fib(n):
    if n < 2: return n
    return fib(n - 1) + fib(n - 2)    # two calls per call

seen in: Naive recursion, trying every subset, brute-forcing a key.
