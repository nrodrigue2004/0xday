CS220 Operating systems

Processes, scheduling, virtual memory, file systems, concurrency and deadlock, with scheduler, paging and Banker's simulators.

needs: CS210, IT120 · 7 modules · ~9 h of study · not started

# modules

  1. 1. Processes and threads ~90 min

    ~/learn: operating systems ~/man: operating-systems cheatsheet OSTEP: processes, free book

    A program is a file; a process is a running instance with its own address space (code, globals, heap, stack), open files and a process ID. The kernel tracks each in a process control block (PCB). States: new, ready, running, waiting (blocked on I/O), terminated. A context switch saves one process's registers and program counter into its PCB and loads another's.

    On Unix a new process starts with fork(), which copies the caller and returns 0 in the child and the child's PID in the parent. exec() replaces the current program image with a new one; wait() collects the exit status. That is how a shell runs a command: fork, exec in the child, wait in the parent. A child that exited but was not waited for is a zombie; a child whose parent died is an orphan, adopted by init.

    Threads live inside a process and share the heap, globals and open files, but each has its own stack, registers and program counter. That makes them cheap and also dangerous: shared memory needs locks. Processes talk through IPC: pipes, sockets, signals, shared memory. User code asks the kernel for services through system calls, a controlled trap into kernel mode. On Linux, try `strace ls` to watch them.

  2. 2. CPU scheduling ~75 min

    ~/ossim: scheduler simulator OSTEP: scheduling

    The scheduler picks which ready process gets the CPU. Metrics: turnaround = completion - arrival; waiting = turnaround - burst; response = first run - arrival. Policies: FCFS (simple, suffers the convoy effect, where short jobs wait behind a long one); SJF (shortest next burst first, minimizes average waiting time but needs burst lengths and can starve long jobs); SRTF (the preemptive version); priority (aging prevents starvation); round robin (each job gets a fixed quantum, good response time, quantum too big becomes FCFS and too small drowns in switching); multilevel feedback queue (start high, demote CPU hogs, keeps interactive jobs snappy without knowing lengths).

    Worked example: bursts 24, 3, 3, all arriving at time 0. FCFS waits are 0, 24, 27, average 17. SJF runs 3, 3, 24 for waits 0, 3, 6, average 3. Do it by hand first, then check it in the simulator; change the quantum and watch round robin move between the two.

  3. 3. Virtual memory ~90 min

    ~/ossim: page replacement simulator OSTEP: virtual memory ~/learn: binary exploitation

    Each process sees its own virtual address space. The hardware MMU translates virtual to physical addresses using page tables: memory is cut into pages (usually 4 KiB), and a virtual address splits into a virtual page number and an offset. With 32-bit addresses and 4 KiB pages the offset is 12 bits and there are 2^20 page numbers, so real systems use multi-level tables. The TLB caches recent translations.

    Pages need not all be in RAM. Touching a valid page that is on disk causes a page fault, and the OS loads it (demand paging). When RAM is full something must be evicted: FIFO, LRU, clock, and the unbuildable optimal (OPT) used as a yardstick. FIFO can get worse with more frames (Belady's anomaly): the string 1,2,3,4,1,2,5,1,2,3,4,5 gives 9 faults with 3 frames and 10 with 4. If working sets exceed RAM the machine thrashes. Copy-on-write lets fork() share pages until one side writes.

    Security link: page permissions give the NX bit (data is not executable) and let the OS keep user code out of kernel memory. ASLR randomizes the layout so exploits can't hard-code addresses. Segmentation faults are the OS stopping a bad access.

  4. 4. File systems ~75 min

    ~/learn: digital forensics ~/learn: Autopsy and FTK Imager OSTEP: file systems

    A Unix file is an inode: owner, permissions, size, timestamps and pointers to data blocks. The name is not in the inode; a directory is a table of name-to-inode entries. So one inode can have several names (hard links, tracked by a link count), and a symbolic link is a tiny file holding a path. Deleting a file removes a name; when the link count reaches zero the blocks are marked free, but the data usually stays on disk until reused, which is what forensic recovery relies on. Space after a file's last byte in its final block is slack space.

    An inode typically holds 12 direct pointers and then single, double and triple indirect blocks. With 4 KiB blocks and 4-byte pointers: direct covers 48 KiB, single indirect 1024 x 4 KiB = 4 MiB, double indirect 4 GiB. Alternatives are contiguous allocation (fast, fragments) and linked allocation (FAT).

    A crash halfway through an update can leave the filesystem inconsistent. Journaling filesystems (ext4, NTFS) log the change first and replay it after a crash. Permissions: rwx for owner, group and others, e.g. 640 is rw-r-----. Mount points and the VFS layer let many filesystems appear in one tree.

  5. 5. Concurrency and synchronization ~90 min

    OSTEP: concurrency ~/dojo

    A race condition is when the result depends on how threads interleave. counter++ compiles to load, add, store, so two threads can both load 5 and both store 6. The region that touches shared state is the critical section, and it needs mutual exclusion.

    Tools: a mutex (lock/unlock); a semaphore, a counter with atomic wait (decrement, block at 0) and signal (increment); condition variables to sleep until something changes; monitors that bundle a lock with its conditions. Hardware supplies atomic instructions: test-and-set and compare-and-swap (CAS). A spinlock busy-waits and is right only for very short holds; a mutex puts the thread to sleep.

    Classic problems: producer/consumer (semaphores empty = N, full = 0, plus a mutex), readers/writers, dining philosophers. Each exists to practice reasoning about ordering. Security link: TOCTOU. A program that checks a file with access() and then opens it can be raced by an attacker who swaps in a symlink. Operate on one file descriptor instead of re-resolving a name.

  6. 6. Deadlock ~60 min

    ~/ossim: Banker's algorithm simulator OSTEP: deadlock

    Deadlock needs all four Coffman conditions at once: mutual exclusion, hold and wait, no preemption, circular wait. Break any one and it cannot happen. Prevention in practice: lock ordering (every thread takes locks in the same global order) kills circular wait; take-all-or-nothing kills hold and wait; try-lock with backoff avoids waiting forever. Detection: build a wait-for graph and look for a cycle, then recover by killing or rolling back a process. Livelock is when threads keep reacting to each other without progress; starvation is when one never gets the resource.

    Avoidance with the Banker's algorithm: each process declares its maximum need; need = max - allocation. A state is safe if some order exists where every process can finish. Grant a request only if the resulting state is still safe. Example: available (3,3,2); P1 needs (1,2,2), which fits, so P1 can finish and return its resources, and the sequence continues. The simulator finds a safe sequence for you.

  7. 7. OS security and protection ~60 min

    ~/learn: system hardening ~/learn: binary exploitation ~/learn: Linux server admin

    Protection starts in hardware: user mode and kernel mode (rings). User code can't run privileged instructions or touch kernel memory; it asks through system calls. The kernel then checks permissions: DAC (owners set access, normal Unix and Windows ACLs) and MAC (a central policy such as SELinux or AppArmor that owners can't override). Least privilege means each process and account gets only what it needs.

    Privilege escalation targets the gaps: setuid-root programs (`find / -perm -4000`), sudo misconfigurations, writable service files, vulnerable drivers. Exploit mitigations make memory bugs harder: NX/DEP, ASLR, stack canaries, RELRO, control-flow integrity. Isolation: containers use namespaces (what a process sees) and cgroups (what it can use) but share the host kernel, so a kernel bug breaks them; VMs add a hypervisor boundary.

    A kernel-level rootkit can lie to user-mode tools about files and processes, which is why defenders use memory forensics and offline scans. Pair this module with the hardening guide and run the checklist on your own machine.
