CS230 Databases

Relational model, normalization, indexes, query plans, transactions and database security, with a dependency tool, an index demo and a serializability checker.

needs: none · 6 modules · ~7.8 h of study · not started

# modules

  1. 1. The relational model and SQL ~90 min

    ~/learn: SQL ~/learn: databases and SQL ~/basics: relational databases ~/man: SQL cheatsheet

    Data lives in relations (tables) of tuples (rows) over attributes (columns). A superkey identifies a row; a candidate key is a minimal superkey; the primary key is the candidate you choose; a foreign key must match a row in another table or be NULL (referential integrity). Relational algebra is the theory under SQL: selection picks rows (WHERE), projection picks columns (SELECT list), join combines tables.

    Refresh the core: SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT. WHERE filters rows before grouping; HAVING filters groups after aggregates. INNER JOIN keeps matches only; LEFT JOIN keeps every left row, filling NULLs, and `WHERE right.id IS NULL` finds rows with no match. NULL is unknown, so `= NULL` never matches; use IS NULL. Know the logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. Practice in the SQL guide's shell before continuing.

  2. 2. Design and normalization ~90 min

    ~/dbsim: functional dependency tool ~/basics: relational databases

    Bad design causes anomalies: update (the same fact stored in many rows, change one and miss another), insert (cannot record a fact without an unrelated one), delete (removing a row loses an unrelated fact). Normalization removes them using functional dependencies: A -> B means rows that agree on A agree on B.

    1NF: atomic values, no repeating groups. 2NF: 1NF plus no partial dependency (a non-key column depending on only part of a composite key). 3NF: 2NF plus no transitive dependency (a non-key column determined by another non-key column). BCNF: every determinant is a candidate key. A handy rule: every non-key column depends on the key, the whole key, and nothing but the key.

    Example: Orders(order_id, product_id, qty, product_name, customer_id, customer_email) with key (order_id, product_id). product_name depends on product_id alone (partial). customer_email depends on customer_id (transitive). Split into orders, order_lines, products, customers. Model many-to-many with a junction table. Denormalize only on purpose, for measured read speed. Use the dependency tool to find keys and the highest normal form.

  3. 3. Indexes ~75 min

    ~/dbsim: index versus scan demo Use The Index, Luke (free)

    An index is a separate sorted structure that lets the database find rows without reading the whole table. Most are B-trees: shallow and wide, so one lookup in millions of rows is a handful of page reads (O(log n)) and range scans and ORDER BY come free. Hash indexes are O(1) for equality but have no ordering. A clustered index defines the physical row order (one per table); non-clustered indexes point back to rows. A covering index holds every column the query needs, so the table isn't touched.

    Rules of thumb: a composite index (a, b) helps filters on a or on a and b, not b alone (leftmost prefix). A function on the column (UPPER(name), DATE(ts)) or a leading wildcard (LIKE '%son') usually defeats the index. Index the columns you filter, join and sort on. Low selectivity (a boolean) rarely pays. Every index slows writes and costs space, so do not index everything. Primary keys and unique constraints get one automatically; foreign keys often don't.

  4. 4. Query plans and the optimizer ~60 min

    ~/dbsim: index versus scan demo SQLite EXPLAIN QUERY PLAN ~/learn: databases and SQL

    The optimizer turns a query into a plan: access method for each table (sequential scan, index scan, index-only scan), join algorithm, join order. Nested loop join: for each outer row probe the inner, great with an index on the inner side. Hash join: build a hash table of one input, probe with the other, good for big equality joins. Merge join: both inputs sorted, walk them together. The optimizer picks the cheapest from row-count estimates based on statistics (run ANALYZE after big changes).

    Read plans with EXPLAIN (add ANALYZE in PostgreSQL for real timings). Red flags: a sequential scan on a large table for a selective filter, estimated rows far from actual rows, a sort that spills to disk, a nested loop over millions of rows. Fix loop: look at the plan, add or change an index, re-run, compare. Write queries so the optimizer can use indexes: compare the bare column to a constant, avoid SELECT * when a narrow covering index would do.

  5. 5. Transactions and ACID ~90 min

    ~/dbsim: schedule serializability checker ~/learn: databases and SQL

    A transaction is a group of statements treated as one unit (BEGIN ... COMMIT or ROLLBACK). ACID: Atomicity (all or nothing), Consistency (constraints hold before and after), Isolation (concurrent transactions don't see each other's half-done work), Durability (committed data survives a crash).

    Durability and atomicity come from write-ahead logging: log the change to disk first, then apply it; after a crash, redo committed work and undo the rest. Isolation levels trade safety for speed: READ UNCOMMITTED allows dirty reads; READ COMMITTED stops them; REPEATABLE READ also stops non-repeatable reads; SERIALIZABLE also stops phantoms and behaves as if transactions ran one at a time. Implementations use two-phase locking or MVCC, where readers see a snapshot and don't block writers. Concurrent locks can deadlock; the database aborts one victim, so applications should retry.

    A schedule is conflict-serializable if its precedence graph (an edge Ti -> Tj when an operation of Ti conflicts with and precedes one of Tj) has no cycle. Try some in the checker.

  6. 6. Database security ~60 min

    ~/basics: web attack classes ~/learn: MongoDB and NoSQL ~/learn: secure data sanitization

    SQL injection happens when user input is concatenated into a query so it's parsed as SQL. The fix is parameterized queries (prepared statements), which keep data separate from code. Escaping by hand is fragile. Add least privilege: the web app's account gets only the statements and tables it needs, never DROP or file-write rights. NoSQL stores have the same problem in a different shape, e.g. operator injection with {"$ne": null} in a login query.

    Store passwords as salted hashes from a slow algorithm (bcrypt, scrypt, Argon2), never reversible encryption. Encrypt data at rest to protect stolen disks and backups, and use TLS in transit; neither stops injection. Turn on auditing, patch the engine, don't expose the port to the internet, remove default accounts. Backups: keep copies offline or immutable so ransomware with database credentials can't destroy them, and test a restore before you need it.
