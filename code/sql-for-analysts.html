Ask a table of alerts real questions: who, how many, which asset. SQL for the analyst who lives in the SIEM. Practice with GROUP BY, JOIN and HAVING.

1simple2mid3complex4hands-on+ref

01 simple // the idea in plain words

A SIEM or IDS stores events as rows in tables. SQL lets you ask the table a question instead of scrolling it. If you can say the question in a sentence, you can usually write it:

  • "show me the alerts from this IP" is SELECT ... WHERE src = '...'
  • "how many alerts per signature" is GROUP BY sig with COUNT(*)
  • "which alerts hit important machines" is a JOIN to the asset table
$ sqlite3 soc.db "SELECT sig, COUNT(*) FROM alerts GROUP BY sig ORDER BY 2 DESC"

Read a query in this order: FROM (which table), WHERE (which rows), GROUP BY (bucket them), SELECT (what to show), ORDER BY, LIMIT. It is not the order you type it, and it explains most beginner errors.

Three habits

  • LIMIT 20 while you explore so a huge table does not flood the screen
  • COUNT(*) first, to see how big the answer is before printing it
  • Quote text values with single quotes: WHERE sig = 'ET SCAN Nmap'

02 mid // how it's actually used

Counting and grouping

GROUP BY collapses rows that share a value, and an aggregate (COUNT, SUM, MIN, MAX, AVG) summarises each group.

$ sqlite3 soc.db "SELECT src, COUNT(*) AS n FROM alerts GROUP BY src ORDER BY n DESC LIMIT 5"
$ sqlite3 soc.db "SELECT dst, COUNT(DISTINCT src) AS sources FROM alerts GROUP BY dst ORDER BY sources DESC"

COUNT(*) counts alerts. COUNT(DISTINCT src) counts different attackers. They answer different questions, and mixing them up is the classic analyst bug: one noisy scanner makes a quiet asset look busy.

WHERE versus HAVING

WHERE filters rows before grouping. HAVING filters groups after it.

$ sqlite3 soc.db "SELECT src, COUNT(*) FROM alerts WHERE sev >= 2 GROUP BY src HAVING COUNT(*) > 5"

Joins: add the context

The alert table has IPs. The asset table knows which IP is the domain controller. A JOIN lines them up on a shared column.

$ sqlite3 soc.db "SELECT a.host, a.crit, COUNT(*) FROM alerts x JOIN assets a ON a.ip = x.dst GROUP BY a.host ORDER BY 3 DESC"

An INNER JOIN (the default) drops alerts whose destination is not in assets. LEFT JOIN keeps them with empty asset columns, which is how you find machines nobody inventoried.

03 complex // what the pros do

Windows, subqueries and CTEs

  • Subquery: WHERE src IN (SELECT src FROM alerts WHERE sig LIKE '%Cobalt%') finds everything else that attacker did
  • CTE (WITH noisy AS (...) SELECT ...) names an intermediate result so a long query reads top to bottom
  • Window function: COUNT(*) OVER (PARTITION BY src) keeps every row and adds the group total beside it
  • Time buckets: timestamps are epoch seconds here, so ts / 3600 groups by hour: GROUP BY ts / 3600
$ sqlite3 soc.db "WITH per AS (SELECT dst, COUNT(DISTINCT src) AS srcs FROM alerts GROUP BY dst) SELECT a.host, per.srcs FROM per JOIN assets a ON a.ip = per.dst WHERE a.crit = 'high' ORDER BY per.srcs DESC"

Habits that hold up on a real SIEM

  • Index the columns you filter and join on (CREATE INDEX idx_src ON alerts(src)). A lookup on an indexed column is a tree walk, O(log n), instead of reading every row, O(n). Same idea as the Big-O page.
  • **EXPLAIN QUERY PLAN** shows whether the query uses the index or scans the table.
  • Parameterise, never concatenate. Building SQL from user input is SQL injection; every language has a placeholder syntax (? in sqlite).
  • Query read-only. Use an account that cannot UPDATE or DELETE when you are only investigating.
  • SIEMs have their own languages (SPL, KQL), but the same ideas carry over: filter, group, count, join. More reps in the SQL dojo.
